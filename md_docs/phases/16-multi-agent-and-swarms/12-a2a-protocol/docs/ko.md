# A2A — 에이전트-투-에이전트 프로토콜

> Google은 2025년 4월 A2A를 발표했습니다; 2026년 4월까지 스펙은 https://a2a-protocol.org/latest/specification/에 있으며 150개 이상의 조직이 이를 지지합니다. A2A는 MCP (Lesson 13)에 대한 수평 보완입니다: MCP가 수직(에이전트 ↔ 툴)이라면, A2A는 피어투피어(에이전트 ↔ 에이전트)입니다. 에이전트 카드(검색), 아티팩트가 있는 작업(텍스트, 구조화된 데이터, 비디오), 불투명한 작업 수명주기, 인증을 정의합니다. 프로덕션 멀티에이전트 시스템은 점점 더 MCP와 A2A를 쌍으로 사용합니다. Google Cloud는 2025-2026년에 Vertex AI Agent Builder에 A2A 지원을 출시했습니다.

**유형:** 학습 + 실습
**언어:** Python (stdlib, `http.server`, `json`)
**선수 과목:** Phase 16 · 04 (Primitive Model)
**소요 시간:** ~75분

## 문제

에이전트가 다른 시스템의 다른 에이전트를 호출해야 합니다. 어떻게? HTTP 엔드포인트를 노출하고, 사용자 정의 JSON 스키마를 정의하고, 다른 쪽이 그것을 사용하기를 희망합니다. 에이전트 모든 쌍이 사용자 정의 통합이 됩니다.

A2A는 해당 호출을 위한 범용 와이어 프로토콜입니다. 표준 검색, 표준 작업 모델, 표준 전송, 표준 아티팩트. 에이전트를 1순위 시민으로 하는 HTTP+REST와 같습니다.

## 개념

### 4가지 요소

**에이전트 카드.** 에이전트를 설명하는 `/.well-known/agent.json`의 JSON 문서: 이름, 스킬, 엔드포인트, 지원 양식, 인증 요구사항. 카드를 읽으면 검색이 발생합니다.

```
GET https://agent.example.com/.well-known/agent.json
→ {
    "name": "code-review-agent",
    "skills": ["review-python", "review-typescript"],
    "endpoints": {
      "tasks": "https://agent.example.com/tasks"
    },
    "auth": {"type": "bearer"},
    "modalities": ["text", "structured"]
  }
```

**작업.** 작업 단위. 수명주기: `제출됨 → 작업 중 → 완료/실패/취소`가 있는 비동기 상태 저장 객체. 클라이언트가 작업을 보내고 업데이트를 폴링하거나 구독합니다.

**아티팩트.** 작업이 produced하는 결과 유형. 텍스트, 구조화된 JSON, 이미지, 비디오, 오디오. 아티팩트가 형식화되어 있어 다양한 양식이 1순위입니다.

**불투명한 수명주기.** A2A는 원격 에이전트가 작업을 *어떻게* 해결하는지 규정하지 않습니다. 클라이언트는 상태 전환과 아티팩트를 봅니다; 구현은 любой 프레임워크를 사용할 자유가 있습니다.

### MCP/A2A 분할

- **MCP** (Lesson 13): 에이전트 ↔ 툴. 에이전트가 JSON-RPC를 통해 툴 서버에 읽기/쓰기합니다. 기본적으로 무상태.
- **A2A**: 에이전트 ↔ 에이전트. 피어 프로토콜; 양쪽 모두 자체 추론이 있는 에이전트입니다.

프로덕션 멀티에이전트 시스템은 둘 다 사용합니다. A2A 피어가 자체側の MCP 툴을 호출합니다. 분할이 두 concerns를 분리된 상태로 유지합니다.

### 검색 흐름

```
클라이언트                     에이전트 서버
  ├──GET /.well-known/agent.json──>
  <──에이전트 카드 JSON─────────────
  ├──POST /tasks {skill, input}──>
  <──201 task_id, state=제출됨
  ├──GET /tasks/{id}──────────────>
  <──state=작업 중, 42% 완료──────
  ├──GET /tasks/{id}──────────────>
  <──state=완료됨, 아티팩트──
```

또는 스트리밍 사용: push 업데이트를 위한 `/tasks/{id}/events`에 SSE 구독.

### 인증

A2A는 세 가지 일반적인 패턴을 지원합니다:

- **Bearer 토큰** — OAuth2 또는 불투명.
- **mTLS** — 상호 TLS; 조직이 서로에게 ID를 증명합니다.
- **서명된 요청** — 페이로드에 대한 HMAC.

인증은 에이전트 카드에 선언됩니다; 클라이언트가 검색하고 준수합니다.

### 2026년 4월 기준 150개 이상의 조직

기업 채택이 A2A 규모를 이끌었습니다. 핵심: A2A는 기업 에이전트 시스템이 신뢰 경계를 교차하는 방식이 되었습니다. Google Cloud가 Vertex AI Agent Builder A2A 지원을 출시했습니다; Microsoft Agent Framework가 그것을 지원합니다; 대부분의 주요 프레임워크(LangGraph, CrewAI, AutoGen)가 A2A 어댑터를 제공합니다.

### A2A가 이기는 곳

- **조직 간 호출.** 회사 A의 에이전트가 회사 B의 에이전트를 호출합니다. A2A 없이는 모든 쌍이 사용자 정의 계약입니다.
- **이기종 프레임워크.** LangGraph 에이전트가 CrewAI 에이전트를 호출하고 사용자 정의 Python 에이전트를 호출합니다. A2A가 정규화합니다.
- **형식화된 아티팩트.** 비디오 결과, 구조화된 JSON, 오디오 — 모두 1순위.
- **장기 실행 작업.** 불투명한 수명주기 + 폴링이 수 시간 작업을 간단하게 만듭니다.

### A2A가艰难的 곳

- **지연 시간 민감한 마이크로 호출.** A2A의 수명주기는 비동기입니다. 1밀리초 미만의 에이전트-투-에이전트는 맞지 않습니다; 직접 RPC를 사용하세요.
- **긴밀하게 결합된 프로세스 내 에이전트.** 두 에이전트가同一个 Python 프로세스에서 실행되면, A2A의 HTTP 라운드트립이 과합니다.
- **소규모 팀.** 스펙 오버헤드가 실제로 있습니다; 내부 전용 에이전트는 형식주의가 필요하지 않을 수 있습니다.

### A2A 대 ACP, ANP, NLIP

2024-2026년에 여러 관련 스펙이 등장했습니다:

- **ACP** (IBM/Linux Foundation) — A2A의 선행자, 더 좁은 범위.
- **ANP** (Agent Network Protocol) — 피어 검색 중시, 분산 우선.
- **NLIP** (Ecma Natural Language Interaction Protocol, 2025년 12월 표준화) — 자연어 콘텐츠 유형.

A2A는 2026년 4월 기준으로 가장 많이 채택된 피어 프로토콜입니다. 비교는 arXiv:2505.02279 (Liu et al., "에이전트 상호운용성 프로토콜 조사")를 참조하세요.

## 실습

`code/main.py`는 `http.server`와 JSON을 사용하여 A2A-최소 서버와 클라이언트를 구현합니다. 서버:

- `/.well-known/agent.json`을 노출하고,
- `POST /tasks`를 수락하고,
- 작업 상태를 관리하고,
- `GET /tasks/{id}`에서 아티팩트를 반환합니다.

클라이언트:

- 에이전트 카드를 가져오고,
- 작업을 제출하고,
- 완료될 때까지 폴링하고,
- 아티팩트를 읽습니다.

실행:

```
python3 code/main.py
```

스크립트가 백그라운드 스레드에서 서버를 시작하고, 그에 대해 클라이언트를 실행합니다. 완전한 흐름이 보입니다: 검색, 제출, 폴링, 아티팩트.

## 활용

`outputs/skill-a2a-integrator.md`가 A2A 통합을 설계합니다: 에이전트 카드 내용, 작업 스키마, 인증 선택, 스트리밍 대 폴링.

## 결과물

체크리스트:

- **스펙 버전을 고정합니다.** A2A는 여전히 진화 중입니다; 에이전트 카드가 프로토콜 버전을 선언해야 합니다.
- **멱등 작업 생성.** 중복 제출(네트워크 재시도)이 하나의 작업을 produced해야 합니다.
- **아티팩트 스키마.** 에이전트가 반환하는 형태를 선언합니다; 소비자가 검증해야 합니다.
- **속도 제한 + 인증.** A2A는 공개 facing입니다; 표준 웹 보안을 적용하세요.
- **실패한 작업의 데드 레터.** 반복적인 실패 유형에 대한 패턴을 시간에 따라 검사합니다.

## 연습 문제

1. `code/main.py`를 실행합니다. 클라이언트가 서버를 검색하고 올바른 아티팩트를 수신하는 것을 확인합니다.
2. 서버에 두 번째 스킬을 추가합니다 (예: "요약"). 에이전트 카드를 업데이트합니다. 작업 유형 기반으로 스킬을 선택하는 클라이언트를 작성합니다.
3. SSE 스트리밍 엔드포인트를 구현합니다: 상태 변화를 emits하는 `/tasks/{id}/events`. 클라이언트가 무엇을 다르게 해야 합니까?
4. A2A 스펙 (https://a2a-protocol.org/latest/specification/)을 읽습니다. 스펙이 규정하는 세 가지를 이 데모가 구현하지 않는 것을 식별합니다.
5. A2A (에이전트 카드 검색) 대 MCP (`listTools`를 통한 서버 측 기능 목록)를 비교합니다. 자기 기술 에이전트와 기능 프로빙 사이의 트레이드오프는 무엇입니까?

## 핵심 용어

| 용어 |人们在说什么 | 实际含义 |
|------|----------------|------------------------|
| A2A | "에이전트-투-에이전트" | 시스템 간 다른 에이전트를 호출하기 위한 피어 프로토콜. Google 2025. |
| 에이전트 카드 | "에이전트의 명함" | 기술, 엔드포인트, 인증을 설명하는 `/.well-known/agent.json`의 JSON. |
| 작업 | "작업 단위" | 수명주기가 있는 비동기 상태 저장 객체; 완료 시 produced되는 아티팩트. |
| 아티팩트 | "결과" | 형식화된 출력: 텍스트, 구조화된 JSON, 이미지, 비디오, 오디오. 1순위 미디어. |
| 불투명한 수명주기 | "해결 방법은 에이전트의 일입니다" | 클라이언트가 상태 전환을 봅니다; 서버가 프레임워크/도구 선택에 자유롭습니다. |
| 검색 | "에이전트 찾기" | `GET /.well-known/agent.json`이 카드를 반환합니다. |
| MCP 대 A2A | "도구 대 피어" | MCP: 수직 에이전트 ↔ 툴. A2A: 수평 에이전트 ↔ 에이전트. |
| ACP / ANP / NLIP | "자매 프로토콜" | 인접 스펙; A2A가 2026년 가장 많이 채택됨. |
