# 공유 메모리 및 블랙보드 패턴

> 2026년 멀티에이전트 시스템에서 두 가지 접근 방식이 공존합니다: **메시지 풀** (모두가所有人的 메시지를 보는, AutoGen GroupChat 또는 MetaGPT에서처럼)과 **구독이 있는 블랙보드** (에이전트가 관련 이벤트에 구독하는, Context-Aware MCP 또는 Matrix 프레임워크에서처럼). 둘 다 멀티에이전트 시스템에서 유일하게 상태 저장인 부분입니다 — 즉 둘 다 흥미로운 버그가 있는 곳입니다. 참조 실패 모드는 **메모리 중독**입니다: 하나의 에이전트가 "사실"을 환각하고, 다른 에이전트가それを 확인된ものとして扱い, 정확도가 점진적으로 저하됩니다. 이는 즉각적인 크래시보다 디버깅하기 훨씬 어려운 방식입니다. 이 레슨은 두 구조를 stdlib에서 구축하고, 중독 공격을 주입하며, 실제로 프로덕션에서 작동하는 세 가지 완화를 보여줍니다.

**유형:** 학습 + 실습
**언어:** Python (stdlib, `threading`)
**선수 과목:** Phase 16 · 04 (Primitive Model), Phase 16 · 09 (Parallel Swarm Networks)
**소요 시간:** ~75분

## 문제

멀티에이전트 시스템은 에이전트가 사실을 공유할 곳이 필요합니다. 문자 그대로의 옵션은 "메시지로 모두 전달"입니다 — 하지만 이는 추가 복사로 공유 상태를 재발명합니다. 또 다른 옵션은 "모두에게 전역 로그를 제공"입니다 — 하지만 전역 로그는 무제한으로 성장하고 쉽게 중독됩니다. 세 번째 옵션은 "에이전트당 보기을 투영"입니다 — 확장 가능하지만 스키마가 무겁습니다.

하나의 에이전트가 환각하고 공유 상태에 환각을 쓸 때, 그것을 읽는 모든 downstream 에이전트가 환각을 사실로 채택합니다. 인간이 눈치챌 때까지 추론 체인은 5단계 깊이고根本 원인은 역대 세 번째 메시지입니다. 멀티에이전트 정확도 저하 디버깅은 크래시 디버깅보다更难합니다.

이것이 메모리 중독입니다. MAST 분류 (Cemri et al., arXiv:2503.13657)에서 두 번째로 문서화된 실패 제품군이며 구조적입니다: 출처와 변경 불가능한 검증자가 없는 모든 공유 메모리 설계는 결국 그것을 exhibit합니다.

## 개념

### 두 가지 주요 토폴로지

**전체 메시지 풀.** 모든 에이전트가 모든 메시지를 읽습니다. AutoGen GroupChat과 MetaGPT가 이를 사용합니다. 단순하고 투명하며 검사 가능하지만, ~10 에이전트를 넘으면 확장되지 않습니다 — 각 에이전트의 컨텍스트가 다른 에이전트의 작업으로 채워지기 때문입니다.

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**구독이 있는 블랙보드.** 에이전트가 주제에 대한 관심을 선언합니다; 기질이 관련 메시지만 라우팅합니다. CA-MCP (arXiv:2601.11595)와 Matrix 분산 프레임워크 (arXiv:2511.21686)가 이를 사용합니다. 더 확장되지만 구독이 의미 있으려면 사전 스키마 설계가 필요합니다.

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 각 것이 이기는 때

- **전체 풀**은 에이전트가 적고 (< 10), 이기종이고, 대화가 단기인 경우에 이깁니다. 모든 것이 모든 것을 보기 때문에 누가 무엇이라고 했는지 추론하는 것이 간단합니다.
- **블랙보드**는 에이전트가 역할에서 동형이지만 인스턴스에서 numerous하고 (스웜), 대화가 장기 실행인 경우에 이깁니다. 라우팅이 토큰 비용과 컨텍스트 오염을 절약합니다.

프로덕션 시스템은 often 혼합합니다: 상단에 작은 전체 풀 (계획 레이어), 아래에 블랙보드 (워커 레이어).

### 한 시나리오에서의 메모리 중독

세 에이전트가 연구 작업에서 작업합니다. 에이전트 A는 검색 에이전트입니다. 에이전트 B는 요약가입니다. 에이전트 C는 분석가입니다.

1. A가 페이지를 가져와서 공유 상태에 메시지를 씁니다: "연구가 42% 정확도 개선을 보고합니다."
2. 가져온 페이지가 실제로 "4.2% 개선"이라고 말했습니다. A가 소수점을 환각했습니다.
3. 공유 상태를 읽는 B가 씁니다: "42% 정확도 게인이 보고되었습니다 (출처: A)."
4. 공유 상태를 읽는 C가 씁니다: "채택 권장 — 42% 리프트가 혁신적입니다."
5. 최종 보고서가 결코 존재하지 않았던 42% 숫자를 인용합니다.

어떤 에이전트도 크래시하지 않았습니다. 어떤 테스트도 실패하지 않았습니다. 시스템이 "작동했습니다." 환각이 공유 상태를 통해 하나의 에이전트의 컨텍스트에서 모든 downstream 에이전트의 추론으로 crossed되었습니다.

### 이것이 구조적인 이유

공유 상태 없이는 에이전트 A의 환각이 A의 컨텍스트에 유지됩니다. Downstream 에이전트가重新取得 또는重新派生하고 오류를 포착할 수 있습니다. 순진한 공유 상태를 사용하면, A의 컨텍스트가 모든 사람의 컨텍스트가 되고, 환각이 사실로 세탁됩니다.

문제는 공유 상태 자체가 아니라 **출처 없이 그리고 독립적인 검증자 없이** 공유 상태입니다. 세 가지 완화가 이를 해결합니다:

1. **모든 쓰기에 출처를 기록합니다.** 공유 상태의 모든 항목은 누가, 언제, 어떤 프롬프트로, 그리고 (해당되는 경우) 에이전트가 인용한 소스가 무엇인지 기록합니다. Downstream 에이전트는 출처에 따라怀疑하며 읽습니다.
2. **쓰기를 버전화합니다; 추가 전용으로 취급합니다.** 수정은 이전 것을 대체하는 새 항목이지, 내부 업데이트가 아닙니다. 감사 추적이 보존됩니다.
3. **공유 상태에 쓸 수 없는 에이전트를至少 하나 유지합니다.** 읽기 전용 검증자 에이전트가 항목을 샘플링하고, 소스를 다시 가져오고, 불일치를 플래그합니다. 풀에 쓸 수 없으므로 풀에 의해 중독될 수 없습니다.

### 블랙보드 선례 (Hayes-Roth, 1985)

블랙보드 패턴은 LLM 에이전트보다 4년 앞서 있습니다. Hayes-Roth (1985, "제어를 위한 블랙보드 아키텍처")는 전역 블랙보드를 관찰하고, 부분 솔루션을 기여하며, 다른 소스를トリ거하는 전문가 지식 소스를 설명했습니다. 2026년 블랙보드 (CA-MCP, Matrix)는 LLM 에이전트를 지식 소스로, JSON blob을 부분 솔루션으로 사용하는 동일한 패턴입니다. 오래된 문헌에는 쓰기 경합, 기회주의적 제어, 현대 시스템이 재발견하는 일관성에 대한 솔루션이 문서화되어 있습니다.

### 투영 대 전체 보기

순수 블랙보드는 모든 구독자에게 동일한 투영(주제 범위)을 제공합니다. 더 공격적인 설계는 **에이전트당 투영**입니다: 각 에이전트가 역할에 맞춰진 보기를 가져옵니다. LangGraph의 상태 감소기가 표준 2026 구현입니다 — 감소기 함수가 전역 상태를 역할별 슬라이스로 접습니다.

에이전트당 투영이 더 확장되지만 스키마가 필요합니다. 없으면, 각 에이전트의 프롬프트에서 ad-hoc 투영을 rebuild합니다.

### 쓰기 경합 패턴

여러 에이전트가 동시에 쓰는 것은 LLM 문제가 아닌 동시성 문제입니다. 세 가지 패턴이 작동합니다:

- **순차적 라이터 (단일 생산자).** 모든 쓰기가 하나는 serialize하는 조정자 에이전트를 통해 이동합니다. 단순하지만 병목입니다.
- **버전화와 낙관적 동시성.** 각 항목에 버전이 있습니다; 라이터가 버전 불일치 시 실패하고 재시도합니다. 클래식 데이터베이스 기술.
- **주제 분할.** 다른 에이전트가 다른 주제를 소유합니다. 교차 주제 경합 없음. 설계된 분할 경계가 필요합니다.

2026년 프레임워크의 대부분은 LLM 호출이 충분히 느려 경합이 드물고 병목이刺痛하지 않기 때문에 순차적 라이터를 기본으로 합니다.

### 변경 불가능한 검증자

가장負荷가는 완화는 읽기 전용 검증자입니다. 구현 규칙:

- 검증자가 팀과 상태를 공유합니다 (블랙보드 또는 풀을 읽습니다).
- 검증자는 공유 상태에 대한 쓰기 핸들이 없습니다 — 별도의 검증 채널에만 있습니다.
- 검증자가 쓰기에서 인용된 소스를 독립적으로 다시 가져옵니다. 불일치를 플래그합니다.
- 검증자出自己的 출력은 인간 또는 별도의 결정 에이전트로 라우팅되며, 절대로 풀에 다시 공급되지 않습니다.

이 분리가 없으면, 검증자의 출력이 풀의 새 항목이 되어, 중독된 풀은 검증자를 중독시키고, 그 검증자를 중독시킵니다.

## 실습

`code/main.py`가 두 토폴로지와toy 중독 공격 및 세 가지 완화를 stdlib Python으로 구현합니다.

- `MessagePool` — 전체 읽기가 있는 스레드 안전 추가 전용 로그.
- `Blackboard` — 에이전트당 구독이 있는 주제 키 pub/sub.
- `ProvenanceEntry` — 모든 쓰기가 (작성자, 타임스탬프, prompt_hash, source_uri)를 기록합니다.
- `PoisoningScenario` — 에이전트 A가 소수점을 환각하는 3-에이전트 연구 작업을 실행합니다. 최종 보고서를 인쇄합니다.
- `Verifier` — 소스를 다시 가져오고 불일치를 플래그하는 읽기 전용 에이전트. 검증자가 있는 동일한 시나리오를 실행합니다.

실행:

```
python3 code/main.py
```

예상 출력:
- 실행 1 (검증자 없음): 환각된 42%가 최종 보고서로 전파됩니다.
- 실행 2 (검증자 있음): 검증자가 불일치를 플래그하고, 풀이 "플래그됨"으로 표시되고, 최종 보고서에 취소를 포함합니다.

## 활용

`outputs/skill-memory-auditor.md`는 모든 멀티에이전트 시스템의 공유 메모리 설계를 출처, 버전 관리, 검증자 분리에 대해 감사하는 스킬입니다. 프로덕션 전에 새 멀티에이전트 아키텍처에서 실행하세요.

## 결과물

모든 공유 메모리 설계에 대해:

- 모든 쓰기에 출처를 기록합니다: `(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`.
- 로그를 추가 전용으로 만듭니다. 수정은 이전 항목을 참조하는 새 항목입니다.
- 독립적 소스 액세스가 있는 최소 하나의 읽기 전용 검증자 에이전트를 배포합니다.
- 검증자 출력을 공유 풀에 다시가 아닌 별도 채널로 라우팅합니다.
- 대체되는 쓰기의 비율을 로그합니다. 상승하는 비율은 환각 패턴의 초기 증거입니다.

## 연습 문제

1. `code/main.py`를 실행합니다. 실행 1이 환각을 전파하고 실행 2가 그것을 잡는지 확인합니다.
2. 두 번째 환각을 추가합니다: 에이전트 B가 데이터 세트 크기를 invented합니다. 검증자가 둘 다 대해 핸드 튜닝 없이 둘 다 잡아야 합니다.
3. 전체 풀을 주제 파티션이 있는 블랙보드로 전환합니다 (`prices`, `summaries`, `analyses`). 주제 파티셔닝이 만들기更难한 중독 시나리오와 그렇지 않은 시나리오는 무엇입니까?
4. Hayes-Roth (1985, "제어를 위한 블랙보드 아키텍처")를 읽습니다. 이 레슨에서 논의되지 않은 두 가지 제어 패턴을 식별합니다 — 2026년 시스템이受益할 것들.
5. CA-MCP (arXiv:2601.11595)를 읽습니다. 해당 Shared Context Store를 `code/main.py`의 MessagePool 또는 Blackboard 클래스에 매핑합니다. CA-MCP가 위에 추가하는 기본 요소는 무엇입니까?

| 용어 |人们在说什么 | 实际含义 |
|------|----------------|------------------------|
| 메시지 풀 | "공유 채팅 히스토리" | 모든 에이전트가 읽는 추가 전용 로그. 완전한 투명성, 나쁜 확장성. |
| 블랙보드 | "공유 작업 공간" | 주제 키 pub/sub. 에이전트가 관련 주제를 구독합니다. 더 멀리 확장. |
| 출처 | "누가 무엇을 썼는지" | 각 쓰기의 메타데이터: 작성자, 타임스탬프, 프롬프트, 소스. |
| 메모리 중독 | "환각이 퍼짐" | 하나의 에이전트의 오류가 공유 상태에 들어가며, downstream 에이전트가 그것을 사실로 채택합니다. |
| 추가 전용 | "내부 업데이트 없음" | 수정은 이전 것을 대체하는 새 항목입니다. 감사 추적을 보존합니다. |
| 변경 불가능한 검증자 | "독립 감사인" | 소스를 다시 가져오고 불일치를 플래그하는 읽기 전용 에이전트. |

| 지식 소스 | "전문가 에이전트" | Hayes-Roth의 1985년 용어 — 블랙보드 참가자. |
