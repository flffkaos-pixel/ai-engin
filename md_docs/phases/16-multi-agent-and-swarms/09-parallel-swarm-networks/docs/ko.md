# 병렬 / 스웜 / 네트워킹 아키텍처

> 수퍼바이저와 대조: 중앙 결정자 없음. 에이전트가 공유 이벤트 버스를 읽고, 작업을 비동기적으로 선택하고, 결과를 다시 작성합니다. LangGraph는 분산, 동적 환경을 위해 "Swarm Architecture"를 명시적으로 지원합니다. Matrix (arXiv:2511.21686)는 오케스트레이터 병목을 제거하기 위해 제어와 데이터 흐름을 분산 큐를 통해 직렬화된 메시지로 표현합니다. 트레이드오프가 명확합니다: 결정론성과 추적 가능성을 위한 확장성. 스웜은 많은 독립적인 하위 문제가 있는 작업에 적합합니다; 단일 일관된 계획이 필요한 작업에는 적합하지 않습니다.

**유형:** 학습 + 실습
**언어:** Python (stdlib, `threading`, `queue`)
**선수 과목:** Phase 16 · 05 (Supervisor Pattern), Phase 16 · 04 (Primitive Model)
**소요 시간:** ~75분

## 문제

수퍼바이저는 소수의 워커로 확장됩니다. 수백 개는 어떻습니까? 수퍼바이저 자체가 병목됩니다: 누가 무엇을 하는지에 대한 모든 결정이 하나의 에이전트를 통해 funnel됩니다. 하나의 느린 계획 단계가 전체 시스템을 stalls합니다.

스웜 아키텍처가 설계를 뒤집습니다. 중앙 플래너가 작업을 dispatch하는 대신, 워커가 공유 큐에서 작업을 선택합니다. "조정"은 이벤트 버스 의미론에	baked됩니다. 오케스트레이터 없음; 시스템이 큐가 할 때까지 확장됩니다.

## 개념

### 형태

```
               ┌──── 공유 큐 ────┐
               │                      │
      ┌────────┼────────┐  ◄──────┬───┘
      ▼        ▼        ▼         │
    Worker  Worker  Worker   Worker
     A       B       C        D
      │        │        │         │
      └────────┴────────┴─────────┘
                │
                ▼
           results pool
```

오케스트레이터 없음. 각 워커가 반복합니다: 작업을 pull하고, 처리하고, 결과를 작성합니다 (및 선택적으로 후속 작업을 enqueue).

### 스웜이 적합할 때

- **많은 독립 작업.** 스크래핑, 변환, 분류. 작업이 서로 의존하지 않습니다.
- **가변 기간 작업.** 일부 작업은 100ms, 일부는 10s가 소요됩니다. 스웜이 자동으로 부하를 균형합니다 — 빠른 워커가 다음 작업을 선택합니다. 수퍼바이저는 기간을 anticipation해야 합니다.
- **처리량 대 결정론.** 총 완료 시간을 신경 쓰고, 엄격한 순서를 신경 쓰지 않습니다.

### 스웜이 실패할 때

- **순서 있는 워크플로우.** 3단계가 2단계의 출력이 필요한 경우, 스웜이 3단계가 2단계가 완료되기 전에 firing될 위험이 있습니다.
- **전역 계획 작업.** 복잡한 연구 질문은 플래너의 이점을 가집니다. 연구자들의 스웜이 독립적인 사실을 산출하고, 일관된 보고서가 아닙니다.
- **디버깅.** 중앙 로그와 비동기 작업이 없어서 버그를再現하는 것이 비용이 많이 듭니다.

### Matrix (arXiv:2511.21686)

Matrix는 스웜을 자연스러운 결론으로 가져가는 2025년 논문입니다: 제어 흐름과 데이터 흐름이 분산 큐의 직렬화된 메시지입니다. 중앙 조정자 없음. 내결함성이 메시지 내구성에서 옵니다. 확장성은 메시지 브로커의 문제이지 시스템의 문제가 아닙니다.

 기여: 에이전트 좌주가 "이 에이전트가 어떤 메시지 주제를 구독합니까?"而不是"수퍼바이저가 다음에 어떤 에이전트를 선택합니까?"라는 프로그래밍 모델. 이것은 시스템을 pub/sub 이벤트 메시처럼 보이게 합니다.

### LangGraph의 Swarm Architecture

LangGraph 2025 문서는 명시적으로 "Swarm Architecture"를 멀티에이전트 패턴 중 하나로 설명합니다: 에이전트가 노드이지만, 에지가 cycles이 있고 모든 노드가 풀에서 활성화될 수 있는 directed graph를 형성합니다. 워커가 수퍼바이저 할당이 아닌 조건으로 사용 가능한 작업에서 선택합니다.

### 실패 모드: 기아와 핫스팟팅

모든 워커가 가장 빠른 가용 작업을 pull하면, 장기 실행 작업이它们이 유일하게 남을 때까지 선택되지 않습니다. 클래식 큐 기아.

 완화:
- 명시적 aging이 있는 우선순위 큐 (대기 시간으로 우선순위 증가).
- 워커 전문화: 일부 워커는 "긴" 작업만 take합니다.
- 역압: 빠른 작업이 큐에 들어가는 속도를 제한합니다.

### content-based routing 링크

스웜은 content-based routing (Lesson 22)과 자연스럽게 쌍을 이룹니다. 일반 큐 대신 메시지 유형당 하나의 큐가 있습니다. 전문 워커가 자신의 유형만 구독합니다. 이것은数千 에이전트로 확장되는 메시지 버스 아키텍처의 기반입니다.

## 실습

`code/main.py`는 공유 `queue.Queue`에서 작업을 pull하는 4개의 워커 스레드 스웜을 구현합니다. 작업은 가변 기간을 가집니다 (일부 빠르고, 일부는 느림). 데모가 대조됩니다:

- **순차적 기준:** 하나의 워커가 모든 작업을 순차적으로 처리합니다.
- **고정 할당:** 각 작업이 특정 워커에 사전 할당됩니다 (수퍼바이저 스타일).
- **스웜:** 워커가 공유 큐에서 pull합니다.

스웜이 자동으로 부하를 분산합니다; 고정 할당은 할당된 작업이 느릴 때 빠른 워커가 유휴 상태로 남습니다.

실행:

```
python3 code/main.py
```

출력은 작업당 워커 수 (스웜이 불균등하지만 최적적으로 분산)와 벽시계 시간을 보여줍니다.

## 활용

`outputs/skill-swarm-fit.md`는 작업이 스웜 대 수퍼바이저를 사용해야 하는지 평가합니다. 입력: 작업 독립성, 기간 분산, 순서 요구사항, 디버그 가능성 요구사항.

## 결과물

체크리스트:

- **aging이 있는 우선순위 큐.** 장기 작업 기아를 방지합니다.
- **워커 멱등성.** 워커가 실행 중 crash하면 작업이 두 번 이상 pull될 수 있습니다. 워커가 멱등이어야 합니다.
- **지속적 큐.** 프로덕션을 위해 Kafka, Redis Streams, 또는 데이터베이스 지원 큐를 사용합니다. `queue.Queue`는 인메모리 전용입니다.
- **작업당 관찰 가능성.** 모든 작업에 추적 ID가 있습니다; 모든 워커가 시작/종료와 함께 로그합니다.
- **역압.** 큐가 워커가 그것을 draining하는 것보다 빠르게 증가하면, 생산자를 slow down합니다.

## 연습 문제

1. `code/main.py`를 실행합니다. 가변 기간 워크로드에서 스웜이 순차적보다 얼마나 빠른가요? 고정 할당보다 얼마나 빠른가요?
2. 우선순위 큐 변형을 추가합니다 (`queue.PriorityQueue` 사용). 작업 "중요도" 필드로 우선순위를 할당합니다. 지속적인 부하에서低 우선순위 작업이 기아 상태가 되는지를 관찰합니다.
3. 핫스팟 감지기를 구현합니다: 모든 워커가 가장 느린 워커보다 3× 더 많은 작업을 처리할 때 로그합니다. 작업 기간 분포에 대해 무엇을 나타냅니까?
4. Matrix 논문 (arXiv:2511.21686) 초록과 섹션 3을 읽습니다. Matrix가 수용하는 하나의 특정 트레이드오프 (확장성 게인)와 하나를 포기하는 것 (추적 가능성, 결정론)을 식별합니다.
5. 작업을 (task_type, payload) 튜플의 `queue.Queue`로 변환하고, 워커가 특정 유형만 구독하도록 합니다. 작업이 이기종일 때 어떤 라우팅 규칙이 의미가 있습니까?

## 핵심 용어

| 용어 |人们在说什么 | 实际含义 |
|------|----------------|------------------------|
| 스웜 아키텍처 | "분산 에이전트" | 워커가 공유 큐에서 pull; 중앙 오케스트레이터 없음. |
| 이벤트 버스 | "에이전트가 주제를 구독합니다" | 유형 또는 콘텐츠별로 작업을 워커에게 라우팅하는 메시지 브로커. |
| 기아 | "작업이 절대 실행되지 않음" |低 우선순위 작업이 더 높은 우선순위 작업이 계속 도착하기 때문에 선택되지 않습니다. |
| 핫스팟팅 | "하나의 워커가 압도당합니다" | 하나의 워커가 대부분의 작업을 받는 부하 불균형. |
| 역압 | "생산자를 slow down합니다" | 큐가 채워질 때上游에 生产을 중지하도록 신호를 보내는 메커니즘. |
| 멱등 워커 | "재실행해도 안전합니다" | 두 번 처리해도 동일한 결과를 산출합니다. 워커가 실행 중 crash할 수 있으므로 필요합니다. |
| 지속적 큐 | "크래시에서 생존합니다" | 디스크 또는 복제된 저장소에 지원하는 큐; 작업이 워커가 crash할 때 손실되지 않습니다. |
| Matrix 프레임워크 | "전체 메시지 전달 스웜" | 데이터와 제어 흐름이 분산 큐의 직렬화된 메시지입니다. |
