# 멀티에이전트 기본 모델

> 2026년에 출하되는 모든 멀티에이전트 프레임워크 — AutoGen, LangGraph, CrewAI, OpenAI Agents SDK, Microsoft Agent Framework —는 4차원 설계 공간의 한 점입니다. 네 가지 기본 요소, 그 이상은 아닙니다: 에이전트, 핸드오프, 공유 상태, 오케스트레이터. 이 레슨은 처음부터它们을 구축하고, 4개 모두에서 toy 시스템을 실행한 다음, 모든 주요 프레임워크를 동일한 축에 매핑하여 새로운 릴리스를 단락으로 읽을 수 있게 합니다.

**유형:** 학습
**언어:** Python (stdlib)
**선수 과목:** Phase 14 (Agent Engineering), Phase 16 · 01 (Why Multi-Agent)
**소요 시간:** ~60분

## 문제

6개월마다 새로운 멀티에이전트 프레임워크가 출하됩니다. 2023년 AutoGen. 2024년 CrewAI. 2024년 LangGraph와 OpenAI Swarm. 2025년 4월 Google ADK. 2026년 2월 Microsoft Agent Framework RC. 각 보도자료는 "올바른 추상화"라고 주장합니다.

하나씩 배우려고 하면 번아웃됩니다. API가 다르게 보입니다. 문서가 "에이전트"가 무엇인지에 동의하지 않습니다. 하나의 프레임워크는 공유 메모리를 "블랙보드"라고 부르고, 다른 하나는 "메시지 풀", 세 번째는 "StateGraph"라고 부릅니다. 이 분야가 그냥 떠돌고 있다는 의심이 듭니다.

그렇지 않습니다. 마케팅 아래에서 네 가지 기본 요소는 안정적입니다. 한 번 배으면 모든 새로운 프레임워크를 단락으로 읽습니다.

## 개념

### 네 가지 기본 요소

1. **에이전트** — 시스템 프롬프트 plus 툴 목록. 무상태; 모든 실행은 시스템 프롬프트와 현재 메시지 히스토리에서 시작합니다.
2. **핸드오프** — 하나의 에이전트에서 다른 에이전트로의 제어권 이전. 기계적으로는 새 에이전트를 반환하는 툴 호출이거나 조건을 따르는 그래프 에지.
3. **공유 상태** — 둘 이상의 에이전트가 읽을 수 있는 (때때로 쓸 수 있는) 모든 데이터 구조. 메시지 풀, 블랙보드, 키-값 저장소, 벡터 메모리.
4. **오케스트레이터** — 누가次に 말할지 결정하는 사람. 옵션: 명시적 그래프 (결정론적), LLM发言人 선택기 (소프트), 마지막发言자의 핸드오프 호출 (OpenAI Swarm), 또는 큐 위의 스케줄러 (스웜 아키텍처).

그것이 전체 설계 공간입니다. 모든 프레임워크가 각 축에 대한 기본값을 선택합니다; 나머지는 표면 구문입니다.

### 모든 2026 프레임워크가 이에 매핑되는 방식

| 프레임워크 | 에이전트 | 핸드오프 | 공유 상태 | 오케스트레이터 |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | 툴이 에이전트를 반환 | 호출자의 문제 | LLM의 다음 핸드오프 호출 |
| AutoGen v0.4 / AG2 | `ConversableAgent` | GroupChat의发言人 선택기 | 메시지 풀 | 선택기 함수 (LLM 또는 라운드 로빈) |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | 연결된 작업 출력 | 관리자 LLM 또는 고정 순서 |
| LangGraph | 노드 함수 | 그래프 에지 + 조건 | `StateGraph` 감소기 | 그래프, 결정론적 |
| Microsoft Agent Framework | 에이전트 + 오케스트레이션 패턴 | 패턴별 | 스레드 / 컨텍스트 | 패턴별 |
| Google ADK | 에이전트 + A2A 카드 | A2A 작업 | A2A 아티팩트 | 호스트가 결정 |

표면적 차이는 커 보입니다. 아래에서: 동일한 네 가지 노브.

### 이것이 중요한 이유

기본 요소를 보면, 프레임워크 비교가 짧은 체크리스트가 됩니다:

- 오케스트레이터가 LLM을 라우팅에 신뢰합니까 (Swarm) 아니면 라우팅을 코드에 고정합니까 (LangGraph)?
- 공유 상태가 전체 히스토리입니까 (GroupChat) 아니면 투영됨 (StateGraph 감소기)?
- 에이전트가 서로의 프롬프트를 수정할 수 있습니다 (CrewAI 관리자) 아니면 핸드오프만 가능합니까 (Swarm)?

이 세 가지 질문이 주어진 문제에 맞는 프레임워크의 80%에 답변합니다. "최고의 멀티에이전트 프레임워크"를 쇼핑하는 것을 멈추고 실제로 신경 쓰는 축을 위해 설계하기 시작합니다.

### 무상태 통찰력

공유 상태를 제외한 모든 기본 요소는 무상태입니다. 에이전트는 (프롬프트, 툴)의 함수입니다. 핸드오프는 함수 호출입니다. 오케스트레이터는 스케줄러입니다. **시스템에서 유일하게 상태 저장인 것은 공유 상태입니다.** 그것이 모든 흥미로운 버그가 사는 곳입니다: 메모리 중독 (Lesson 15), 메시지 순서 지정, 버전 관리, 쓰기 경합.

공유 상태를 숨기는 프레임워크 (Swarm)는 문제를 호출자에게 밀어붙입니다. 중앙화하는 프레임워크 (LangGraph 체크포인터, AutoGen 풀)는 검사 가능하게 하지만 조정 비용을 공유 상태 구현으로 옮깁니다.

### 단일 기본 요소 해부

#### 에이전트

```
Agent = (system_prompt, tools, model, optional_name)
```

메모리 없음. 무상태. 동일한 시스템 프롬프트와 툴을 가진 두 에이전트는 교환 가능합니다. 에이전트별 상태로 보이는 모든 것은 실제로 공유 상태 또는 핸드오프 프로토콜에 있습니다.

#### 핸드오프

```
Handoff = (from_agent, to_agent, reason, payload)
```

세 가지 구현이 지배적입니다:

- **함수 반환** — 툴이 다음 에이전트를 반환합니다. 이것이 OpenAI Swarm 패턴입니다. 에이전트는 툴 스키마에 라우팅을 담습니다.
- **그래프 에지** — LangGraph. 에지는 선언적입니다. LLM이 값을 산출합니다; 조건이 다음 노드를 선택합니다.
- **发言자 선택** — AutoGen GroupChat. 선택기 함수 (종종 스스로 LLM 호출)가 풀을 읽고 다음发言자를 선택합니다.

#### 공유 상태

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

최소한 메시지 목록입니다. 자주 더 많습니다: 구조화된 아티팩트 (CrewAI 작업 출력), 형식화된 컨텍스트 (LangGraph 감소기), 외부 메모리 (MCP, 벡터 DB).

두 토폴로지: **전체 풀** (모든 에이전트가 모든 메시지를 봄)과 **투영됨** (에이전트가 역할 범위 보기을 봄). 전체 풀은 단순하고 확장성이 나쁩니다. 투영 풀은 확장되지만 사전 스키마 설계가 필요합니다.

#### 오케스트레이터

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

네 가지 맛:

- **정적** — 그래프가 빌드 시간에 고정됩니다 (LangGraph 결정론적, CrewAI 순차적).
- **LLM 선택** — LLM이 풀을 읽고 다음发言자를 선택합니다 (AutoGen, CrewAI 계층적).
- **핸드오프驱动** — 현재 에이전트가 핸드오프 툴을 호출하여 결정합니다 (Swarm).
- **큐驱动** — 워커가 공유 큐에서 작업을 폴링합니다; 명시적 다음发言자 없음 (스웜 아키텍처, Matrix).

### 프레임워크 간 변경 사항

기본 요소가 고정되면, 나머지 설계 결정은:

- **메모리 전략** — 일시적 vs 지속적 체크포인팅 (LangGraph checkpointer).
- **安全 경계** — 핸드오프를 승인할 수 있는 사람 (인간参与的-loop).
- **비용 회계** — 에이전트별 토큰 예산.
- **관찰 가능성** — 핸드오프 추적, 재생을 위한 상태 유지.

모두 기본 요소 위에 구현 가능합니다. 그 중 어느 것도 새로운 기본 요소가 아닙니다.

## 실습

`code/main.py`는 ~150줄의 stdlib Python으로 네 가지 기본 요소를 구현합니다. 실제 LLM 없음 — 각 에이전트는 조정 구조에 초점을 유지하기 위해 스크립트된 정책입니다.

파일이 내보내기:

- `Agent` — 이름, 시스템 프롬프트, 툴, 정책 함수의 데이터클래스.
- `Handoff` — 새 에이전트를 반환하는 함수.
- `SharedState` — 스레드 안전한 메시지 풀.
- `Orchestrator` — 세 가지 변형: `StaticOrchestrator`, `HandoffOrchestrator`, `LLMSelectorOrchestrator` (시뮬레이션됨).

데모는 세 가지 오케스트레이터 유형 모두를 통해 동일한 3-에이전트 파이프라인 (리서치 → 쓰기 → 리뷰)을 실행하고 끝에 메시지 풀을 인쇄합니다. 출력이 *누가 다음을 선택하는가*에서만 다름을 볼 수 있습니다; 에이전트와 공유 상태는 실행 간에 동일합니다.

실행:

```
python3 code/main.py
```

예상 출력: 세 가지 오케스트레이터 실행, 패턴당 하나. 각자 최종 메시지 풀을 인쇄합니다. 핸드오프驱动 실행은 研究자이 일찍 완료되었다고 판단하면 더 적은 에이전트에 도달합니다 — 이것은 LLM-라우팅 트레이드오프의 미니어처입니다.

## 활용

`outputs/skill-primitive-mapper.md`는 모든 멀티에이전트 코드베이스 또는 프레임워크 문서를 읽고 네 가지 기본 요소 매핑을 반환하는 스킬입니다. 문서를 깊이 있게 읽기 전에 새로운 프레임워크 릴리스에서 단락 이해를 얻으려면 실행하세요.

## 연습 문제

1. `code/main.py`를 세 번 실행하여 다른 에이전트 정책을観察하세요. 오케스트레이터 선택이 실행되는 에이전트를 어떻게 변경하는지 관찰하세요.
2. 네 번째 오케스트레이터 유형을 구현하세요: 에이전트가 공유 상태에서 작업을 폴링하는 큐驱动型的 것. 어떤 교착 상태가 발생할 수 있으며 어떻게 감지합니까?
3. LangGraph quickstart (https://docs.langchain.com/oss/python/langgraph/workflows-agents)를 가져와 네 가지 기본 요소로 다시 작성하세요. LangGraph의 어떤 추상화가 1:1로 매핑되고 어떤 것이 편의 래퍼입니까?
4. OpenAI Swarm cookbook (https://developers.openai.com/cookbook/examples/orchestrating_agents)을 읽으세요. 네 가지 기본 요소 중 Swarm이 가장 인체공학적으로 만드는 것과 호출자에게 밀어붙이는 것을 식별하세요.
5. 이 테이블에서 공유 상태를 전혀 숨기는 하나의 프레임워크를 찾으세요. 핸드오프 간에 히스토리를 다시 읽지 않고 에이전트가 조정해야 할 때 무엇이 망가지는지 설명하세요.
