# 프로덕션 스케일링 — 큐, 체크포인트, 내구성

> 수천 개의 동시 실행으로 멀티 에이전트 시스템을 확장하려면 **지속적 실행**이 필요합니다. LangGraph의 런타임은 각 super-step 후에 `thread_id`를 키로하여 체크포인트를 기록합니다 (기본적으로 Postgres); 작업자 크래시 시 임대期限가到期하고 다른 작업자가 재개합니다. 에이전트는 인간 입력을 기다리며 무기한 잠들 수 있습니다. **MegaAgent** (arXiv:2408.09955)는 세 가지 상태 (Idle / Processing / Response)와 이-layer 조정 (그룹 내 채팅 + 그룹 간 admin 채팅)이 있는 에이전트당 생산자-소비자 큐를 실행했습니다. **Fiber/async**는 LLM 스트리밍에 thread-per-job을 능가합니다: 스레드는 토큰을 기다리는 동안 99% 유휴 상태이며, fiber는 I/O에서 협력적으로 양보합니다. 반론: Ashpreet Bedi의 "Scaling Agentic Software"는 **FastAPI + Postgres + 그게 다임**을 부하가 입증될 때까지 주장합니다 — 간단한 아키텍처가预期的보다 더 멀리 갑니다. 이 레슨은 내구성 체크포인트 로그, 상태 전이가 있는 에이전트당 작업 큐, async 대 thread 데모를 빌드하고 실용적인 "단순하게 시작" 규칙을 적용합니다.

**유형:** 학습 + 실습
**언어:** Python (stdlib, `asyncio`, `sqlite3`)
**선수 과목:** Phase 16 · 09 (Parallel Swarm Networks), Phase 16 · 13 (Shared Memory)
**소요 시간:** ~75분

## 문제

프로토타입 멀티 에이전트 시스템이 메모리 내 이벤트 루프에서 세 에이전트와 하나의 노트북에서 작동합니다. 프로덕션으로 이동:

- 에이전트는 때때로 몇 시간 동안 실행됩니다 (긴 연구, 인간参与的 대기).
- 작업자 프로세스가 크래시됩니다. 재시작하면 상태가 손실됩니다.
- 피크 부하가 평균의 10배입니다; 수평 확장이 필요합니다.
- 사용자가 에이전트 실행당 지불합니다; 청구를 위해 exactly-once 의미 체계가 필요합니다.

메모리 내 이벤트 루프는 이러한 것 중 아무것도 하지 않습니다. 지속적 실행 레이어가 필요합니다. 2026년 정식 옵션:

1. 체크포인트가 있는 워크플로 엔진 (Temporal, LangGraph 런타임).
2. 상태 저장소가 있는 메시지 큐 (Postgres + SQS/RabbitMQ).
3. 액터 모델 프레임워크 (MegaAgent의 에이전트당 생산자-소비자).
4. 핸드 롤 FastAPI + Postgres (Bedi의 주장).

이 레슨은 각각의 미니버전을 빌드합니다.

## 개념

### 지속적 실행, 패턴

지속적 실행 엔진은 각 "step" (LangGraph의 언어에서 super-step) 후에 전체 프로그램 상태를 유지합니다. 크래시 시:

```
작업자가 step 중간에 크래시
  -> 임대 期限制到期
  -> 다른 작업자가 thread_id를拾い上げ
  -> 마지막 체크포인트에서 재개
  -> 중복 부작용 없음
```

작동하기 위한 요구 사항:

- **직렬화 가능한 상태.** 모든 에이전트 상태가 유지 가능해야 합니다. 활성화된 데이터베이스 연결이 있는 함수 클로저는 survival하지 않습니다.
- **결정적 재개.** 동일한 상태와 동일한 입력 given, 에이전트가 동일한 작업을 산출합니다 (또는 LLM 호출에 대해 외부 결정적 오라클에 연기합니다).
- **멱등 부작용.** 외부 호출 (도구 호출, 지불)은 멱등하거나 중복 제거 키를 사용해야 합니다.

LangGraph는 각 super-step 후에 체크포인트를 기록합니다; Temporal은 각 활동 후에 기록합니다; Restate는 event-sourced 저널을 사용합니다. 세 가지 모두 동일한 패턴을 구현합니다.

### LangGraph의 런타임

각 에이전트가 `thread_id`를 가집니다; 상태는 타입 dict입니다; 각 super-step이 체크포인트 테이블에 행을 기록합니다. 재개 시 런타임이 마지막 체크포인트에서 처음부터가 아닌 리플레이합니다. 에이전트가 인간 입력을 기다리며 `interrupt()`할 수 있습니다; 런타임이 상태를 유지하고 작업자를 해제합니다. 입력이 도착하면 모든 작업자가 재개할 수 있습니다.

2026년 4월 현재 이것이 참조 프로덕션 디자인입니다.

### MegaAgent의 에이전트당 큐

arXiv:2408.09955는 수천 개의 동시 에이전트가 있는 클러스터의規模 실험을 설명합니다. 아키텍처:

```
에이전트 i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- 에이전트 i에 주소된 메시지
  out_queue  -> 답변 + 부작용

조정자:
  그룹 내 채팅  (같은 그룹의 에이전트)
  그룹 간 admin 채팅  (고수준 라우팅)
```

이-layer 조정을 통해 그룹 내 대화가 밀하게 발생하는 동안 그룹 간는 희소하게 유지됩니다 — 수천 개의 에이전트에서 비용을 선형으로 유지하는 패턴입니다.

### Async 대 thread-per-job

LLM 호출은 I/O 바운드입니다. 다음 토큰을 기다리는 스레드는 99% 유휴 상태입니다. 스레드당 ~1MB RAM이 듭니다; 10,000개의 동시 호출에서 스택에만 10GB가 듭니다.

Fiber (Python `asyncio`, Go goroutines, Rust `tokio`)는 I/O에서 협력적으로 양보합니다. 동일한 10,000개의 호출이 편안하게 process에 맞습니다. LLM 에이전트 규모에서 async는 최적화가 아니라 아키텍처입니다.

예외: CPU 바운드 사후 처리 (임베딩, 토크나이저 트릭)仍然是 스레드나 프로세스를 원합니다. I/O 레이어를 CPU 레이어와 분리하세요.

### Bedi의 반론

"Scaling Agentic Software" (Ashpreet Bedi, 2026)는 대부분의 팀이 부하를 측정하기 전에 과엔지니어링한다고 주장합니다. 실용적 기본값:

- FastAPI + Postgres.
- 각 에이전트 실행은 행입니다; 낙관적 동시성으로 상태를 제자리에서 업데이트합니다.
- `pg_notify` 또는 간단한 Celery 작업자를 통한 백그라운드 작업.
- 애플리케이션 코드의 재시도 정책.

~100개의 동시 에이전트 실행 미만의 부하에서, 이것이 종종 필요한 전부입니다. 측정하여 실패할 때 업그레이드하세요.

규칙: 간단한 아키텍처가 해결할 수 없는 구체적인 문제에 부딪힐 때 지속적 실행 프레임워크를 채택하세요. 조기 채택은 지불되지 않는仪式에 시간을 consumption합니다.

### Exactly-once 의미 체계

유료 에이전트 실행의 경우 "exactly-once effective" (at-least-once 배달 + 멱등 소비자)가 필요합니다. 엔지니어링 이동:

- **실행당 중복 제거 키.** 모든 부작용 호출에 포함합니다.
- **아웃박스 패턴.** 부작용을 먼저 테이블에 작성한 다음 별도 프로세스가 실행합니다. 두 단계 모두 멱등합니다.
- **보상 트랜잭션.** 부작용이成功했지만 해당 추적 쓰기가 실패하면 보상을 예약합니다.

이것들은 데이터베이스 엔지니어링 패턴이지 LLM 특정이지 않습니다. LLM 세금은 LLM 호출이 느리다는 것입니다; 다른 모든 것은 표준 분산 시스템입니다.

### 레인보우 배포

Anthropic의 멀티 에이전트 연구 시스템은 "레인보우 배포"를 사용합니다: 런타임의 여러 버전이 장기 실행 에이전트가 모든 코드 배포에서 죽을 필요가 없도록 동시에 실행됩니다. 새로운 버전을 트래픽 조각에서 canary합니다; 에이전트가 완료되면 이전 버전을 폐쇄합니다.

이것은 장기 실행 상태적 시스템의 표준입니다; 2026년 적응은 에이전트가 몇 시간 동안 생존할 수 있으므로 배포 周기가 그것을Accommodate해야 합니다.

### 정식 프로덕션 체크리스트

- 내구성 상태 (체크포인트, 스냅샷, 또는 아웃박스 + replayable 로그).
- 멱등 부작용.
- LLM 호출용 async I/O 레이어.
- 중복 제거가 있는 at-least-once 배달.
- 상태적 워크로드용 레인보우/canary 배포.
- 관찰 가능성: 에이전트별 추적, super-step 감사, 재시도 카운터.

## 빌드

`code/main.py`가 구현합니다:

- `CheckpointStore` — thread-id 키가 있는 SQLite 백엔드 체크포인트 로그. 각 super-step이 행을 추가합니다.
- `run_with_checkpoint(agent, thread_id)` — 중간 실행 크래시를 시뮬레이션합니다; 두 번째 작업자가 마지막 체크포인트에서 재개합니다.
- `AgentQueue` — 작은 작업 큐가 있는 에이전트당 Idle / Processing / Response 상태 머신.
- `demo_async_vs_threads()` — asyncio와 스레드를 통해 500개의 동시 "LLM 호출"을 실행합니다; wall-clock과 피크 메모리를 보고합니다 (근사치).

실행:

```
python3 code/main.py
```

예상 출력: 시뮬레이션된 크래시 후 체크포인트 재개가成功합니다; async 버전이 500개의 동시 호출을 < 1초 내에 처리합니다; 스레드 버전은 여러 초가 걸리고 동시 유닛당 훨씬 더 많은 메모리를 사용합니다.

- **구체적인 문제에 부딪힐 때 지속적 실행 엔진 (Temporal / LangGraph / Restate)을 채택하세요:** 몇 시간에 달하는 인간参与的 대기, 교차 영역 조정, 복잡한 재시도/보상 정책.
- **I/O 레이어에는 Async.** CPU 바운드 사후 처리에만 스레드.

## 연습문제

1. `code/main.py`를 실행하세요. 체크포인트 재개가 작동하고, async 대 thread 동시성 차이가 측정됩니다.
2. **아웃박스** 테이블을 구현하세요: 모든 도구 호출이 먼저 아웃박스에 작성한 다음 별도 고루틴/작업이 실행합니다. 도구 호출을 두 번 실행하여 멱등성을 확인하세요.
3. **레인보우 배포**를 시뮬레이션하세요: 두 개의 동시 런타임 버전; 새 thread_id의 절반을 각각으로 라우팅합니다; 이전 버전의 진행 중 스레드가 중단되지 않음을 확인합니다.
4. LangGraph의 런타임 문서를 읽으세요 (아래 링크). 핸드 롤 FastAPI + Postgres 버전에서 복제하는 데 가장 오래 걸릴 런타임 기능은 무엇입니까? 채택 이유입니까, 연기할 수 있습니까?
5. MegaAgent (arXiv:2408.09955) Section 3을 읽으세요. 이-layer 조정 (그룹 내 + 그룹 간 admin 채팅)이 두 개의 큐 패밀리가 있는 메시지 큐에 어떻게 매핑될지 스케치하세요.

## 핵심 용어

| 용어 | 人们怎么说 | 실제 의미 |
|------|----------------|------------------------|
| Durable execution | "프로그램 상태 유지" | 엔진이 각 super-step 후 상태를 기록합니다; 크래시 복구가 결정적입니다. |
| Super-step | "트랜잭션 경계" | 체크포인트 사이의 작업 단위. LangGraph 용어. |
| thread_id | "에이전트 실행 식별자" | 체크포인트 및 재개 로직을 바인딩하는 키. |
| 멱등성 | "안전한 재시도" | 부작용을 반복하면 한 번의 시도만큼 동일한 결과가 발생합니다. |
| Outbox 패턴 | "부작용 분리" | 의도를 테이블에 작성합니다; 별도 실행자가 수행하고 완료로 표시합니다. |
| At-least-once 배달 | "가능한 중복" | 메시지 큐 의미 체계; 중복 제거 키가 소비자를 effective-once로 만듭니다. |
| Rainbow deploy | "중복 버전" | 장기 실행 워크로드 동안 여러 런타임 버전이 동시 실행됩니다. |
| Async fiber | "협력적 양보" | 사용자 모드 동시성; I/O 바운드 부하에서 스레드보다 저렴합니다. |
| Checkpoint | "상태 스냅샷" | super-step 경계의 직렬화된 상태; 재개를 위한 키. |
