# 멀티에이전트가 필요한 이유

> 하나의 에이전트가 벽에 부딪힙니다. 더 큰 에이전트를 만드는 것이 아니라, 더 많은 에이전트를 만드는 것이 현명한 방법입니다.

**유형:** 학습
**언어:** TypeScript
**선수 과목:** Phase 14 (Agent Engineering)
**소요 시간:** ~60분

## 학습 목표

- 단일 에이전트의 한계(컨텍스트 오버플로, 혼합된 전문성, 순차적 병목)를 식별하고, 여러 에이전트로 분할해야 하는 시점을 설명
- 오케스트레이션 패턴(파이프라인, 병렬 fan-out, 수퍼바이저, 계층적)을 비교하고 주어진 작업 구조에 맞는 올바른 패턴을 선택
-明確な役割 경계, 공유 상태, 통신 계약이 있는 멀티에이전트 시스템 설계
- 멀티에이전트 복잡성(지연시간, 비용, 디버깅 어려움)의 트레이드오프와 단일 에이전트 단순성을 분석

## 문제

 Phase 14에서 단일 에이전트를 구축했습니다. 작동합니다. 파일을 읽고, 명령을 실행하고, API를 호출하고, 결과를 추론할 수 있습니다. 그런 다음 실제 코드베이스에 투입합니다: 200개 파일, 3개 언어, 인프라에 의존하는 테스트, 코드 작성 전에 외부 API를 연구해야 하는 요구사항.

에이전트는 고통받습니다. LLM이 멍청해서가 아니라, 작업이 하나의 에이전트 루프로 처리할 수 있는 범위를 초과하기 때문입니다. 컨텍스트 윈도우가 파일 내용으로 채워집니다. 에이전트는 40개의 툴 호출 전에 읽은 내용을 잊어버립니다. 연구자, 코더, 리뷰어 역할을 모두 동시에 수행하려고 시도하며 세 가지 모두에서 형편없이 수행합니다.

これが单一年历の天井です。次の場合に壁にぶつかります：

- **하나의 윈도우에 맞는 것보다 더 많은 컨텍스트가 필요한 경우** - 50개 파일 읽기는 200k 토큰을 훌쩍 넘습니다
- **다른 단계에서 다른 전문성이 필요한 경우** - 리서치는 코드 생성과 다른 프롬프팅이 필요합니다
- **병렬로 발생할 수 있는 작업인 경우** - 세 파일을 순차적으로 읽는 대신 동시에 읽을 수 있는 경우 왜 순차적으로 읽어야 합니까?

## 개념

### 단일 에이전트의 천장

단일 에이전트는 하나의 루프, 하나의 컨텍스트 윈도우, 하나의 시스템 프롬프트입니다. 상상해 보세요:

```
┌─────────────────────────────────────────┐
│            단일 에이전트                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         컨텍스트 윈도우            │  │
│  │                                   │  │
│  │  리서치 노트                      │  │
│  │  + 코드 파일                      │  │
│  │  + 테스트 출력                    │  │
│  │  + 리뷰 피드백                    │  │
│  │  + API 문서                       │  │
│  │  + ...                            │  │
│  │                                   │  │
│  │  ████████████████ 가득 참 ███  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  하나의 시스템 프롬프트가                │
│  리서치 + 코딩 + 리뷰 + 테스트를 덮으려 함   │
│                                         │
│  결과: 모든 것에서 형편없음              │
└─────────────────────────────────────────┘
```

세 가지가 망가집니다:

1. **컨텍스트 포화** - 툴 결과가 쌓입니다. 30번째 턴이 되면 에이전트는 150k 토큰의 파일 내용, 명령 출력, 이전 추론을 소비했습니다. 5번째 턴의 중요한 세부 사항이 사라집니다.

2. **역할 혼란** - "연구자, 코더, 리뷰어, 테스터입니다"라고 말하는 시스템 프롬프트는 반만 리서치하고, 반만 코딩하며, 리뷰를 끝내지 못하는 에이전트를 생성합니다.

3. **순차적 병목** - 에이전트가 파일 A를 읽은 다음 파일 B를 읽고, 그 다음 파일 C를 읽습니다. 세 개의 순차적 LLM 호출. 세 개의 순차적 툴 실행. 병렬성 없음.

### 멀티에이전트 솔루션

작업을 분할합니다. 각 에이전트에 하나의 작업, 하나의 컨텍스트 윈도우, 그 작업에 맞게 조정된 하나의 시스템 프롬프트를 부여합니다:

```
┌──────────────────────────────────────────────────────────┐
│                    오케스트레이터                          │
│                                                          │
│  "사용자 관리 REST API 구축"                              │
│                                                          │
│         ┌──────────┬──────────┬──────────┐               │
│         │          │          │          │               │
│         ▼          ▼          ▼          ▼               │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │리서처    │ │ 코더     │ │ 리뷰어   │ │ 테스터   │  │
│   │          │ │          │ │          │ │          │  │
│   │ 문서     │ │ 리서치   │ │ 코드     │ │ 테스트   │  │
│   │ 읽고     │ │ 기반     │ │ 품질     │ │ 실행     │  │
│   │ 패턴     │ │ 코드     │ │ 확인,    │ │ 결과     │  │
│   │ 찾기     │ │ 작성     │ │ 버그     │ │ 보고     │  │
│   │          │ │          │ │ 발견     │ │          │  │
│   └─────┬────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│         │           │            │             │         │
│         └───────────┴────────────┴─────────────┘         │
│                          │                               │
│                     결과 병합                             │
└──────────────────────────────────────────────────────────┘
```

각 에이전트가 보유한 것:
- 집중된 시스템 프롬프트 ("당신은 코드 리뷰어입니다. 버그를 찾는 것이 유일한 작업입니다.")
- 자체 컨텍스트 윈도우 (다른 에이전트의 작업으로 오염되지 않음)
- 명확한 입력/출력 계약 (리서치 노트를 받고 코드를 출력)

### 실제로 이를 수행하는 시스템

**Claude Code 서브에이전트** - Claude Code가 `Task`로 서브에이전트를 생성할 때, 범위 지정된 작업으로 자식 에이전트를 생성합니다. 부모는 컨텍스트를 깨끗하게 유지합니다. 자식은 집중된 작업을 수행하고 요약을 반환합니다.

**Devin** - 플래너 에이전트, 코더 에이전트, 브라우저 에이전트를 실행합니다. 플래너가 작업을 단계로 분할합니다. 코더가 코드를 작성합니다. 브라우저가 문서를 연구합니다. 각자 별도의 컨텍스트를 보유합니다.

**멀티에이전트 코딩 팀 (SWE-bench)** - SWE-bench에서 최고 성능의 시스템은 코드베이스를 읽는 리서처, 수정을 설계하는 플래너, 구현하는 코더를 사용합니다. 단일 에이전트 시스템은 점수가 더 낮습니다.

**ChatGPT Deep Research** - 병렬로 여러 검색 에이전트를 생성하고, 각 에이전트가 다른 각도를 탐색한 다음 결과를 종합합니다.

### 스펙트럼

멀티에이전트는 이진적이지 않습니다. 스펙트럼입니다:

```
단순 ──────────────────────────────────────────── 복잡

  단일        서브         파이프라인    팀         스웜
  에이전트     에이전트

  ┌───┐     ┌───┐        ┌───┐───┐  ┌───┐───┐  ┌─┐┌─┐┌─┐
  │ A │     │ A │        │ A │ B │  │ A │ B │  │ ││ ││ │
  └───┘     └─┬─┘        └───┘─┬─┘  └─┬─┘─┬─┘  └┬┘└┬┘└┬┘
              │                │       │      ┌┴──┴──┴┐
            ┌─┴─┐          ┌───┘───┐   │      │공유   │
            │ a │          │ C │ D │ ┌─┴───┴─┐  │ 상태   │
            └───┘          └───┘───┘ │  메시지 │  └───────┘
                                      │  버스   │
  1 루프      부모 +        단계별     │       │  N 피어,
  1 컨텍스트  자식 작업     처리       └───────┘  창발적
                                      명시적     행동
                                      역할
```

**단일 에이전트** - 하나의 루프, 하나의 프롬프트. 단순한 작업에 적합.

**서브에이전트** - 부모가 집중된 하위 작업을 위해 자식을 생성합니다. 부모가 계획을 유지합니다. 자식이 보고합니다. 이것이 Claude Code가 수행하는 방식입니다.

**파이프라인** - 에이전트가 순차적으로 실행됩니다. 에이전트 A의 출력이 에이전트 B의 입력이 됩니다. 단계별 워크플로우에 적합: 리서치 -> 코드 -> 리뷰 -> 테스트.

**팀** - 에이전트가 공유 메시지 버스로 병렬 실행됩니다. 각자 역할이 있습니다. 오케스트레이터가 조정합니다. 다양한 기술이 동시에 필요할 때 적합합니다.

**스웜** - 공유 상태가 있는 많은 동일 또는 유사한 에이전트. 고정 오케스트레이터 없음. 에이전트가 큐에서 작업을 선택합니다. 고처리량 병렬 작업에 적합합니다.

### 4가지 멀티에이전트 패턴

#### 패턴 1: 파이프라인

```
입력 ──▶ 에이전트 A ──▶ 에이전트 B ──▶ 에이전트 C ──▶ 출력
          (리서치)     (코드)        (리뷰)
```

각 에이전트가 데이터를 변환하여 전달합니다. 추론하기 쉽습니다. 한 단계에서 실패하면 나머지가 차단됩니다.

#### 패턴 2: Fan-out / Fan-in

```
                ┌──▶ 에이전트 A ──┐
                │                │
입력 ──▶ 분할 ├──▶ 에이전트 B ──├──▶ 병합 ──▶ 출력
                │                │
                └──▶ 에이전트 C ──┘
```

 작업을 병렬 에이전트에 분할한 다음 결과를 병합합니다. 독립적인 하위 작업으로 분해 가능한 작업에 적합합니다.

#### 패턴 3: 오케스트레이터-워커

```
                    ┌──────────┐
                    │  오케스트. │
                    └──┬───┬───┘
                  작업 │   │ 작업
                 ┌─────┘   └─────┐
                 ▼               ▼
           ┌──────────┐   ┌──────────┐
           │ 워커 A   │   │ 워커 B   │
           └──────────┘   └──────────┘
```

스마트 오케스트레이터가 무엇을 할지 결정하고, 워커에 위임하고, 결과를 종합합니다. 오케스트레이터 자체가 워커를 생성하는 도구가 있는 에이전트입니다.

#### 패턴 4: 피어 스웜

```
          ┌───┐ ◄──── 메시지 ────▶ ┌───┐
          │ A │                    │ B │
          └─┬─┘                    └─┬─┘
            │                          │
       메시지 │    ┌───────────┐     │ 메시지
            └───▶│  공유     │◄────┘
                 │  상태     │
            ┌───▶│  / 큐    │◄────┐
            │    └───────────┘     │
       메시지 │                    │ 메시지
          ┌─┴─┐                  ┌─┴─┐
          │ C │ ◄──── 메시지 ────▶ │ D │
          └───┘                  └───┘
```

중앙 오케스트레이터 없음. 에이전트가 피어투피어로 통신합니다. 결정이 상호작용에서 발생합니다. 디버깅이 더 어렵지만 많은 에이전트로 확장됩니다.

### 멀티에이전트를 사용하지 말아야 할 때

멀티에이전트는 복잡성을 추가합니다. 에이전트 간 모든 메시지는 잠재적 실패 지점입니다. 디버깅은 "하나의 대화를 읽는 것"에서 "5개의 에이전트에 걸쳐 메시지를 추적하는 것"으로 변경됩니다.

**단일 에이전트 유지:**
- 작업이 하나의 컨텍스트 윈도우에 맞는 경우 (작업 데이터 ~100k 토큰 미만)
-異なる段階に異なるシステムプロンプトが必要ない場合
- 순차 실행이 충분히 빠른 경우
- 작업이 충분히 단순하여 분할이 오버헤드보다 가치가 많은 경우

**복잡성 비용:**
- 모든 에이전트 경계는 손실 압축 단계입니다: 에이전트 A의 전체 컨텍스트가 에이전트 B를 위한 메시지로 요약됩니다
- 조정 로직 (누가 무엇을, 언제, 어떤 순서로 하는지) 자체가 버그의 원인입니다
- 지연시간 증가: N 에이전트는 최소 N개의 순차적 LLM 호출을 의미하며,来回する必要がある 경우 더 많습니다
- 비용 증가: 각 에이전트가 독립적으로 토큰을 소비합니다

경험 규칙: 작업이 20개 미만의 툴 호출과 100k 토큰에 맞는 경우 단일 에이전트를 유지하세요.

## 실습

### 단계 1: 과부하된 단일 에이전트

모두를 수행하려고 시도하는 단일 에이전트입니다. 거대한 시스템 프롬프트 하나와 리서치, 코드, 리뷰를 포함하는 하나의 컨텍스트 윈도우가 있습니다:

```typescript
type AgentResult = {
  content: string;
  tokensUsed: number;
  toolCalls: number;
};

async function singleAgentApproach(task: string): Promise<AgentResult> {
  const systemPrompt = `당신은 풀스택 개발자입니다. 다음을 수행해야 합니다:
1. 요구사항 연구
2. 코드 작성
3. 버그 대해 코드 리뷰
4. 테스트 작성
이 모든 것을 단일 대화에서 수행합니다.`;

  const contextWindow: string[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const research = await fakeLLMCall(systemPrompt, `연구: ${task}`);
  contextWindow.push(research.output);
  totalTokens += research.tokens;
  totalToolCalls += research.calls;

  const code = await fakeLLMCall(
    systemPrompt,
    `이 연구를 고려:\n${contextWindow.join("\n")}\n\n이제 대해 코드 작성: ${task}`
  );
  contextWindow.push(code.output);
  totalTokens += code.tokens;
  totalToolCalls += code.calls;

  const review = await fakeLLMCall(
    systemPrompt,
    `모든 이전 컨텍스트를 고려:\n${contextWindow.join("\n")}\n\n코드를 리뷰하세요.`
  );
  contextWindow.push(review.output);
  totalTokens += review.tokens;
  totalToolCalls += review.calls;

  return {
    content: contextWindow.join("\n---\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

이 접근법의 문제점:
- 컨텍스트 윈도우가 모든 단계마다 증가합니다. 리뷰 단계가 되면 리서치 노트와 코드와 이전 추론을 모두 포함합니다.
- 시스템 프롬프트가 범용적입니다. 각 단계에 맞게 조정할 수 없습니다.
- 아무것도 병렬로 실행되지 않습니다.

### 단계 2: 전문 에이전트

이제 분할합니다. 각 에이전트가 하나의 작업을 수행합니다:

```typescript
type SpecialistAgent = {
  name: string;
  systemPrompt: string;
  run: (input: string) => Promise<AgentResult>;
};

function createSpecialist(name: string, systemPrompt: string): SpecialistAgent {
  return {
    name,
    systemPrompt,
    run: async (input: string) => {
      const result = await fakeLLMCall(systemPrompt, input);
      return {
        content: result.output,
        tokensUsed: result.tokens,
        toolCalls: result.calls,
      };
    },
  };
}

const researcher = createSpecialist(
  "researcher",
  "당신은 기술 연구자입니다. 문서를 읽고, 패턴을 찾고, 발견사항을 요약합니다. 구현에 필요한 사실만 출력합니다."
);

const coder = createSpecialist(
  "coder",
  "당신은 시니어 TypeScript 개발자입니다. 요구사항과 연구 노트가 주어지면 깔끔하고 테스트된 코드를 작성합니다. 다른 것은 없습니다."
);

const reviewer = createSpecialist(
  "reviewer",
  "당신은 코드 리뷰어입니다. 버그, 보안 문제, 논리 오류를 찾습니다. 구체적입니다. 줄 번호를 인용합니다."
);
```

각 전문가는 집중된 프롬프트를 가집니다. 각자는 필요한 입력만 있는 깨끗한 컨텍스트 윈도우를 받습니다.

### 단계 3: 메시지로 조정

명시적 메시지 전달로 전문 에이전트를 연결합니다:

```typescript
type AgentMessage = {
  from: string;
  to: string;
  content: string;
  timestamp: number;
};

async function multiAgentApproach(task: string): Promise<AgentResult> {
  const messages: AgentMessage[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const researchResult = await researcher.run(task);
  messages.push({
    from: "researcher",
    to: "coder",
    content: researchResult.content,
    timestamp: Date.now(),
  });
  totalTokens += researchResult.tokensUsed;
  totalToolCalls += researchResult.toolCalls;

  const coderInput = messages
    .filter((m) => m.to === "coder")
    .map((m) => `[${m.from}에게서]: ${m.content}`)
    .join("\n");

  const codeResult = await coder.run(coderInput);
  messages.push({
    from: "coder",
    to: "reviewer",
    content: codeResult.content,
    timestamp: Date.now(),
  });
  totalTokens += codeResult.tokensUsed;
  totalToolCalls += codeResult.toolCalls;

  const reviewerInput = messages
    .filter((m) => m.to === "reviewer")
    .map((m) => `[${m.from}에게서]: ${m.content}`)
    .join("\n");

  const reviewResult = await reviewer.run(reviewerInput);
  messages.push({
    from: "reviewer",
    to: "orchestrator",
    content: reviewResult.content,
    timestamp: Date.now(),
  });
  totalTokens += reviewResult.tokensUsed;
  totalToolCalls += reviewResult.toolCalls;

  return {
    content: messages.map((m) => `[${m.from} -> ${m.to}]: ${m.content}`).join("\n\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

각 에이전트는 자신에게 주소된 메시지만 받습니다. 컨텍스트 오염 없음. 研究자의 50k 토큰의 문서 읽기는 리뷰어의 컨텍스트에 들어가지 않습니다.

### 단계 4: 비교

```typescript
async function compare() {
  const task = "Express.js API용 속도 제한 미들웨어 구축";

  console.log("=== 단일 에이전트 ===");
  const single = await singleAgentApproach(task);
  console.log(`토큰: ${single.tokensUsed}`);
  console.log(`툴 호출: ${single.toolCalls}`);

  console.log("\n=== 멀티에이전트 ===");
  const multi = await multiAgentApproach(task);
  console.log(`토큰: ${multi.tokensUsed}`);
  console.log(`툴 호출: ${multi.toolCalls}`);
}
```

멀티에이전트 버전이 더 많은 총 토큰을 사용합니다 (세 에이전트, 세 개의 별도 LLM 호출)하지만 각 에이전트의 컨텍스트는 깨끗하게 유지됩니다. 시스템 프롬프트가 전문화되기 때문에 각 단계의 품질이 향상됩니다.

## 연습 문제

1. 4번째 전문 에이전트 "테스터"를 추가하세요. 코더에게서 코드를 받고 리뷰어에게서 리뷰 피드백을 받은 다음 테스트를 작성합니다.
2. 리뷰어가 코더에게 수정 루프를 위해 피드백을 보낼 수 있도록 파이프라인을 수정하세요 (최대 2 라운드).
3. 순차적 파이프라인을 fan-out으로 변환: 리서처와 "요구사항 분석가" 에이전트를 병렬로 실행한 다음 코더에게 전달하기 전에 출력을 병합합니다.

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|----------------------|
| 스웜 | "AI 에이전트의 둔기 정신" | 공유 상태와 고정 리더가 없는 피어 에이전트 세트. 동작이 지역적 상호작용에서 발생합니다. |
| 오케스트레이터 | "보스 에이전트" | 다른 에이전트를 생성하고 관리하는 도구가 있는 에이전트. 계획하고 위임하지만 실제 작업은 하지 않을 수 있습니다. |
| 코디네이터 | "교통경찰" | 에이전트 간 메시지를 규칙에 따라 라우팅하는 비에이전트 구성요소 (종종 코드가 LLM이 아님). |
| 콘센서스 | "에이전트들이 동의함" | 진행하기 전에 여러 에이전트가 합의해야 하는 프로토콜. 충돌하는 출력을 해결해야 할 때 사용됩니다. |
