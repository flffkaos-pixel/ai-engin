# 수퍼바이저 / 오케스트레이터-워커 패턴

> 하나의 주요 에이전트가 계획하고 위임합니다; 전문 워커가 병렬 컨텍스트에서 실행되고 보고합니다. 이것은 Anthropic의 Research 시스템 뒤의 패턴입니다 (리드로 Opus 4, 서브에이전트로 Sonnet 4), 내부 리서치 eval에서 단일 에이전트 Opus 4보다 +90.2% 측정. Anthropic의 엔지니어링 게시물은 BrowseComp의 분산 80%가 토큰 사용량만으로 설명된다고 보고합니다 — 멀티에이전트가 주로 이기는 이유는 각 서브에이전트가 새로운 컨텍스트 윈도우를 얻기 때문입니다. 이 레슨은 기본 요소에서 수퍼바이저 패턴을 구축하고 프로덕션 배포의 2026 엔지니어링 레슨을 다룹니다.

**유형:** 학습 + 실습
**언어:** Python (stdlib, `threading`)
**선수 과목:** Phase 16 · 04 (Primitive Model)
**소요 시간:** ~75분

## 문제

리서치는 단일 에이전트 시스템이 실패하는 프로토타입 작업입니다. "2023년에서 2026년 사이에 멀티에이전트 시스템에서 무엇이 변경되었나요?"라고 묻습니다. 단일 에이전트가 5개의 논문을 순차적으로 읽고, 텍스트의 절반으로 컨텍스트를 채우고, 그 다음 모두 함께 추론해야 합니다. 첫 번째 논문을 5번째에 도달할 때까지 잊어버립니다. 병렬화할 수 없습니다.

수퍼바이저 패턴이 이것을 수정합니다: 하나의 주요 에이전트가 검색을 계획하고, 각 하위 질문으로 워커에 위임하고, 종합합니다. 각 워커는 좁은 질문에 대해 자체 200k 토큰 윈도우를 얻습니다. 주요는 원본 논문을 절대 보지 않습니다 — 워커 요약만 봅니다.

Anthropic의 프로덕션 Research 시스템은 단일 Opus 4 대비 내부 리서치 eval에서 +90.2%를 보고합니다. 같은 게시물은 BrowseComp 분산의 80%가 *토큰 사용량만으로* 설명된다고 주목합니다. 서브에이전트당 새 컨텍스트가 주요 메커니즘입니다.

## 개념

### 패턴

```
                 ┌──────────────┐
                 │   주요       │  계획, 분해,
                 │  (Opus 4)    │  종합
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ 워커 1  │  │ 워커 2  │  │ 워커 3  │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         새로운        새로운       새로운
         컨텍스트      컨텍스트     컨텍스트
```

주요는 원본 자료를 절대 읽지 않습니다. 워커는 주요가 종합할 때까지 서로의 작업을 절대 보지 않습니다. 각 화살표는 좁은 아티팩트가 있는 핸드오프입니다.

### 왜 이기는가

세 가지 메커니즘:

1. **서브에이전트당 새 컨텍스트.** "FIPA-ACL 유산"을 탐색하는 워커는 주요가 계획에 소비한 40k 토큰을 담지 않습니다. 하나의 질문에 200k 윈도우를 얻습니다.
2. **프롬프트를 통한 전문화.** 주요의 프롬프트는 "분해하고 종합"이고 "리서치"가 아닙니다. 각 워커의 프롬프트는 좁습니다: "X에서 변경된 내용을 찾습니다." 집중된 프롬프트가 집중된 출력을 산출합니다.
3. **병렬성.** 워커가 동시에 실행됩니다. 벽시계 시간은 roughly `max(worker_times) + plan + synthesis`이고, `sum(worker_times)`이 아닙니다.

### 엔지니어링 레슨 (Anthropic 2025)

Anthropic 게시물은 여전히 2026에 관련된 몇 가지 프로덕션 레슨을 나열합니다:

- **노력 규모를 查询 복잡도에 맞춥니다.** 단순 查询: 하나의 에이전트, 3-10개의 툴 호출. 복잡한 查询: 10개 이상의 에이전트. 주요는 호출자가 아니라 查询 복잡도를 추정해야 합니다.
- **먼저 넓게, then 좁게.** 먼저 넓은 하위 질문으로 분해한 다음, 답이 깊이를 보장하면 하위 질문당 더 많은 워커를 생성합니다.
- **레인보우 배포.** 에이전트는 길게 실행되고 상태 저장입니다. 전통적인 블루-그린이 작동하지 않습니다. Anthropic은 이전 것이 드레인되는 동안 새로운 버전을 점진적으로 출시하는 레인보우를 사용합니다.
- **토큰 사용량이 지배합니다.** 멀티에이전트는 단일 에이전트의 ~15× 토큰입니다. 작업 가치가 비용을 정당화할 때만 실행하세요.

### LangGraph 전환

LangGraph는 원래 고수준 `create_supervisor` 도우미와 함께 `langgraph-supervisor` 라이브러리를 출하했습니다. 2025년 LangChain은 툴 호출을 통해 직접 수퍼바이저 패턴을 구현할 것을 권장으로 이동했습니다, 툴 호출이 *수퍼바이저가 보는 것* (컨텍스트 엔지니어링)에 더 많은 제어를 주기 때문입니다. 라이브러리가 여전히 작동합니다; 문서가 이제 툴 호출 형태를 권장합니다.

### 실패 모드

- **주요가 계획을 환각합니다.** 주요가 실제 질문을 분해하지 않는 하위 질문을 생성하면, 워커가 잘못된 대상에 정확한 리서치를 수행합니다.
- **워커가 과도하게 탐색합니다.** 명시적 범위 경계 없이는 워커가 할당된 하위 질문을 넘어 드리프트하고 종합 단계를 오염시킵니다.
- **종합 충돌.** 두 워커가 모순되는 사실을 반환합니다. 주요는 다시询问 (라운드 추가)하거나 불일치를 명시적으로 기록해야 합니다. 한쪽을 조용히 선택하는 것이 최악의 실패입니다: 사용자가 불일치가 발생했는지 절대 알지 못합니다.

### 수퍼바이저가 잘못된 경우

- **순차적 작업.** 2단계가 literally 1단계의 출력이 필요하면, 병렬성이 아무것도 사지 않습니다. 파이프라인을 사용하세요 (CrewAI 순차적, LangGraph 선형 그래프).
- **단순 查询.** 단일 에이전트가 더 빠르고 저렴하게 처리합니다. 워커를 생성하기 전에 주요의 "노력 규모" 확인을 사용하세요.
- **엄격한 결정론.** 수퍼바이저는 LLM 선택 위임을 사용합니다. 감사/재생이 적응성보다 중요한 경우 정적 그래프가 더 좋습니다.

## 실습

`code/main.py`는 `threading`을 사용하여 3개의 병렬 워커의 수퍼바이저를 구현합니다. 주요는 쿼리를 하위 질문으로 분해하고, 워커가 각 하위 질문에서 동시에 실행되고, 주요가 종합합니다. 실제 LLM 없음 — 워커는 가져오기-및-요약하는 것을 시뮬레이션하기 위해 스크립트됩니다.

주요 구조:

- `Lead.plan(query)` 쿼리를 3개의 하위 질문으로 분할합니다.
- `Worker.run(sub_q)` 가짜 요약을 반환합니다 (프로덕션의 모든 툴 사용 에이전트일 수 있음).
- `Lead.run(query)` 스레드에서 워커를 시작하고, 조인하고, 종합합니다.

실행:

```
python3 code/main.py
```

출력은 계획, 시작/종료 타임스탬프로 병렬 워커 추적, 최종 종합을 보여줍니다. 0.3초 워커 3개가 ~0.35초에서 실행되는 것을 볼 수 있습니다, 0.9초가 아닙니다.

## 활용

`outputs/skill-supervisor-designer.md`는 사용자 쿼리를 가져와 수퍼바이저 패턴 설계를 산출합니다: 주요 시스템 프롬프트, 워커 역할, 하위 질문 분해 규칙, 종합 템플릿. 새로운 리서치 스타일 에이전트 시스템을 구축하기 전에 이것을 사용하세요.

## 결과물

수퍼바이저 패턴을 배포하기 전 체크리스트:

- **모델 페어링.** 주요는 추론层级 모델 (Opus 클래스, `o3` 클래스) 위에서. 워커는 더 빠르고 저렴한 모델 (Sonnet, `o4-mini`) 위에서.
- **워커 시간 초과.** 2× 중위수 런타임을 초과하는 워커는 죽입니다; 주요는 더 좁은 범위로 다시 생성하거나 없이 진행합니다.
- **워커당 토큰 캡.** 하드 한도 (예: 예상 합성 입력의 10×)는 도망가는 워커가 예산을 날리는 것을 방지합니다.
- **관찰 가능성.** 주요의 계획, 각 워커의 툴 호출, 합성을 추적합니다. 이것은 사후 디버깅의 기초입니다.
- **레인보우 출시.** 상태 저장 긴 실행 에이전트는 핫 스왑이 아닌 버전화된 드레인-교체이 필요합니다.

## 연습 문제

1. `code/main.py`를 실행한 다음 주요를 수정하여 5개의 워커를 생성하도록 하세요. 워커 스폰 오버헤드가 이 데모에서 병렬 절약량을 초과하는 것은 몇 번째 워커 카운트에서인지 관찰하세요.
2. 워커 시간 초과를 구현하세요: 0.5초 이상 실행되는 워커를 죽이고 주요가 남은 결과를 종합하게 하세요. 워커가 잘렸다는 것을 아려면 어떤 관찰 가능성이 필요합니까?
3. 주요의 종합에 충돌 감지 단계를 추가하세요: 두 워커가 모순되는 답을 반환하면, 주요는 하나를 선택하는 대신 불일치를 기록합니다. LLM을 호출하지 않고 모순을 감지하려면 어떻게 해야 합니까?
4. Anthropic의 Research 시스템 엔지니어링 게시물을 읽으세요. 이toy 데모가 프로덕션에서 실행하려면 채택해야 하는 세 가지 관행을 나열하세요.
5. LangGraph의 `create_supervisor` (레거시) 대 새로운 툴 호출 권장 사항을 비교하세요. 수퍼바이저가 보는 것에 대한更好的 제어를 제공하는 것은どれ입니까? Anthropic이 왜 원본 워커 컨텍스트가 아닌 하위 답변만 합성에 전달하는지 명시적으로 설명합니까?
