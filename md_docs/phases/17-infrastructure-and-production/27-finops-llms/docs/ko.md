# LLM를 위한 FinOps — 단위 경제학 및 멀티 테넌트 귀인

> 전통적인 FinOps는 LLM 지출에서 깨집니다. 비용은 토큰-트랜잭션이지 리소스 가동 시간이 아닙니다. 태그가 매핑되지 않습니다 — API 호출은 자산이 아닌 트랜잭션입니다. 엔지니어링 결정 (프롬프트 설계, 컨텍스트 창, 출력 길이)은 재무 결정입니다. 2026년 플레이북에는 1일目に 계측할 세 가지 귀인 차원이 있습니다: 사용자당 (`user_id`) — 좌석 가격 책정 및 확장을 위해, 작업당 (`task_id` + `route`) — 제품 표면 비용 및 우선 순위를 위해, 테넌트당 (`tenant_id`) — 단위 경제학 및 갱신을 위해. 4가지 토큰 레이어 — 프롬프트, 도구, 메모리, 응답 — 하나의 버킷이 지출을 숨깁니다. 멀티 테넌트 제품의 시행 사다리: 테넌트당 비율 제한 (예상 피크의 2-3배, 명확한 429 + retry-after); 일일 지출 상한 (계약된 천장의 1.5-3배; 비율 tightening + 경고 트리거); 지출 z-점수 > 4에서 킬 스위치 (자동 일시 중지 + 온콜 페이지). 귀인 패턴: 태그 및 집계, 원격 측정 조이너 (추적 ID → 결제; 가장 높은 정확도), 샘플링 및 외삽, 모델 기반 할당, 이벤트 소싱, 실시간 스트리밍. 단위 메트릭: 해결된 쿼리당 비용, 생성된 아티팩트당 비용 — $/M 토큰이 아닙니다. 소급 태그 지정은 항상 놓칩니다; 요청 생성 시 계측합니다.

**유형:** 학습
**언어:** Python (stdlib, 킬 스위치가 있는toy 비용 귀인 시뮬레이터)
**선수 과목:** Phase 17 · 13 (관찰 가능성), Phase 17 · 14 (캐싱)
**소요 시간:** ~60분

## 학습 목표

- 전통적인 FinOps (태그 + 계층)가 LLM 지출에서 깨지는 이유를 설명하고 세 가지 새로운 귀인 차원을 이름 짓습니다.
- 4가지 토큰 레이어 (프롬프트, 도구, 메모리, 응답)를 열거하고 단일 버킷 청구가 비용을 숨기는 이유를 설명합니다.
- 멀티 테넌트 제품에 대한 시행 사다리 (비율 → 지출 상한 → 킬 스위치)를 설계합니다.
- $/M 토큰 대신 단위 메트릭 (해결된 쿼리당 비용 / 아티팩트당 비용)을 선택합니다.

## 문제

 청구서에는 $40,000이라고 적혀 있습니다. 모릅니다:
- 어떤 테넌트가 그것을 지출했는지.
- 어떤 제품 기능이 그것을驱动했는지.
- 개별 사용자가 남용했는지.
- 프롬프트 풍금, 도구 호출 또는 메모리 증폭이 범인인지.

공급자側에서 태그 및 집계는 태그가 라인 항목으로 전파되는 클라우드 리소스 (EC2, S3)에 대해 작동합니다. LLM API 호출은 자동 태그 지정되지 않습니다 — 호출 사이트에서 user/task/tenant를 stampt하고携带해야 합니다. 소급 귀인은 항상 edge cases을 놓칩니다.

## 개념

### 세 가지 귀인 차원

**사용자당** (`user_id`): 누가 무엇에 비용을 쓰는가. 좌석 가격 책정, 확장 대화, 파워 유저 식別に 사용됩니다.

**작업당** (`task_id` + `route`): 어떤 제품 표면이 무엇에 비용이 드는가. 기능 우선 순위, 비싼 기능 kill 결정에 사용됩니다.

**테넌트당** (`tenant_id`): 어떤 고객이 수익적인가. 단위 경제학, 갱신 가격 책정, 계층 임계값에 사용됩니다.

첫날에 호출 사이트에서 세 가지를 모두 계측합니다. 소급은 항상 더 나쁩니다.

### 4가지 토큰 레이어

| 레이어 | 예 | 총액의 전형적인 % |
|-------|-----|------------------|
| 프롬프트 | 시스템 + 사용자 입력 | 40-60% |
| 도구 | 되돌아가는 도구 호출 결과 | 20-40% (에이전트 워크로드) |
| 메모리 | 이전 대화 / 검색된 문서 | 10-30% |
| 응답 | 모델 출력 | 10-30% |

4개를 모두 함께 버키팅하면 최적화가 블라인드됩니다. 귀인 스키마에서它们를分解합니다.

### 시행 사다리

1. **비율 제한** 테넌트당. 예상 피크의 2-3배. 429와 함께 반환 + `Retry-After`. 테넌트가 마찰을 saw; 놀라운 청구서 없음.

2. **일일 지출 상한** 테넌트당. 계약된 천장의 1.5-3배. 트리거: 비율 제한 tightening + 고객 성공 경고.

3. **킬 스위치** 테넌트 기준 대비 지출 z-점수 > 4에서. 자동 일시 중지 테넌트; 온콜 페이지; ops + CS로エスカレーション.

### 귀인 패턴

- **태그 및 집계**: 메타데이터 헤더를 stampt; 나중에 집계. 단순; 대략적.
- **원격 측정 조이너**: 추적 ID를 통해 추적을 결제에 조인. 가장 높은 정확도. 성숙한 팀이 하는 일.
- **샘플링 + 외삽**: 5-10% 샘플링, 곱셈. 대략적인 지출에 비용 효과적; tails을 놓칩니다.
- **모델 기반 할당**: 비용驱动 요인을推断하기 위한 회귀. 태그 없는 레거시 데이터용.
- **이벤트 소싱**: 스트림의 비용 이벤트 (Kafka / Kinesis). 실시간.
- **실시간 스트리밍**: 대시보드가 초 미만으로 업데이트됩니다.

### 비용/X가 단위 메트릭입니다

$/M 토큰은 공급업체 말입니다. 제품 메트릭:

- 해결된 지원 티켓당 비용.
- 생성된 아티팩트당 비용.
- 성공적인 에이전트 작업당 비용.
- 사용자 세션-분당 비용.

 비용을 제품 결과에 연결합니다. 그렇지 않으면 최적화가 고정되지 않습니다.

### 비용 귀인 추적 형태

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

모든 호출에서emit합니다. 데이터 레이크에 저장합니다. 차원별로 집계합니다. Phase 17 · 13 관찰 가능성 스택이 이것이 사는 곳입니다.

### 복합 절감 스택

스택: 캐시 + 배치 + 라우팅 + 게이트웨이. 4개 모두 함께:
- 캐시 L2 (Phase 17 · 14): 입력 ~10x 더 저렴.
- 배치 (Phase 17 · 15): 50% 할인.
-廉价 모델로 라우팅 (Phase 17 · 16): 비용 60% 감소.
- 게이트웨이 효율성 (Phase 17 · 19): 중복 + 재시도.

최상의 경우 누적: naive 기준의 ~5-10%. 대부분의 팀은 2-3개 레버만 활용; 4개 모두 누적하는 팀은 거의 없습니다.

### 기억해야 할 숫자

- 귀인 차원: 사용자당, 작업당, 테넌트당.
- 4가지 토큰 레이어: 프롬프트, 도구, 메모리, 응답.
- 킬 스위치: 지출 z-점수 > 4.
- 단위 메트릭: 해결된 쿼리당 비용, $/M 토큰 아님.
- 누적 최적화: 기준의 ~5-10% 가능.

## 활용

`code/main.py`는 3단계 시행 사다리가 있는 멀티 테넌트 LLM 서비스를 시뮬레이션합니다. 남용 테넌트를 주입하고 킬 스위치가 발사되는 것을演示합니다.

## 연습문제

1. `code/main.py`를 실행하세요. 킬 스위치가 어느 z-점수에서 발사합니까? 임계값을 어떻게 선택합니까?
2. 테넌트별, 작업별 비용 대시보드를 설계하세요. 처음 구축하는 5가지 뷰는 무엇입니까?
3. 가장 큰 테넌트가 단위 경제학적으로 negative입니다. 고객 영향별로 정렬된 3가지 개입을 제안하세요.
4. 지원 제품의 해결된 티켓당 비용을 계산합니다: 티켓당 3M 토큰, ~하루 800 티켓, GPT-5 캐시된 요금.
5. 소급 태그 지정이 작동할 수 있는지 주장하세요. 언제 허용가능합니까?
