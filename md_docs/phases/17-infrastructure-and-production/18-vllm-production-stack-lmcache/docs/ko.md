# LMCache KV 오프로딩이 있는 vLLM 프로덕션 스택

> vLLM의 프로덕션 스택은 참조 Kubernetes 배포입니다 — 라우터, 엔진, 관찰 가능성이 함께 연결됩니다. LMCache는 KV 캐시를 GPU 메모리에서 추출하여 쿼리 및 엔진 전반에서 재사용하는 KV 오프로딩 레이어입니다 (CPU DRAM, 그 다음 disk/Ceph). vLLM 0.11.0 KV 오프로딩 커넥터 (2026년 1월)는 이를 Connector API (v0.9.0+)를 통해 비동기식 및 플러그형으로 만듭니다. 오프로딩 지연은 사용자에게 공개되지 않습니다. LMCache는 공유 접두사 없이도 가치가 있습니다 — GPU가 KV 슬롯에서 실행되지 않을 때, 선점된 요청이を再計算하는 대신 CPU에서 복원될 수 있습니다. 16x H100 (80GB HBM)에서 4 a3-highgpu-4g에 걸친 게시된 벤치마크: KV 캐시가 HBM을 초과할 때 네이티브 CPU 오프로드와 LMCache 모두 처리량을 크게 개선합니다; KV 발자국이 낮으면 모든 구성이 기준과 일치하며 작은 오버헤드가 있습니다.

**유형:** 학습
**언어:** Python (stdlib, toy KV-spill 시뮬레이터)
**선수 과목:** Phase 17 · 04 (vLLM Serving Internals), Phase 17 · 06 (SGLang/RadixAttention)
**소요 시간:** ~60분

## 학습 목표

- vLLM 프로덕션 스택 레이어를 다이어그램으로 그립니다: 라우터, 엔진, KV 오프로드, 관찰 가능성.
- KV 오프로딩 커넥터 API (v0.9.0+)와 0.11.0 비동기 경로가 오프로딩 지연 시간을 숨기는 방법을 설명합니다.
- LMCache CPU-DRAM이 도움되는 경우 (KV > HBM) 대 오버헤드를 추가하는 경우 (KV가 HBM에 맞을 만큼 충분히 작은 경우)를 정량화합니다.
- 배포 제약 조건 given으로 네이티브 vLLM CPU 오프로드와 LMCache 커넥터 사이에서 선택합니다.

## 문제

vLLM 제공에서 동시성이 올라갈 때마다 HBM 100%에서 선점 이벤트가 있는 GPUs가 보입니다. 요청이 제거되고, 다시 대기열에 넣고, 같은 2K 토큰 프롬프트를 한 시간에 네 번 다시 prefill합니다. GPU 계산이冗長한 prefills에 spent됩니다; goodput은 원시 처리량보다 훨씬 낮습니다.

더 많은 GPU 추가는 선형으로 비용이 듭니다. 더 많은 HBM 추가는 불가능합니다. 하지만 CPU DRAM은 저렴합니다 — 하나의 소켓에는 순서대로 더 나쁜 지연 시간으로 HBM보다 훨씬 낮은 512 GB+가 있지만 "일시적으로 따뜻한" KV 캐시에는 fine입니다.

LMCache는 KV 캐시를 CPU DRAM으로 추출하여 선점된 요청이 빠르게 복구되고, 엔진 전반에서 반복되는 접두사가 각 엔진이 다시 prefill하지 않고 캐시를 공유합니다.

## 개념

### vLLM 프로덕션 스택

`github.com/vllm-project/production-stack`은 참조 Kubernetes 배포입니다:

- **라우터** — 캐시 인식 (Phase 17 · 11). KV 이벤트를 소비합니다.
- **엔진** — vLLM 작업자. GPU당 하나 또는 TP/PP 그룹당 하나.
- **KV 캐시 오프로드** — LMCache 배포 또는 네이티브 커넥터.
- **관찰 가능성** — Prometheus 스크래프, Grafana 대시보드, OTel 추적.
- **컨트롤 플레인** — 서비스 검색, 구성, 롤링 업데이트.

Helm 차트 + 오퍼레이터로 제공됩니다.

### KV 오프로딩 커넥터 API (v0.9.0+)

vLLM 0.9.0은 플러그형 KV 캐시 백엔드를 위한 Connector API를 도입했습니다. 엔진이 커넥터에 블록을 오프로드합니다; 커넥터가 它们를 저장합니다 (RAM, 디스크, 객체 스토리지, LMCache). 요청이 블록이 필요하면 커넥터가 다시 로드합니다.

vLLM 0.11.0 (2026년 1월)은 비동기 오프로드 경로를 추가합니다 — 오프로드가 배경에서 발생할 수 있으므로 엔진이 일반적인 경우 그것에서 차단하지 않습니다. 종단 간 지연 시간과 처리량은 여전히 작업 형태, KV 캐시 적중률, 시스템 압력에 따라 달라집니다; vLLM의 자체 노트는 사용자 정의 커널 오프로드가 낮은 적중률에서 처리량을 저하시킬 수 있으며 비동기 스케줄링이 스펙큘러티브 디코딩과 알려진 상호 작용 문제가 있다고呼叫합니다.

### 네이티브 CPU 오프로드 대 LMCache

**네이티브 vLLM CPU 오프로드**: 엔진-로컬. KV 블록을 호스트 RAM에 저장합니다. 구현이 빠르고 네트워크 홉이 없습니다. 엔진을 횡단하지 않습니다.

**LMCache 커넥터**: 클러스터 규모. CPU DRAM + Ceph/S3 계층이 있는 공유 LMCache 서버에 블록을 저장합니다. 블록은 모든 엔진에서 액세스할 수 있습니다. 16x H100 벤치마크 게시.

엔진 하나에 HBM 압력이 있을 때 네이티브를 선택하세요. 여러 엔진이 접두사를 공유할 때 (일반적인 시스템 프롬프트가 있는 RAG, 공유 템플릿이 있는 멀티 테넌트) LMCache를 선택하세요.

### 벤치마크 동작

16x H100 (80 GB HBM) 4 a3-highgpu-4g에 걸친 테스트:

- 낮은 KV 발자국 (짧은 프롬프트, 낮은 동시성): 모든 구성이 기준과 일치하고, LMCache는 ~3-5% 오버헤드를 추가합니다.
- 중간 발자국: LMCache가 엔진 전반의 접두사 재사용에서 도움이 되기 시작합니다.
- KV가 HBM을 초과합니다: 네이티브 CPU 오프로드와 LMCache 모두 처리량을 크게 개선합니다; 교차 엔진 공유로 인해 LMCache가 더 큰 이득입니다.

### LMCache가 결정적인 경우

- 시스템 프롬프트가 테넌트 전반에서 공유되는 멀티 테넌트 제공.
- 문서 청크가 쿼리 전반에서 반복되는 RAG.
- 동일한 베이스에서 fine-tuned 변형 (LoRA) — 베이스 모델 KV 재사용이冗長한 작업을 절감합니다.
- 선점 무거운 작업: CPU에서 복원하는 것이 다시 prefill하는 것보다 저렴합니다.

### 활성화하지 말 때

- 작은 HBM 압력 — 혜택 없이 오버헤드를 지불합니다.
- 짧은 컨텍스트 (<1K 토큰) — 전송 시간 > 다시 prefill.
- 단일 테넌트 단일 프롬프트 작업 — 캡처할 재사용이 없습니다.

### 분리된 서비스와의 통합

Phase 17 · 17 분리된 서비스 + LMCache가 결합됩니다: prefill 풀에서 decode 풀트로의 KV 전송이 사용되지 않으면 LMCache에landing합니다; 후속 쿼리가 LMCache에서 가져옵니다. Phase 17 · 11 캐시 인식 라우터는 지역 OR LMCache 공유 캐시가 일치하는 엔진으로 라우팅할 수 있습니다.

### 기억해야 할 숫자

- vLLM 0.9.0: 커넥터 API shipping.
- vLLM 0.11.0 (2026년 1월): 비동기 오프로드 경로; 종단 간 지연 시간 영향은 작업, KV 적중률, 시스템 압력에 따라 다릅니다 (절대 보장이 아님).
- 16x H100 벤치마크: KV 발자국이 HBM을 초과할 때 LMCache가 도움됩니다.
- 작은 HBM 압력: 이점 없이 3-5% 오버헤드.

## 활용

`code/main.py`는 LMCache 유무에 관계없이 선점 무거운 작업을 시뮬레이션합니다. 피한 재-prefills, 처리량 이득, 균형 HBM 利用률을 보고합니다.

## 결과물

이 레슨은 `outputs/skill-vllm-stack-decider.md`를 산출합니다. 작업 형태와 vLLM 배포가 주어지면 네이티브 대 LMCache 대 둘 다 아님을 결정합니다.

## 연습문제

1. `code/main.py`를 실행하세요. 어느 HBM 利用률에서 LMCache가 지불하기 시작합니까?
2. 테넌트가 시간당 200개의 쿼리에서 6K 토큰 시스템 프롬프트를 공유합니다. 테넌트당 예상 LMCache 절감을 계산하세요.
3. LMCache 서버는 단일 장애 지점입니다. HA 전략 (복제본, 네이티브로 폴백)을 디자인하세요.
4. LMCache가 스핀닝 디스크의 Ceph에 저장합니다. 70B FP8에서 4K 토큰 KV (500 MB)의 읽기 시간 대 다시 prefill은 얼마입니까?
5. vLLM 0.11.0 비동기 경로가 "무료"인지 주장하세요 — 오버헤드가 어디에 숨겨집니까?
