# 접두사 무거운 작업을 위한 SGLang과 RadixAttention

> SGLang은 KV 캐시를 라딕스 트리에 저장된 일등 시민, 재사용 가능한 리소스로 취급합니다. vLLM이 요청을 FCFS (선착순)로 스케줄링하는 반면, SGLang의 캐시 인식 스케줄러는 더 긴 공유 접두사를 가진 요청을 우선시합니다 — 효과적으로 깊이 우선 라딕스 순회하여 핫 브랜치가 HBM에 상주하도록 합니다. ShareGPT 유사 1K 프롬프트가 있는 Llama 3.1 8B에서 SGLang은 vLLM의 ~12,500에 비해 ~16,200 tok/s를 hits하여 ~29% 우위입니다. 접두사 무거운 RAG 작업에서 우위가 6.4배에 도달합니다. 음성 클로닝 형태의 작업에서 캐시 적중率 86%를clear했습니다. 2026년 xAI, LinkedIn, Cursor, Oracle, GCP, Azure, AWS에서 400,000+ GPU에 배포되었습니다. 함정은 접두사 순서가 일관되지 않으면 6.4배 숫자가 증발한다는 것입니다 — 순서가 엔지니어의 지렛대입니다.

**유형:** 학습
**언어:** Python (stdlib, toy radix-tree cache + cache-aware 스케줄러)
**선수 과목:** Phase 17 · 04 (vLLM Serving Internals), Phase 14 (Agentic RAG)
**소요 시간:** ~75분

## 학습 목표

- RadixAttention을 다이어그램으로 그립니다: 접두사가 라딕스 트리에 저장되는 방식과 KV 블록이 같은 브랜치에 뿌리를 둔 시퀀스間で共有되는 방식.
- 캐시 인식 스케줄링을 설명하고 FCFS가 접두사 무거운 트래픽에 왜 잘못되었는지 설명합니다.
- 접두사 캐시 적중率과 프롬프트 길이 분포가 주어지면 예상되는 스피드업을 계산합니다.
- 6.4배 숫자를 진짜 versus 잃은 상향으로 만드는 프롬프트 순서 규율을 이름 짓습니다.

## 문제

클래식 서비스는 각 요청의 프롬프트를 불투명하게 취급합니다. 5,000개의 RAG 요청이 모두 동일한 2,000토큰 시스템 프롬프트 plus 동일한 검색 침두어로 시작하더라도 vLLM은 그 2,000토큰 접두사를 5,000번 prefill합니다. GPU가 같은 작업을 반복합니다.

관찰: 에이전트 및 RAG 작업의 프롬프트는 거의 항상 긴 접두사를 공유합니다. 시스템 프롬프트, 도구 스키마, 퓨샷 예제, 검색 헤더, 대화 기록 — 모두 요청間で 반복됩니다. 그 접두사에 대한 KV 캐시를 한 번 저장하고 재사용하면 다시 prefill할 필요가 없습니다.

RadixAttention이 정확히 이것을 합니다. 토큰은 라딕스 트리에 인덱싱됩니다; 각 노드는 경로 위의 토큰 시퀀스에 대한 KV 블록을 소유합니다. 새 요청이 트리를 walking합니다: 토큰이 일치하는 노드는 해당 노드의 KV 블록을 재사용합니다. Prefill 비용이 전체 프롬프트가 아닌 "새" 접미사에 비례합니다.

도전은 스케줄링입니다. 두 요청이 2,000토큰 접두사를 공유하고 세 번째가 같은 접두사의 200토큰만 공유하면, 두 개의 긴 공유 요청을 함께 제공하여 긴 접두사가 HBM에 상주하도록 해야 합니다. FCFS는反対합니다 — 도착한 요청을 먼저提供服务하여, 다음 긴 접두사 요청이 도착하기 전에 핫 브랜치가 제거될 수 있습니다.

## 개념

### KV 인덱스로서의 라딕스 트리

라딕스 트리 (압축 trie)는 토큰 시퀀스를 저장합니다. 각 노드는 토큰 범위와 해당 범위에 대해 계산된 KV 블록을 소유합니다. 하위는 시퀀스를 하나 이상의 토큰으로 확장합니다.

```
root
  |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
       |- "Context: <doc A>..."        (500 tokens, 31 blocks)
            |- "Question: Alice..."    (80 tokens, 5 blocks)
            |- "Question: Bob..."      (95 tokens, 6 blocks)
       |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

시스템 프롬프트 + "Context: <doc A>" + "Question: Carol"이 포함된 새 요청이 도착합니다. 스케줄러가 walking합니다: 시스템 접두사 일치 (124 블록 재사용), doc-A 브랜치 일치 (31 블록 재사용), 그 다음 "Question: Carol" (4 블록)에만 새 블록을 할당합니다. Prefill 비용: 4 블록의 새 토큰. 트리 없이는: 160 블록. Prefill에서 ~40배 절감.

### 캐시 인식 스케줄링

라딕스 트리 지원 재사용은 캐시가 소용돌이칠 경우 무의미합니다. 두 가지 주요 정책:

1. **깊이 우선 배포**. 대기열에서 다음 요청을 선택할 때 현재 실행 세트와 같은 브랜치에 뿌리를 둔 요청을 선호합니다. 이것은 핫 브랜치를 고정합니다.
2. **블록 수준而非 브랜치 수준의 LRU**. 개별 블록而非 가장 짧게 사용된 리프부터 시작하여 전체 브랜치 (가장 짧게 사용된 리프부터)를 제거하여 캐시 모양이 라딕스 모양과 일치하도록 합니다.

FCFS는 둘 다 위반합니다. 2,000토큰을 공유하는 요청이 50토큰을 공유하는 요청 뒤에 앉아 있으면 2,000토큰 브랜치가 50토큰 것을 허용하기 위해 제거됩니다.

### 외워야 할 벤치마크 숫자

- Llama 3.1 8B, H100, ShareGPT 1K 프롬프트: SGLang ~16,200 tok/s 대 vLLM ~12,500 (~29% 우위).
- 접두사 무거운 RAG (동일한 시스템 + 동일한 doc, 다양한 질문): SGLang에서 최대 6.4배.
- 음성 클로닝 작업: 86.4% 접두사 캐시 적중率.
- SGLang 고객 전체의 프로덕션 적중율: 프롬프트 규율에 따라 50-99%.
- 2026년 400,000+ GPU에 배포.

### 순서 함정

6.4배 숫자는 일관된 프롬프트 템플릿 순서에 의존합니다. 클라이언트가 일부 요청에서 `[system, tools, context, history, question]`로 프롬프트를 구성하고 다른 요청에서 `[system, context, tools, history, question]`로 구성하면 트리가 공유 접두사를 찾을 수 없습니다. 인간에게 공유 접두사로 보이는 것은 라딕스 트리에는 두 개의 고유한 시퀀스입니다.

엔지니어의 지렛대: 프롬프트 템플릿은 캐시 키입니다. 순서를 수정하세요. 모든 불변 (system, tools, schemas)을 먼저 배치하세요. 검색 컨텍스트를 다음에 배치하세요. 사용자 질문을 마지막에 배치하세요. 동적 콘텐츠를 캐시 가능한 접두사에 섞지 마세요.

연구의 실제 사례: 동적 콘텐츠를 캐시 가능한 접두사 밖으로 이동하면 한 배포에서 7%에서 74% 캐시 적중율로 변경되었습니다.

### RadixAttention이 이기고 지는 곳

이기는 곳:
- RAG (동일한 검색 침두사, 다양한 질문).
- 에이전트 (동일한 도구 스키마, 다양한 쿼리).
- 긴 시스템 프롬프트가 있는 채팅.
- 반복된 침두사가 있는 음성/비전 작업.

지는 곳 (vLLM 수준 처리량으로 돌아감):
- 고유한 프롬프트가 있는 단일 샷 생성 (코드 완성, 시스템 프롬프트 없이 열린 채팅).
- 모든 요청이 접두사에 고유한 콘텐츠를 섞는 동적 프롬프트.

### 이것이 스케줄러 문제이고 커널 문제만이 아닌 이유

KV 재사용을 커널 트릭으로 구현할 수 있습니다. SGLang의 통찰력은 재사용이 스케줄러가 핫 브랜치를 상주시키는 경우에만 payoff한다는 것입니다. 순진한 "가능하면 재사용" 정책은 mixed 부하에서 캐시를 소용돌이칠 것입니다. 라딕스 트리 인덱싱 스케줄러가 커널 트릭을 29% 프로덕션 우위로 전환합니다.

### vLLM과의 상호작용

두 시스템은 엄격한 경쟁자가 아닙니다. 2026년 vLLM은 접두사 캐싱 (`--enable-prefix-caching`)과 캐시 인식 라우터 (Rust의 vLLM Router)를 추가했습니다. 격차가 줄어들었지만 완전히 사라지지 않았습니다 — SGLang의 전체 스택이 라딕스 우선입니다; vLLM은 그것을 접목했습니다. 접두사 재사용이 지배하는 작업의 경우 SGLang이 여전히 기본값입니다. 강력한 접두사 패턴 없이 범용服务的 경우 vLLM이 동일하거나 더 좋습니다.

## 활용

`code/main.py`는 두 가지 정책 (FCFS 및 캐시 인식)이 있는 toy radix-tree KV 캐시 plus 스케줄러를 구현합니다. 동일한 작업을 통해 둘 다 실행하고, 접두사 캐시 적중率과 처리량 델타를 보고합니다. 그런 다음 "랜덤 순서" 작업을 실행하여 6.4배 collapse를 보여줍니다.

## 연습문제

1. `code/main.py`를 실행하세요. 동일한 작업에서 FCFS와 캐시 인식을 비교하세요. 델타가 어디서 오는지 — prefill 절감, decode 절감, 큐 지연?
2. 프롬프트가 `[system, tools, context]`를 무작위로 permute하도록 작업을 수정하세요. 다시 실행하세요. 적중율에 무엇이 발생합니까? 왜?
3. Llama 3.1 8B에서 2,000토큰 시스템 프롬프트를 하나의 라딕스 브랜치로 상주시키는 HBM 비용을 계산하세요. 접두사 재사용 없이 16시퀀스 배치 비용과 비교하세요.
4. SGLang RadixAttention 논문을 읽으세요. 세 문장으로 트리 모양 LRU 제거가 접두사 무거운 부하에서 블록 모양 LRU를 이기는 이유를 설명하세요.
5. 고객이 8% 캐시 적중율만 보고합니다. 세 가지 가능한 원인과 각각 대해 실행할 진단의 이름을 붙이세요.

## 핵심 용어

| 용어 | 人们怎么说 | 실제 의미 |
|------|----------------|------------------------|
| RadixAttention | "SGLang 것" | KV 캐시가 공유 접두사가 블록을 재사용하도록 라딕스 트리로 인덱싱됨 |
| 라딕스 트리 | "압축 trie" | 각 노드가 토큰 범위와 KV 블록을 소유하는 트리 |
| 캐시 인식 스케줄러 | "hot-branch-first" | 상주 브랜치를 공유하는 요청을 선호하는 스케줄러 |
| 접두사 캐시 적중율 | "프롬프트의 얼마가 무료였는지" | 재사용된 KV 블록에서 서비스된 프롬프트 토큰 비율 |
| FCFS | "선착순" | 접두사 지역성을 깨는 기본 스케줄링 |
| 브랜치 수준 LRU | "리프 제거" | 라딕스 모양과 일치하는 것으로 제거된 eviction 정책 |
| 프롬프트 템플릿 순서 | "캐시 키" | 트리가 공유할 수 있는 것을 결정하는 프롬프트 구성 요소 순서 |
| 시스템 프롬프트 고정 | "상주 접두사" | 제거 소용돌이를 피하기 위해 불변 시스템을 고정 상태로 유지 |
