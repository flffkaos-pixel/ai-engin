# 장기 실행 백그라운드 에이전트: 지속적 실행

> 프로덕션 장기 실행 에이전트는 `while True`로 실행되지 않는다. 모든 LLM 호출은 체크포인트, 재시도 및 재생이 있는 활동이 된다. Temporal의 OpenAI Agents SDK 통합은 2026년 3월에 GA가 되었다. Claude Code Routines(Anthropic)는 지속적인 로컬 프로세스 없이 예약된 Claude Code 호출을 실행한다. 세션은 인간 입력에서 일시 중지되고, 배포에서 살아남으며, `thread_id`로 키가 지정된 최신 체크포인트에서 재개된다. 새로운 사용성 뒤에는 오래된 패턴(워크플로우 오케스트레이션)이 있으며, 하나의 새로운 입력이 있다: 복구 시 결정적으로 재생되어야 하는 비결정적 활동으로서의 LLM 호출.

**Type:** 학습
**Languages:** Python (stdlib, minimal durable-execution state machine)
**Prerequisites:** Phase 15 · 10 (권한 모드), Phase 15 · 01 (장기 실행 에이전트)
**Time:** ~60분

## 문제

4시간 동안 실행되는 에이전트를 생각해보자. 세 가지 도구를 호출하고, 사용자에게 두 번 프롬프트하며, 40번의 LLM 호출을 한다. 중간에 실행 중인 호스트가 재부팅된다. 무슨 일이 일어나는가?

- 순진한 `while True` 루프에서는: 모든 것이 손실된다. 실행이 처음부터 다시 시작된다. 세 가지 도구 호출(실제 부작용 포함)이 다시 실행된다. 사용자는 이미 승인한 것에 대해 다시 프롬프트된다. 40번의 LLM 호출이 다시 청구된다.
- 지속적 실행에서는: 실행이 가장 최근 체크포인트에서 재개된다. 이미 완료된 활동은 재실행되지 않으며, 그 결과는 지속적 로그에서 재생된다. 사용자는 이미 승인한 것을 다시 승인하지 않는다. 이미 이루어진 LLM 호출은 다시 청구되지 않는다.

이는 워크플로우 엔진이 10년 동안 제공해온 것과 동일한 패턴이다(Temporal, Cadence, Uber의 Cherami). 새로운 점은 LLM 호출이 이제 한 종류의 활동(비결정적이고, 비용이 많이 들며, 부작용이 있음)이 되었고, 이 패턴에 깔끔하게 맞는다는 것이다.

이 레슨의 핵심 주제: 장기 실행 신뢰도는 감소한다(METR은 "35분 저하"를 관찰 — 성공률이 지평에 따라 대략 2차 함수적으로 감소). 지속적 실행은 신뢰도 프로필이 지원하는 것보다 더 긴 실행을 가능하게 하며, 이는 설계가 올바르면 안전하게, 올바르지 않으면 안전하지 않게 실패하는 새로운 방식이다.

## 개념

### 활동, 워크플로우 및 재생

- **워크플로우**: 결정적 오케스트레이션 코드. 활동의 순서, 분기, 대기를 정의한다. 이벤트 로그에서 놀라운 발산 없이 재생될 수 있도록 결정적이어야 한다.
- **활동**: 비결정적이고, 잠재적으로 실패하는 작업 단위. LLM 호출, 도구 호출, 파일 쓰기, HTTP 요청. 각 활동은 입력과 (완료되면) 출력과 함께 로깅된다.
- **이벤트 로그**: 지속적 백업 저장소. 모든 활동 시작, 완료, 실패, 재시도 및 모든 워크플로우 결정이 기록된다.
- **재생**: 복구 시, 워크플로우 코드가 처음부터 다시 실행된다; 이미 완료된 모든 활동은 재실행 없이 로깅된 결과를 반환한다. 완료되지 않은 활동만 실제로 실행된다.

이는 React가 가상 DOM에 대해 리렌더링하는 것, 또는 Git이 커밋에서 작업 트리를 재구축하는 것과 동일한 형태다. 오케스트레이터의 결정론이 지속성을 저렴하게 만드는 것이다.

### LLM 호출이 패턴에 맞는 이유

LLM 호출은:
- 비결정적이다(온도 > 0; 온도 0도 모델 버전에 따라 표류).
- 비용이 많이 든다(돈과 지연 시간).
- 잠재적으로 실패한다(비율 제한, 시간 초과).
- 부작용이 있다(도구를 호출하는 경우).

이는 정확히 활동 프로필이다. 모든 LLM 호출을 활동으로 감싸면 지수 백오프가 있는 재시도, 재시작 간 체크포인트, 디버깅을 위한 재생 가능한 추적을 제공한다.

### `thread_id`로 키가 지정된 체크포인트

LangGraph, Microsoft Agent Framework, Cloudflare Durable Objects 및 Claude Code Routines는 모두 동일한 API 형태로 수렴되었다: `thread_id`(또는 동등한 것)가 세션을 식별하고; 각 상태 전환은 백엔드(PostgreSQL 기본값, 개발용 SQLite, 캐시용 Redis)에 유지되고; 재개는 최신 체크포인트를 읽는다.

백엔드 선택이 중요하다:

- **PostgreSQL**: 지속적, 쿼리 가능, 배포에서 살아남음. LangGraph의 기본값.
- **SQLite**: 로컬 개발 전용; 호스트 간 데이터 손실.
- **Redis**: 빠르지만 AOF/스냅샷이 구성되지 않으면 일시적.
- **Cloudflare Durable Objects**: 투명하게 분산; 고유 키로 범위 지정; 몇 시간에서 몇 주 동안 지속.

### 인간 입력을 일급 상태로

제안-후-커밋(레슨 15)은 지속적인 "인간 대기 중" 상태가 필요하다. 워크플로우가 일시 중지되고, 외부 큐가 보류 중인 요청을 보유하며, 승인이 정확히 그 지점에서 재개된다. 지속성 없이는 최선의 노력에 불과하다; 지속성이 있으면, 야간 승인이 도착하고 워크플로우가 아침에 이어받는다.

### 35분 저하

METR은 측정된 모든 에이전트 클래스가 약 35분 이상의 연속 운영 후 신뢰도 감소를 보인다는 것을 관찰했다. 작업 기간을 두 배로 늘리면 실패율이 대략 4배가 된다. 지속적 실행은 이를 수정하지 않는다; 신뢰도 프로필이 지원하는 것보다 더 오래 실행할 수 있게 할 뿐이다. 안전한 패턴은 지속성을 재진입 시 새로운 HITL이 필요한 체크포인트 및 벽시계 시간에 관계없이 총 컴퓨팅을 제한하는 예산 킬 스위치(레슨 13)와 결합하는 것이다.

### 지속적 실행이 잘못된 답인 경우

- 인간 입력 없이 몇 분 미만의 짧은 실행. 오버헤드 > 이점.
- 엄격히 읽기 전용 정보 검색.
- 정확성을 위해 하나의 컨텍스트 윈도우 내 종단간 처리가 필요한 작업(일부 추론 작업, 일부 원샷 생성).

## 사용하기

`code/main.py`는 stdlib Python으로 최소 지속적 실행 엔진을 구현한다. 지원:

- `@activity` 데코레이터가 입력과 출력을 JSON 이벤트 로그에 기록.
- 활동을 순서화하는 워크플로우 함수.
- 완료된 활동을 재실행하지 않고 재생하는 `run_or_replay(workflow, event_log)` 함수.

드라이버는 3-활동 워크플로우를 시뮬레이션하고, 중간에 충돌하며, (a) 모든 것을 재실행하는 순진한 재시도와 (b) 누락된 활동만 실행하는 재생을 보여준다.

## 출시하기

`outputs/skill-durable-execution-review.md`는 제안된 장기 실행 에이전트 배포를 올바른 지속적 실행 형태(활동, 결정론, 체크포인트 백엔드, 인간 입력 상태, 재개 시 HITL 정책)에 대해 검토한다.

## 연습문제

1. `code/main.py`를 실행하라. 순진한 재시도와 재생 간의 활동 실행 횟수 차이를 관찰하라. 충돌 지점을 변경하고 재생 횟수가 그에 따라 변하는지 보여라.

2. 장난감 엔진이 `thread_id`를 명시적으로 사용하도록 변환하라. 엔진을 공유하는 두 개의 동시 세션을 시뮬레이션하고 이벤트 로그가 충돌하지 않는지 확인하라.

3. 장난감 엔진에서 하나의 활동을 가져와라. 비결정론(워크플로우 결정 내부의 벽시계 타임스탬프)을 도입하라. 재생 시 발산을 보여라. 실제 엔진이 이를 어떻게 처리하는지 설명하라(부작용 등록, `Workflow.now()` API).

4. LangChain의 "프로덕션 딥 에이전트 뒤의 런타임" 게시물을 읽어라. 런타임이 유지하는 모든 상태를 나열하고 각각이 어떤 실패 모드를 다루는지 말하라.

5. 6시간 자율 코딩 작업에 대한 체크포인트 정책을 설계하라. 어디에서 체크포인트를 만드는가? 충돌 시 재개는 어떻게 보이는가? 어떤 것이 새로운 HITL을 필요로 하는가?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| 워크플로우 (Workflow) | "에이전트의 스크립트" | 결정적 오케스트레이션 코드; 이벤트 로그에서 재생 가능 |
| 활동 (Activity) | "한 단계" | 비결정적 단위(LLM 호출, 도구 호출); 전후 로깅됨 |
| 이벤트 로그 (Event log) | "백업 저장소" | 모든 상태 전환의 지속적 기록 |
| 재생 (Replay) | "재개" | 워크플로우 재실행; 완료된 활동은 재실행 없이 로깅된 결과 반환 |
| 체크포인트 (Checkpoint) | "저장 지점" | thread_id로 키가 지정된 유지된 상태; 재개 시 최신 승리 |
| thread_id | "세션 키" | 지속적 상태의 범위를 지정하는 식별자 |
| 35분 저하 (35-minute degradation) | "신뢰도 감소" | METR: 성공률이 지평에 따라 ~2차 함수적으로 감소 |
| 비결정론 (Non-determinism) | "재생 시 표류" | 벽시계, 난수, LLM 출력; 부작용으로 등록되어야 함 |
