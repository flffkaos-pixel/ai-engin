# 인간-인-더-루프: 제안-후-커밋

> 2026년 HITL에 대한 합의는 구체적이다. "에이전트가 묻고, 사용자가 승인을 클릭"하는 것이 아니다. 제안-후-커밋이다: 제안된 작업이 멱등성 키와 함께 지속적 저장소에 유지되고, 의도, 데이터 계보, 접근된 권한, 폭발 반경 및 롤백 계획과 함께 검토자에게 표시되며, 긍정적 확인 후에만 커밋되고, 부작용이 실제로 발생했는지 확인하기 위해 실행 후 검증된다. LangGraph의 `interrupt()` + PostgreSQL 체크포인팅, Microsoft Agent Framework의 `RequestInfoEvent`, Cloudflare의 `waitForApproval()` 모두 동일한 형태를 구현한다. 표준적인 실패 모드는 도장 찍기 승인이다: "승인하시겠습니까?"가 검토 없이 클릭된다. 문서화된 완화책은 명시적 체크리스트가 있는 도전-및-응답이다.

**Type:** 학습
**Languages:** Python (stdlib, propose-then-commit state machine with idempotency)
**Prerequisites:** Phase 15 · 12 (지속적 실행), Phase 15 · 14 (트립와이어)
**Time:** ~60분

## 문제

에이전트가 작업을 수행한다. 사용자는 결정해야 한다: 승인 또는 거부. 결정이 즉각적이라면, 아마 검토가 아니다. 결정이 구조화되어 있다면, 느리지만 신뢰할 수 있다. 엔지니어링 질문은 구조화된 검토를 최소 저항 경로로 만드는 방법이다.

2023년 시대의 HITL 패턴은 동기식 프롬프트였다: "에이전트가 X에게 본문 Y로 이메일을 보내려고 합니다 — 승인하시겠습니까?" 사용자가 승인을 클릭한다. 모두가 시스템이 안전하다고 느낀다. 실제로 이 표면은 심하게 도장 찍힌다: 사용자는 빠르게 승인하고, 승인은 거의 예측하지 못하며, 에이전트가 잘못될 때 감사 추적은 사용자가 기억하지 못하는 오랜 승인 내역을 보여준다.

2026년 패턴 — 제안-후-커밋 — 은 HITL을 지속적 기반으로 옮기고, 구조화된 메타데이터를 첨부하며, 긍정적 커밋을 요구한다. 모든 관리형 에이전트 SDK가 버전을 제공한다: LangGraph `interrupt()`, Microsoft Agent Framework `RequestInfoEvent`, Cloudflare `waitForApproval()`. API 이름은 다르지만 형태는 동일하다.

## 개념

### 제안-후-커밋 상태 머신

1. **제안.** 에이전트가 제안된 작업을 생성한다. 지속적 저장소(PostgreSQL, Redis, Durable Object)에 유지된다. 포함:
   - 의도 (에이전트가 이를 수행하는 이유)
   - 데이터 계보 (이 제안으로 이끈 출처)
   - 접근된 권한 (어떤 범위/파일/엔드포인트)
   - 폭발 반경 (최악의 경우는 무엇인가)
   - 롤백 계획 (커밋되면, 어떻게 되돌리는가)
   - 멱등성 키 (제안당 고유; 재제출 시 동일한 레코드 반환)
2. **표시.** 검토자가 모든 메타데이터와 함께 제안을 본다. 검토자는 사람이다(자신을 검토하는 에이전트가 아님).
3. **커밋.** 긍정적 확인. 작업이 실행된다.
4. **검증.** 실행 후, 부작용이 다시 읽혀지고 확인된다. 검증 단계가 실패하면, 시스템은 알려진 나쁜 상태에 있으며 경보가 작동한다.

### 멱등성 키

멱등성 키가 없으면, 일시적 실패 후 재시도가 이미 승인된 작업을 이중 실행할 수 있다. 구체적 예: 사용자가 "A에서 B로 $100 이체"를 승인한다. 네트워크가 끊긴다. 워크플로우가 재시도한다. 사용자는 한 번 승인했지만 이체가 두 번 실행된다. 멱등성 키는 승인을 단일 고유 부작용에 묶는다; 두 번째 실행은 무효하다.

이는 Stripe와 AWS API가 사용하는 것과 동일한 멱등성 패턴이다. 에이전트 승인에 재사용하는 것은 Microsoft Agent Framework 문서에 명시되어 있다.

### 지속성: 승인이 프로세스를 넘어 지속되는 이유

승인 대기실은 에이전트가 소유하지 않은 상태 조각이다. 워크플로우가 일시 중지된다(레슨 12). 승인이 도착하면, 워크플로우가 정확히 그 지점에서 재개된다. 이것이 LangGraph가 `interrupt()`를 인메모리 상태가 아닌 PostgreSQL 체크포인팅과 짝짓는 이유다 — 이틀 후의 승인이 여전히 워크플로우를 온전하게 찾는다.

### 도장 찍기 승인 및 도전-및-응답 완화책

HITL의 기본 UI("승인"/"거부" 버튼)는 진정한 검토 없이 빠른 승인을 생성한다. 문서화된 완화책: 승인 버튼이 활성화되기 전에 특정 질문에 대한 긍정적 답변을 요구하는 도전-및-응답 체크리스트. 구체적 형태:

- "이 작업이 어떤 리소스에 닿는지 이해하고 있습니까? [ ]"
- "폭발 반경이 수용 가능함을 확인했습니까? [ ]"
- "이것이 실패할 경우 롤백 계획이 있습니까? [ ]"

자체를 위한 관료주의가 아니다 — 강제 함수다. 상자를 체크할 수 없는 검토자는 설명을 요청하거나(상향) 거절한다(안전 기본값). Anthropic 에이전트 안전 연구는 도장 찍기 승인 패턴에 대한 완화책으로 체크리스트 기반 HITL을 명시적으로 인용한다.

### 결과적인 것으로 간주되는 것

모든 작업에 제안-후-커밋이 필요한 것은 아니다. 2026년 지침:

- **결과적 작업** (항상 HITL): 되돌릴 수 없는 쓰기, 금융 거래, 외부 통신, 프로덕션 데이터베이스 변경, 파괴적 파일 시스템 작업.
- **되돌릴 수 있는 작업** (때때로 HITL): 로컬 파일 편집, 스테이징 환경 변경, 명확한 롤백이 있는 되돌릴 수 있는 쓰기.
- **읽기 및 검사** (절대 HITL): 파일 읽기, 리소스 나열, 읽기 전용 API 호출.

### 사후 작업 검증

"커밋이 실행되었다"는 "부작용이 발생했다"와 같지 않다. 네트워크 파티션 및 경쟁 조건은 백엔드가 유지하지 않았는데 성공했다고 생각하는 워크플로우를 생성할 수 있다. 검증 단계는 커밋 후 대상 리소스를 다시 읽어서 확인한다. 이는 `RETURNING` 절이 있는 데이터베이스 트랜잭션 또는 `PutObject` 후 AWS `GetObject`와 동일한 패턴이다.

### EU AI Act 제14조

제14조는 고위험 AI 시스템에 대한 효과적인 인간 감독을 EU에서 의무화한다. "효과적"은 장식적이지 않다. 규제 언어는 특히 도장 찍기 패턴을 배제한다. 제안-후-커밋과 도전-및-응답은 Microsoft Agent Governance Toolkit 준수 문서에서 제14조 심사를 통과하는 형태다.

## 사용하기

`code/main.py`는 stdlib Python으로 제안-후-커밋 상태 머신을 구현한다. 지속적 저장소는 JSON 파일이다. 멱등성 키는 (thread_id, action_signature)의 해시다. 드라이버는 세 가지 사례를 시뮬레이션한다: 깨끗한 승인 흐름, 일시적 실패 후 재시도(이중 실행 안 됨), 도장 찍기 기본값 대 도전-및-응답 흐름.

## 출시하기

`outputs/skill-hitl-design.md`는 제안된 HITL 워크플로우를 제안-후-커밋 형태에 대해 검토하고 누락된 메타데이터, 멱등성, 검증 또는 도전-및-응답 계층을 플래그한다.

## 연습문제

1. `code/main.py`를 실행하라. 승인된 제안의 재시도가 지속적 레코드를 사용하고 재실행되지 않는지 확인하라. 이제 멱등성 키에 타임스탬프를 포함하도록 변경하고 재시도가 이중 실행되는 것을 보여라.

2. 제안 레코드에 `rollback` 필드를 추가하라. 검증 단계가 실패하는 실행을 시뮬레이션하라. 롤백이 자동으로 발사되는 것을 보여라.

3. Microsoft Agent Framework의 `RequestInfoEvent` 문서를 읽어라. API가 포함하고 장난감 엔진이 누락한 하나의 메타데이터 필드를 식별하라. 추가하고 무엇을 보호하는지 설명하라.

4. 특정 작업(예: "공개 Twitter 계정에 게시")에 대한 도전-및-응답 체크리스트를 설계하라. 검토자가 답해야 할 세 가지 질문은 무엇인가? 왜 그 세 가지인가?

5. 동기식 "승인하시겠습니까?" 프롬프트로 충분할 하나의 사례(지속적 저장소 불필요)를 골라라. 이유를 설명하고, 수용하는 위험 클래스를 말하라.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| 제안-후-커밋 (Propose-then-commit) | "2단계 승인" | 유지된 제안 + 긍정적 커밋 + 검증 |
| 멱등성 키 (Idempotency key) | "재시도 안전 토큰" | 제안당 고유; 두 번째 실행은 무효 |
| 데이터 계보 (Data lineage) | "어디서 왔는가" | 제안으로 이끈 특정 출처 콘텐츠 |
| 폭발 반경 (Blast radius) | "최악의 경우" | 작업이 잘못될 경우 영향 범위 |
| 도장 찍기 (Rubber-stamp) | "빠른 승인" | 진정한 검토 없이 "승인" 클릭 |
| 도전-및-응답 (Challenge-and-response) | "강제 체크리스트" | 검토자가 특정 질문에 긍정적으로 확인해야 함 |
| RequestInfoEvent | "MS Agent Framework 기본 요소" | 구조화된 메타데이터가 있는 지속적 HITL 요청 |
| `interrupt()` / `waitForApproval()` | "프레임워크 기본 요소" | 동일한 형태의 LangGraph / Cloudflare 버전 |
