# 체크포인트 및 롤백

> 모든 그래프 상태 전환이 유지된다. 작업자가 충돌하면, 임대가 만료되고 다른 작업자가 최신 체크포인트에서 이어받는다. Cloudflare Durable Objects는 몇 시간 또는 몇 주 동안 상태를 유지한다. 제안-후-커밋(레슨 15)은 작업당 롤백 계획을 정의한다. 사후 작업 검증이 루프를 닫는다. EU AI Act 제14조는 고위험 시스템에 대해 효과적인 인간 감독을 의무화한다 — 실제로 이는 체크포인트가 쿼리 가능해야 하고, 롤백이 리허설되어야 하며, 감사 추적이 배포를 넘어 생존해야 함을 의미한다. 날카로운 실패 모드: 멱등성 키와 사전 조건 검사가 없으면, 일시적 실패 후 재시도가 이미 승인된 작업을 이중 실행할 수 있다. 사후 작업 검증이 이것을 잡아낸다.

**Type:** 학습
**Languages:** Python (stdlib, checkpoint and rollback state machine)
**Prerequisites:** Phase 15 · 12 (지속적 실행), Phase 15 · 15 (제안-후-커밋)
**Time:** ~60분

## 문제

지속적 실행(레슨 12)은 충돌한 에이전트를 재개 가능하게 만든다. 제안-후-커밋(레슨 15)은 승인된 작업을 감사 가능하게 만든다. 이 레슨은 이 둘을 결합한다: 승인된 작업이 부분적으로 실행되고, 충돌하며, 재개될 때 무슨 일이 일어나는가? 롤백은 언제, 어떤 상태에 대해 실행되는가?

실제 시스템은 이를 다르게 연결한다:

- **LangGraph**는 모든 그래프 상태 전환을 PostgreSQL에 체크포인트한다. 작업자 충돌 시, 임대가 해제되고 다른 작업자가 최신 체크포인트에서 재개한다. 워크플로우는 `interrupt()`에서 일시 중지되며, 이 자체도 유지된다.
- **Cloudflare Durable Objects**는 몇 시간 또는 몇 주 동안 키별 상태를 유지한다. 승인된 작업에 대한 저장소와 함께 계산을 공동 배치한다.
- **Microsoft Agent Framework**는 워크플로우 API에서 `Checkpoint` 기본 요소를 노출한다; 재생과 멱등성이 재시도를 다룬다.

모든 경우에서, 실제로 작동하는 조합은: 멱등성 키(이중 실행 방지) + 사전 조건 검사(상태가 여전히 승인된 것과 일치) + 사후 작업 검증(부작용이 실제로 발생) + 검증 실패 시 롤백.

## 개념

### 모든 전환이 유지된다

그래프 상태 전환은 워크플로우를 하나의 명명된 상태에서 다른 상태로 이동시키는 모든 단계다. 순진한 구현은 특정 커밋 지점에서만 유지한다; 프로덕션 구현은 모든 전환을 유지한다. 비용(몇 번의 추가 쓰기)은 신뢰도 이득(재생이 어디든 착륙, 임대 복구가 정확)에 비해 작다.

### 임대 복구

작업자가 충돌하면, 워크플로우가 손실되지 않는다; 임대(이 작업자가 이 실행을 실행 중이라는 단기 주장)가 만료될 뿐이다. 다른 작업자가 최신 체크포인트를 선택하고 재개한다. 임대 메커니즘은 프로덕션 시스템이 롤링 배포에서 진행 중인 작업을 잃지 않고 생존할 수 있게 하는 것이다.

### 멱등성 + 사전 조건

멱등성만으로는 충분하지 않다. 고려: 워크플로우가 "잔액 > $1000일 때 A에서 B로 $100 이체"를 승인받았다. 워크플로우가 커밋되고, 실행 중간에 충돌하며, 재개된다. 멱등성 키만 확인되면, 이체는 한 번 실행된다(올바름). 하지만 충돌과 재개 사이에 A의 잔액이 다른 워크플로우를 통해 $500로 떨어진 경우를 고려하라. 멱등성 검사는 여전히 통과한다; 사전 조건은 통과하지 않는다. 사전 조건 검사 없이, 초과 인출을 출시한다.

모든 결과적 작업에는 둘 다 필요하다:

- **멱등성 키**: 이중 실행 방지.
- **사전 조건 검사**: 상태가 여전히 승인된 것과 일치하는지 확인.

### 사후 작업 검증

"도구가 200을 반환했다"는 검증이 아니다. 실제 검증은 대상 상태를 다시 읽고 부작용이 실제로 발생했는지 확인한다. 패턴:

- 데이터베이스 업데이트: `UPDATE ... RETURNING *` 후 반환된 행이 의도된 상태와 일치하는지 확인.
- 이메일 전송: 제출 후 보낸 편지함에서 메시지 ID 확인.
- 파일 쓰기: 파일을 다시 읽고 해시.
- API 호출: 대상 리소스에 대한 후속 `GET`.

검증이 실패하면, 워크플로우는 알려진 나쁜 상태에 있다. 롤백이 작동한다.

### 롤백 계획

제안-후-커밋(레슨 15)의 모든 결과적 작업에는 롤백 계획이 있다. 유형:

- **인밴드 롤백**: 부작용을 직접 되돌림(`INSERT` 후 `DELETE`, 전송 후 `Send-correction-email`).
- **보상 트랜잭션**: 원래 작업을 무력화하는 새 작업(표준 SAGA 패턴).
- **아웃오브밴드 롤백**: 인간에게 경고, 워크플로우 일시 중지, 조사를 위해 나쁜 상태 유지.

무효 롤백("되돌릴 수 없음")은 제안에 명명되어야 한다. 롤백이 없는 작업은 커밋 시 더 강력한 HITL이 필요하다(레슨 15 도전-및-응답).

### EU AI Act 제14조 운영적 해석

제14조는 고위험 시스템에 대해 "효과적인 인간 감독"을 요구한다. 운영적 용어로, 구현자는 다음과 같이 읽는다:

- 체크포인트는 감사자가 쿼리 가능해야 한다.
- 롤백은 리허설되어야 한다(최소 한 번 종단간 테스트).
- 감사 추적은 배포를 넘어 생존해야 한다(체크포인트 백엔드는 일시적이지 않음).
- 실패한 검증은 조용히 로깅되지 않고 경보가 발생해야 한다.

커밋 중간에 충돌하고, 재개하며, 검증 + 롤백 경로 없이 부작용을 완료하는 워크플로우는 제14조 테스트를 통과하지 못한다.

### 날카로운 실패 모드: 이중 실행

이 공간에서 가장 흔한 프로덕션 사고:

1. 작업 승인, 멱등성 키 k.
2. 커밋 시작, 실행, 200 반환.
3. "커밋됨" 상태를 유지하기 전에 워크플로우 충돌.
4. 워크플로우 재개; "승인되었지만 커밋되지 않음"을 보고 재실행.
5. 부작용이 두 번 발생.

완화책: 실행 전에 "진행 중" 의도를 유지하고, 멱등성 키로 실행한 다음, 사후 작업 검증 성공 후에만 "커밋됨"으로 표시. 작업이 발사되고 상태 쓰기가 실패하면, 검증하고 (필요시) 재발사. 상태 쓰기가 성공하고 작업이 실패하면, 검증하고 복구 경로를 통해 정확히 한 번 발사.

## 사용하기

`code/main.py`는 멱등성, 사전 조건, 검증 및 롤백이 있는 체크포인트된 워크플로우를 구현한다. 드라이버는 네 가지 시나리오를 시뮬레이션한다: 깨끗한 실행, 충돌 후 재시도(멱등성이 잡음), 사전 조건 실패(워크플로우가 발사 없이 중단), 검증 실패(롤백 발사).

## 출시하기

`outputs/skill-rollback-rehearsal.md`는 제안된 워크플로우에 대한 롤백 리허설 테스트를 설계하고 감사 추적 지속성에 대해 체크포인트 백엔드를 감사한다.

## 연습문제

1. `code/main.py`를 실행하라. 네 가지 시나리오를 확인하라. 커밋 중 충돌 사례에 대해 작업이 재시도 간에 정확히 한 번 실행되는지 확인하라.

2. "먼저 완료로 표시한 다음 수행" 패턴을 상태 쓰기가 작업 후에 실행되도록 수정하라. 충돌 시나리오를 다시 실행하라. 얼마나 많은 중복 작업이 발사되는지 측정하라.

3. 특정 프로덕션 작업(예: "Slack 채널에 게시")에 대한 롤백 계획을 설계하라. 인밴드, 보상 또는 아웃오브밴드로 분류하라. 선택을 정당화하라.

4. 아는 하나의 워크플로우를 가져와라. 모든 상태 전환을 식별하라. 각각을 지속성 요구 사항(유지/유지하지 않음)으로 표시하라. 현재 유지하지 않는 것을 세어보라.

5. 리허설된 롤백 테스트: 실제 워크플로우를 실행하고, 충돌시키며, 롤백 경로가 발사되는지 확인하는 종단간 테스트를 설계하라. 테스트가 무엇을 단언하는가?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| 체크포인트 (Checkpoint) | "저장 지점" | 모든 그래프 상태 전환이 지속적 저장소에 유지됨 |
| 임대 (Lease) | "작업자 주장" | 작업자가 실행을 실행 중이라는 단기 주장; 충돌 시 만료 |
| 사전 조건 (Precondition) | "상태 게이트" | 상태가 여전히 승인된 작업과 일치하는지 단언 |
| 사후 작업 검증 (Post-action verify) | "재읽기 확인" | 대상 시스템에서 부작용이 실제로 발생했는지 확인 |
| 인밴드 롤백 (In-band rollback) | "직접 실행 취소" | 역연산으로 부작용 되돌리기 |
| 보상 트랜잭션 (Compensating transaction) | "SAGA 실행 취소" | 원본을 무력화하는 새 작업 |
| 먼저-완료-표시 (Mark-as-done-first) | "상태 쓰기 순서" | 커밋에서 반환되기 전에 커밋된 상태 유지 |
| 제14조 (Article 14) | "EU AI Act 인간 감독" | 운영적: 쿼리 가능한 체크포인트, 리허설된 롤백, 감사 가능한 추적 |
