# 비동기 및 Hogwild! 추론

> 추측적 디코딩(10단계 15과)은 단일 시퀀스 내에서 토큰을 병렬화합니다. 다중 에이전트 프레임워크는 전체 시퀀스에 걸쳐 병렬화하지만 명시적 조정(투표, 하위-작업 분할)을 강제합니다. Hogwild! 추론 (Rodionov et al., arXiv:2504.06261)은 다른 것을 수행합니다: 동일한 LLM의 N개 인스턴스를 공유 키-값 캐시에 대해 병렬로 실행합니다. 각 워커는 다른 모든 워커가 생성한 토큰을 즉시 봅니다. 현대 추론 모델(QwQ, DeepSeek-R1)은 미세 조정 없이 공유 캐시를 통해 자기 조정할 수 있습니다. 이 접근법은 실험적이지만, 추측적 디코딩과 직교하는 완전히 새로운 추론 병렬화 축을 엽니다. 이 과는 stdlib Python으로 2-워커 Hogwild! 시뮬레이터를 구현하고 공유-캐시 협력이 기존 모델의 추론 능력에서 어떻게 발생하는지 설명합니다.

**유형:** 구축
**언어:** Python (stdlib)
**사전 필요과목:** 10단계 12과 (추론 최적화), 10단계 15과 (추측적 디코딩)
**시간:** ~60분

## 학습 목표

- 세 가지 일반적인 병렬-LLM 토폴로지(투표, 하위-작업, Hogwild!)를 설명하고 각각이 어떤 문제를 대상으로 하는지 명명할 수 있다
- 핵심 Hogwild! 설정(여러 워커, 하나의 공유 KV 캐시, 자기-프롬프팅을 통한 창발적 조정)을 설명할 수 있다
- 워커 수 `N`, 작업-수준 병렬화 `p`, 조정 오버헤드 `c`의 함수로 Hogwild!의 벽시계 속도 향상을 계산할 수 있다
- 장난감 문제에서 2-워커 Hogwild! 시뮬레이터를 구현하고 창발적 작업 분할을 관찰할 수 있다

## 문제

현대 LLM은 긴 추론 사슬을 생성하여 어려운 문제를 해결합니다 — 5000 토큰의 단계별 로직은 흔하고, 수만 토큰은 어려운 수학 문제에서 발생합니다. 70B 모델에서 초당 35토큰 디코드 속도로 50k 토큰은 24분입니다. 대화형이라고 할 수 없습니다.

추측적 디코딩(10단계 15과)은 단일 시퀀스 내에서 병렬화하여 3-5배 속도 향상을 얻습니다. 그 이상으로 자기회귀 디코딩의 순차적 의존성이 단단한 상한선입니다. 각 새 토큰은 모든 이전 토큰에 의존합니다.

명백한 질문: 시퀀스 전체에 걸쳐 병렬화할 수 있을까? 동일한 모델의 여러 복사본을 동일한 문제에 대해 실행하고, 협력하게 하고, 작업을 분할하게 할 수 있을까?

이전 연구: 투표 앙상블(N개 모델 실행, 다수결 답변 선택), 생각의-트리(추론 경로 분기 및 재결합), 다중-에이전트 프레임워크(각 에이전트에 하위-작업 할당, 조정자 사용). 이들은 모두 특정 작업 영역에서 도움이 됩니다. 모두 명시적 조정 메커니즘(투표 규칙, 분기-및-가지치기 로직, 에이전트-간 메시징 프로토콜)도 도입합니다.

Hogwild! 추론은 다른 접근법을 취합니다. N개의 워커가 단일 KV 캐시를 공유합니다. 각 워커는 다른 모든 워커가 생성한 토큰을 자신의 컨텍스트인 것처럼 즉시 봅니다. 워커들은 — 어떤 학습이나 미세 조정 없이 — 작업을 분할하는 방법을 알아냅니다. 현대 추론 모델(QwQ, DeepSeek-R1, Claude-패밀리 추론 모드)은 공유 캐시를 읽고 "워커 2가 이미 기본 케이스를 처리했으니, 귀납적 단계를 작업하겠다"와 같은 말을 할 수 있습니다.

속도 향상은 워크로드 의존적이며 2026년 4월 기준으로 실험적입니다. 하지만 아이디어는 새로운 추론 병렬화 축을 열기 때문에 알아둘 가치가 있습니다.

## 개념

### 설정

N개의 워커 프로세스를 초기화하고, 모두 동일한 LLM을 실행합니다. 워커별 KV 캐시 대신 하나의 공유 캐시를 유지합니다. 워커 `i`가 토큰 `t_j`를 생성하면, 토큰은 공유 캐시의 다음 위치에 기록됩니다. 워커 `k`가 다음 단계를 수행할 때, 지금까지 모든 N개 워커가 생성한 모든 것을 포함하는 캐시의 현재 상태를 읽습니다.

단계 시간에 워커들은 토큰을 쓰기 위해 경쟁합니다. 워커별 위치 인덱스는 없습니다 — 캐시는 단일 증가 시퀀스입니다. 순서는 쓰기 도착 시간에 의해 결정됩니다.

### 조정이 발생하는 이유

워커들은 프롬프트를 공유합니다. 일반적으로 "당신은 이 문제에 함께 작업하는 N개 인스턴스 중 하나입니다. 각 인스턴스는 공유 메모리를 읽고 다른 인스턴스가 쓴 내용을 볼 수 있습니다. 중복 작업을 피하십시오." 프롬프트와 공유 캐시만으로 충분합니다. 추론 모델은 캐시를 읽고, 문제의 어떤 부분이 이미 시도되었는지 알아차리고, (항상은 아니지만 종종) 탐색되지 않은 부분으로 전환합니다.

Hogwild! 논문(Rodionov et al., 2025)은 다음과 같은 관찰을 보고합니다:

- 워커들이 계획을 수립하고 캐시를 통해 다른 워커에게 전달합니다.
- 워커들이 다른 워커의 추론에서 오류를 발견하고 지적합니다.
- 워커들이 계획이 실패할 때 적응하고 대안을 제안합니다.
- 중복을 확인하라는 프롬프트가 주어지면, 워커들이 이를 감지하고 전환합니다.

이 중 어느 것도 미세 조정을 필요로 하지 않습니다. 창발적 행동은 모델이 이미 가진 추론 능력에서 비롯됩니다.

### 이름의 유래

논문의 이름은 비동기 업데이트 최적화 도구인 Hogwild! SGD (Recht et al., 2011)에서 따왔습니다. 유사점: SGD의 비동기 워커들은 모두 공유 파라미터 벡터에 씁니다; Hogwild! 추론의 워커들은 모두 공유 KV 캐시에 씁니다. 둘 다 동기화 보장보다 경험적 수렴에 의존합니다.

### RoPE가 이를 가능하게 함

Rotary Position Embedding (RoPE, Su et al. 2021)은 Q와 K 벡터의 회전을 통해 위치 정보를 인코딩합니다. 위치가 회전이고 내장된 오프셋이 아니기 때문에, KV 캐시 항목을 다시 계산하지 않고 토큰의 위치가 이동할 수 있습니다. 워커 `i`가 위치 `p`에 공유 캐시에 쓸 때, 그 위치를 읽는 다른 워커들은 캐시된 항목을 직접 사용할 수 있습니다 — 재회전이 필요 없습니다.

학습된-위치 또는 절대-위치 모델에서 Hogwild!는 동시 쓰기마다 캐시 무효화가 필요합니다. RoPE는 캐시를 안정적으로 유지합니다.

### 벽시계 시간 수학

`T_serial`을 한 워커가 혼자 문제를 해결하는 시간이라고 하겠습니다. `p`를 작업-수준 병렬화 가능 비율이라고 하겠습니다. `c`를 단계당 조정 오버헤드(확장된 캐시 읽기, 무엇을 쓸지 결정)라고 하겠습니다.

단일-워커 시간: `T_serial`.
N-워커 Hogwild! 시간, 조정이 무료인 경우: `T_serial * ((1 - p) + p / N)`. 고전적인 Amdahl.
조정 오버헤드 포함: `T_serial * ((1 - p) + p / N) + c * steps_per_worker`.

워커가 생산적이려면 `c`가 단계당 디코드 시간에 비해 작아야 합니다. 5k+ 토큰을 생성하는 추론 모델에서 워커들은 수백 토큰의 조정 오버헤드를 감당하고도 앞설 수 있습니다. 짧은 채팅 작업에서는 조정이 지배적이며 Hogwild!는 직렬보다 나쁩니다.

### 구체적 예

추론 문제: 10k 토큰의 사고-사슬. 문제가 `p = 0.7`의 병렬화 가능 내용(다른 증명 전략, 다른 사례 분석)과 워커당 `c = 200` 토큰의 조정 오버헤드를 가진다고 가정합니다. `N = 4` 워커:

- 직렬 시간: 10000 디코드 단계.
- Hogwild! 시간: 10000 * (0.3 + 0.7 / 4) + 200 * 4 = 10000 * 0.475 + 800 = 5550 디코드 단계.
- 속도 향상: 10000 / 5550 = 1.8배.

이것은 적당합니다. 하지만 더 긴 추론 문제(50k 토큰)에서는 조정 오버헤드가 상각되고 속도 향상이 2.5-3배로 올라갑니다. Hogwild!는 자연스럽게 멀티스레드 코드를 작성할 수 있는 언어에서의 스레드-수준 병렬 처리의 추론 등가물입니다.

### Hogwild!를 사용해야 할 때

- 독립적인 하위-목표에 걸쳐 병렬화될 수 있는 긴 추론 문제(수천 토큰).
- 단계별로 생각하도록 학습된 추론 모델. 비-추론 모델은 자기 조정을 잘하지 못합니다.
- 공유 캐시와 N개의 워커 프로세스를 담을 충분한 VRAM이 있는 단일-노드 배포. 캐시는 공유되지만 각 워커는 자신의 활성화 메모리를 가집니다.

### 사용하지 말아야 할 때

- 짧은 대화형 채팅. 조정 오버헤드가 지배적입니다.
- 병렬화되지 않는 작업(단일 선형 증명, 단일 컴파일). N=1이 최대입니다.
- 비-추론 모델. 조정이 발생하지 않습니다.
- 다중-노드 배포. 공유 캐시는 매우 빠른 교차-워커 동기화가 필요합니다. 노드 내는 괜찮지만, 노드 간은 지연 시간 재앙입니다.

### 실험적 상태

2026년 4월 기준으로 Hogwild!는 오픈소스 PyTorch 구현을 가진 연구 방법입니다. 프로덕션 채택은 이루어지지 않았습니다. 세 가지 장애물:

1. 동시 프로세스 간 공유 KV 캐시 관리는 사소한 엔지니어링이 아닙니다.
2. 창발적 조정은 작업 의존적입니다; 벤치마크가 아직 구축 중입니다.
3. 속도 향상은 추측적 디코딩이 이미 제공하는 것에 비해 적당하며, 둘을 결합할 수 있지만 결합 엔지니어링은 또 다른 계층입니다.

알아둘 가치가 있습니다. 실험해볼 가치가 있습니다. 아직 제품을 걸기에는 이릅니다.

## 직접 구현하기

`code/main.py`는 장난감 Hogwild! 시뮬레이터를 구현합니다:

- 두 개의 워커 프로세스, 각각 알려진 확률로 여러 토큰 범주(작업-토큰, 관찰-토큰, 조정-토큰) 중 하나를 생성하는 결정론적 "LLM".
- 두 워커가 읽고 쓰는 공유 캐시(단순히 토큰 리스트).
- 간단한 조정 로직: 워커가 다른 워커가 이미 한 범주에 충분한 작업 토큰을 생성했음을 보면, 다른 범주를 선택합니다.

시뮬레이터는 고정된 단계 예산으로 실행되며 다음을 보고합니다:

- 총 작업-토큰 생성 수.
- 총 벽시계 시간 (워커 단계 수).
- 단일 워커 대비 유효 속도 향상.
- 어떤 워커가 어떤 토큰을 썼는지에 대한 추적.

### 1단계: 공유 캐시

두 워커가 추가하는 리스트. 실제 구현에서는 간단한 잠금(Python `threading.Lock`); 카운터로 시뮬레이션합니다.

### 2단계: 워커 루프

각 워커는 각 단계에서:

- 현재 공유 캐시를 읽습니다.
- 이미 있는 내용을 기반으로 어떤 범주의 토큰을 쓸지 결정합니다.
- 하나의 토큰을 씁니다.

### 3단계: 조정 휴리스틱

범주 X가 캐시에 이미 K개의 토큰을 가지고 있고 워커의 의도된 범주가 X이면, 워커는 범주 Y로 전환합니다. 이것은 "이것은 이미 다루어졌으니, 대신 다른 것을 하라"는 추론 모델 행동의 장난감 대체물입니다.

### 4단계: 측정된 속도 향상

동일한 총 단계 예산으로 N=1 워커와 N=2 워커로 시뮬레이터를 실행합니다. 생성된 작업-토큰을 셉니다. N=2는 조정-주도 작업 분할로 인해 대략 1.5-1.8배 더 많은 작업-토큰을 생성해야 합니다.

### 5단계: 조정 스트레스 테스트

조정 휴리스틱의 민감도를 줄입니다. 다시 실행합니다. 좋은 조정 없이 N=2가 동일한 토큰을 중복 생성하고 속도 향상이 1 미만으로 떨어지는 것을 관찰합니다. 이는 논문의 관찰과 일치합니다: 이 트릭은 워커가 자기 조정할 추론 능력을 가진 경우에만 작동합니다.

## 활용하기

2026년 4월 기준 프로덕션에서 Hogwild! 통합은 연구-급입니다. Yandex/HSE/IST의 참조 구현은 PyTorch 기반이며 DeepSeek-R1 및 QwQ 모델에서 단일-노드 다중-프로세스 설정을 대상으로 합니다.

실용적 채택 경로:

1. 추론-작업 워크로드를 프로파일링하십시오. 탐색적(여러 전략, 사례 분석, 검색) 대 선형적 토큰의 비율을 측정하십시오.
2. 탐색이 지배적이면 2-워커 Hogwild! 실험을 실행하십시오. 벽시계 시간 개선을 측정하십시오.
3. 개선이 1.3배 미만이면 조정-지배 영역에 있는 것입니다. 단일-워커로 되돌리십시오.
4. 개선이 1.5배 이상이면 N=4로 밀고 다시 측정하십시오. 수확 체감은 일반적으로 N=4-8에서 발생합니다.

추측적 디코딩과 결합: 각 Hogwild! 워커는 독립적으로 추측적 디코딩을 사용할 수 있습니다. 두 속도 향상이 (대략) 곱해져, 3배 추측적 디코딩과 1.8배 Hogwild!가 순진한 단일-워커 디코딩 대비 효과적인 5.4배가 됩니다.

## 배포하기

이 과는 `outputs/skill-parallel-inference-router.md`를 생성합니다. 추론 워크로드 프로필(토큰 예산, 작업 병렬화 프로필, 모델 패밀리, 배포 대상)이 주어지면 투표, 생각의-트리, 다중-에이전트, Hogwild!, 추측적 디코딩 전략 사이를 라우팅합니다.

## 연습 문제

1. `code/main.py`를 기본 설정으로 실행하십시오. N=2 Hogwild! 설정이 동일한 벽시계 시간에 N=1 기준선보다 더 많은 작업-토큰을 생성하는지 확인하십시오.

2. 조정 휴리스틱의 강도를 줄이십시오(`coordination_weight=0.1`). 다시 실행하십시오. 속도 향상이 붕괴됨을 보이십시오. 이유를 설명하십시오: 워커가 조정할 수 없을 때 노력을 중복합니다.

3. `p=0.8, c=500` 및 N=4 워커로 50k-토큰 추론 작업에 대한 예상 Hogwild! 속도 향상을 계산하십시오. `p=0.3, c=200` 및 N=4로 1k-토큰 채팅 작업에 대해 동일하게 수행하십시오. 왜 하나는 이득이고 다른 하나는 손실인가?

4. Hogwild! 논문의 섹션 4(예비 평가)를 읽으십시오. 저자들이 보고하는 두 가지 실패 모드를 식별하십시오. 더 나은 조정 프롬프트가 각각을 어떻게 완화할 수 있는지 설명하십시오.

5. 장난감에서 Hogwild!와 추측적 디코딩을 결합하십시오: 각 워커가 내부적으로 2-토큰 추측적 디코딩을 사용합니다. 곱셈적 속도 향상을 보고하십시오. 두 워커가 동일한 공유-캐시 프리픽스를 확장하려고 할 때 어떤 부기 문제가 발생하는가?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|-------------------|-----------|
| Hogwild! | "병렬 워커, 공유 캐시" | 하나의 공유 KV 캐시로 동시에 실행되는 동일 LLM의 N개 인스턴스; 자기-프롬프팅을 통한 창발적 조정 |
| 공유 KV 캐시 | "조정 매체" | 모든 워커가 읽고 쓰는 단일 증가 KV 버퍼; 워커 간 즉시 토큰 가시성 가능 |
| 창발적 조정 | "학습 불필요" | 추론 가능한 LLM이 미세 조정이나 명시적 프로토콜 없이 공유 캐시를 읽고 작업을 분할할 수 있음 |
| 조정 오버헤드 (c) | "방향 설정에 쓰는 토큰" | 확장된 캐시를 읽고 무엇을 할지 결정하는 워커당 비용; 총 디코드 시간 대비 작게 유지해야 함 |
| 병렬화 가능 비율 (p) | "병렬로 실행 가능한 것" | 작업-수준 병렬화: 본질적으로 순차적이지 않은 총 작업의 비율 |
| RoPE가 Hogwild!를 가능하게 함 | "회전 위치는 시프트 불변" | 위치가 회전이므로 공유 캐시에 쓰는 것이 이전 토큰의 재계산을 필요로 하지 않음 |
| 투표 앙상블 | "N개 실행, 다수결 선택" | 가장 간단한 병렬 추론 토폴로지; 분류에 유용, 긴 형식 추론에는 덜 유용 |
| 생각의 트리 | "분기 및 가지치기" | 여러 분기를 탐색하고 가지치기하는 추론 전략; 명시적 조정 로직 |
| 다중-에이전트 프레임워크 | "하위-작업 할당" | 각 에이전트가 역할을 받음; 조정자가 오케스트레이션; 무거운 프로토콜 오버헤드 |
