# 실패 모드: 에이전트가 작동을 멈추는 이유

> MASFT (버클리, 2025)는 3개 범주의 14가지 다중 에이전트 실패 모드를 분류합니다. Microsoft의 분류학은 기존 AI 실패가 에이전틱 환경에서 어떻게 증폭되는지 문서화합니다. 업계 현장 데이터는 다섯 가지 반복 모드로 수렴됩니다: 환각된 행동, 범위 확장, 계단식 오류, 컨텍스트 손실, 도구 오용.

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 05 (Self-Refine and CRITIC), Phase 14 · 24 (Observability)
**Time:** ~60분

## 학습 목표

- MASFT의 세 가지 실패 범주와 각각의 최소 네 가지 특정 모드를 명명합니다.
- 에이전틱 실패가 기존 AI 실패 모드(편향, 환각)를 증폭시키는 이유를 설명합니다.
- 업계에서 반복되는 다섯 가지 모드와 그 완화 방법을 설명합니다.
- 에이전트 트레이스에 실패 모드 레이블을 태깅하는 stdlib 탐지기를 구현합니다.

## 문제

팀은 90%의 트레이스에서 작동하는 에이전트를 출시합니다. 10%의 실패는 무작위 노이즈가 아니라 소수의 반복 범주에 속합니다. 이름을 붙일 수 있게 되면 모니터링하고 수정할 수 있습니다.

## 개념

### MASFT (버클리, arXiv:2503.13657)

다중 에이전트 시스템 실패 분류학. 3개 범주로 클러스터링된 14가지 실패 모드. 주석자 간 Cohen's Kappa 0.88 — 범주를 확실히 구분할 수 있습니다.

중심 주장: 실패는 다중 에이전트 시스템의 근본적인 설계 결함이지, 더 나은 기본 모델로 해결할 LLM 한계가 아닙니다.

### Microsoft의 에이전틱 AI 시스템 실패 모드 분류학

- 기존 AI 실패(편향, 환각, 데이터 유출)가 에이전틱 환경에서 증폭됩니다.
- 자율성에서 새로운 실패가 발생합니다: 규모에 따른 의도치 않은 행동, 도구 오용, 임무 이탈.
- 백서는 에이전틱 제품의 위험 등록부입니다.

### 에이전틱 AI의 결함 특성화 (arXiv:2603.06847)

- 오케스트레이션, 내부 상태 진화 및 환경 상호작용에서 실패가 발생합니다.
- 단순히 "잘못된 코드"나 "잘못된 모델 출력"이 아닙니다.

### LLM 에이전트 환각 조사 (arXiv:2509.18970)

두 가지 주요 표현:

1. **지시 따르기 이탈** — 에이전트가 시스템 프롬프트를 따르지 않음.
2. **장거리 컨텍스트 오용** — 에이전트가 이전 턴의 컨텍스트를 잊거나 잘못 적용함.

하위 의도 오류: 생략(단계 누락), 중복(단계 반복), 무질서(단계 순서 오류).

### 업계에서 반복되는 다섯 가지 모드

Arize, Galileo, NimbleBrain 2024-2026 현장 분석이 수렴하는 바:

1. **환각된 행동.** 에이전트가 존재하지 않는 도구를 호출하거나 인수를 조작함.
2. **범위 확장(Scope creep).** 에이전트가 사용자의 요청을 넘어 작업을 확장함(추가 PR 생성, 추가 이메일 전송).
3. **계단식 오류.** 하나의 잘못된 호출이 하류 영향을 초래함. 환각 SKU가 네 번의 API 호출을 유발 — 다중 시스템 사고.
4. **컨텍스트 손실.** 장기 작업이 초기 턴의 제약 조건을 잊어버림.
5. **도구 오용.** 올바른 도구를 잘못된 인수로 호출하거나 완전히 잘못된 도구를 사용함.

계단식 오류가 가장 위험합니다. 에이전트는 "실패했다"와 "작업이 불가능하다"를 구분하지 못하며, 종종 루프를 닫기 위해 400 오류에 성공 메시지를 환각합니다.

### 완화: 모든 단계에서의 게이트

추론 체인의 모든 단계에서 환경 상태에 대한 사실적 근거를 확인하는 자동화된 검증 게이트. 구체적으로:

- 단계별 안전 분류기 (Lesson 21).
- 도구 호출 인수 검증 (Lesson 06).
- 알려진 사실에 대한 검색 콘텐츠 교차 확인 (Lesson 05, CRITIC).
- 상태 재조사로 성공 환각 탐지 (파일이 실제로 생성되었는가?).

### 실패 모니터링이 잘못되는 경우

- **충돌만 태깅.** 대부분의 에이전트 실패는 유효해 보이는 출력을 생성합니다. 콘텐츠 수준 검사가 필요합니다.
- **기준선 없음.** 드리프트 감지에는 마지막으로 알려진 정상 상태가 필요함; 없으면 "악화되고 있다"고 말할 수 없음.
- **과도한 알림.** 모든 실패가 페이지를 생성합니다. 클러스터링하고 비율을 제한하세요.

## 빌드하기

`code/main.py`는 stdlib 실패 모드 태거를 구현합니다:

- 다섯 가지 모드를 다루는 합성 트레이스 데이터셋.
- 모드별 탐지기 함수 (도구 호출, 출력, 반복 작업의 시그니처 패턴).
- 각 트레이스에 레이블을 지정하고 모드 분포를 보고하는 태거.

실행:

```
python3 code/main.py
```

출력: 트레이스별 레이블 + 전체 분포, Phoenix의 트레이스 클러스터링이 제공하는 것을 저렴하게 재현.

## 사용하기

- **Phoenix** — 프로덕션 드리프트 클러스터링용 (Lesson 24).
- **Langfuse** — 세션 재생 + 주석용.
- **커스텀** — 관찰 가능성 플랫폼이 감지할 수 없는 도메인별 시그니처용.

## 배포하기

`outputs/skill-failure-detector.md`는 도메인에 맞춤화된 실패 모드 탐지기를 생성하여 트레이스 저장소에 연결합니다.

## 연습 문제

1. "성공 환각" 탐지기를 추가합니다: 에이전트가 성공을 반환했지만 대상 상태가 변경되지 않음.
2. 구축한 제품의 실제 트레이스 100개를 태깅합니다. 어떤 모드가 지배적인가요? 수정 비용은 얼마인가요?
3. "계단식 반경" 메트릭을 구현합니다: N단계에서 실패가 발생했을 때, 몇 개의 하류 단계에 영향을 미쳤나요?
4. MASFT의 14가지 실패 모드를 읽습니다. 제품에 적용되는 세 가지를 선택합니다. 탐지기를 작성합니다.
5. 하나의 탐지기를 CI 작업에 연결합니다: 트레이스의 5% 이상이 모드를 태깅하면 빌드 실패.

## 주요 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|------------------|-----------|
| MASFT | "다중 에이전트 실패 분류학" | 버클리 14-모드 분류 |
| Cascading error | "파급 효과 실패" | 하나의 초기 실수가 N단계로 전파 |
| Context loss | "제약 조건을 잊음" | 장기 턴이 초기 턴의 사실을 떨어뜨림 |
| Tool misuse | "잘못된 도구 / 잘못된 인수" | 유효한 호출, 잘못된 호출 방식 |
| Success hallucination | "가짜 완료" | 에이전트가 400에서 성공 주장; 상태 변경 없음 |
| Scope creep | "초과 달성" | 에이전트가 요청받은 것보다 더 많이 수행 |
| Instruction-following deviation | "불복종" | 시스템 프롬프트 또는 사용자 제약 무시 |
| Sub-intention errors | "계획 버그" | 계획 실행에서 생략, 중복, 무질서 |
