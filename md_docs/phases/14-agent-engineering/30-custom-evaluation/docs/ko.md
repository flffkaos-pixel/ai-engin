# 맞춤 평가

> 특정 제품은 자체 평가가 필요하다. 여기서는 질문 생성(golden set)의 과정을 보여준다. 레슨 33(Dify)은 애플리케이션 빌드의 파이프라인을 보여준다. 레슨 34(Weave)는 평가가 실험 관리에 연결되는 방식을 보여준다. LLM-as-judge로 합성골든 세트를 생성하고, 수동 검증한 다음, 지속적인 평가를 위한 스코어 카드를 배포한다.

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 26 (LM Eval Harness), Phase 14 · 19 (Benchmarks)
**Time:** ~75분

## 학습 목표

- 커스텀 평가를 구축하는 세 단계(generate → validate → deploy)를 설명한다.
- 복잡한 정답이 없는 작업(요약, 생성)에 대한 합성 gold를 위한 LLM-as-judge 평가기를 설계한다.
- golden set을 평가 시스템(레슨 26)에 연결하는 평가기 인터페이스를 빌드한다.
- 평가가 실험 관리(레슨 34) 및 관찰 가능성(레슨 23-24)과 어떻게 연결되는지 설명한다.

## 문제

표준 벤치마크(SWE-bench, GAIA)는 일반적이다. 특정 제품은 자체 평가가 필요하다 — 트레이드오프: "자체 도메인에 대해 내가 승인하는 것만 측정한다." 이상적으로는 수동으로 골든을 구축하지만, 확장되지 않는다. LLM-as-judge를 사용한 합성 생성을 적용한다: 합성 gold를 생성하고, 사람이 검증하며, 프로덕션에서 지속적으로 평가한다. 정밀도가 완벽하지는 않지만 확장되고, 부족한 부분은 수동으로 채운다. 평가는 관찰 가능성 파이프라인에 통합된다.

## 개념

### 평가 유형

| 유형 | 방법 | 정확도 | 확장성 |
|------|--------|---------|---------|
| 수동 | 사람이 출력 평가 | 높음 | 나쁨 |
| LLM-as-judge | LLM이 출력 평가 | 중간-높음 | 좋음 |
| 골든 세트 | 사람이 작성한 예상 출력 | 높음 | 중간 |
| 합성 골든 | LLM이 예상 출력 생성 | 중간-높음 | 좋음 |

수동이 정확도를 제공한다. 골든 세트는 사람이 검증한 정확도를 제공한다. 합성 골든은 LLM-as-judge가 사람의 시간을 확장하게 한다. 제품에서 모든 입력을 수동으로 평가할 수는 없다 — 합성 + LLM-as-judge는 대부분의 설정에 가장 적합한 균형이다.

### 단계

**1단계: 골든 세트 생성** "최고의 도우미" 스타일 평가의 경우:

- 작업이 결정론적인가(코드에서 괄호, 왼쪽 또는 오른쪽)? → 자동 평가기를 빌드.
- 작업이 개방형인가(고객 이메일 요약)? → LLM에게 모범 답변을 생성하도록 요청.
- 모호한가(시스템이 까다로운 법률 질문에 잘못된 답변을 함)? → 수동 골든.

**2단계: LLM-as-judge 평가기**

- 원래 질문 + 에이전트 출력 + 골든 답변 → 스코어 카드.
- 스코어 카드는 객관식: "출력이 정확하고 편향되지 않으며 안전하다."
- LLM-as-judge는 LLM을 사용하여 평가.

**3단계: 스코어 카드 배포**

- 연속 평가를 위해 평가 결과를 관찰 가능성(레슨 23-24)에 게시.
- 이전 기준과 델타를 보여주는 평가 대시보드.
- 프롬프트 템플릿, 모델, 공급자를 변경할 때 골든 세트를 다시 실행.

### 평가 대시보드

평가 결과는 프롬프트 템플릿(레슨 31), 모델, 공급자별로 집계되어야 한다. 각 차원에 대한 기준선과 델타를 표시한다. Flux가 있는 Weights & Biases(레슨 34)가 평가를 실험 관리에 연결한다. 평가 대시보드는 "프롬프트 A가 프롬프트 B보다 이 골든 세트에서 5% 더 좋음"을 보여준다.

### 평가와 관찰 가능성의 오해

| 개념 | 관찰 가능성은 평가를 위해 이것을 사용 | 평가는 관찰 가능성을 위해 이것을 사용 |
|-------|--------------------------------------|--------------------------------------|
| 추적 | 출력에 평가 점수 적용 | 점수를 위한 추적 컨텍스트에서 로그 사용 |
| LLM-as-judge | 평가기로 사용 | 평가 대시보드에 기록 |
| 골든 세트 | 평가 기준 | 기준선을 설정하기 위해 관찰 가능성에 게시 |

둘은 평가기 인터페이스에서 연결된다: 평가기가 점수를 생성하고, 관찰 가능성이 점수를 추적한다.

### 이 패턴이 잘못되는 경우

- **LLM-as-judge를 모든 것에 사용.** LLM-as-judge는 결정론적 작업에 나쁨. 항상 작업 유형과 일치시키라.
- **수동 검증 없음.** 골든 세트가 합성 생성만으로 구축됨. 사람이 검증하지 않으면 모델이 편향을 배울 수 있음.
- **실험과 평가 분리.** 평가 대시보드가 프롬프트 변경에 연결되지 않으면 프롬프트 엔지니어링이 맹목적으로 이루어짐.

## 직접 구현하기

`code/main.py`는 커스텀 평가 파이프라인을 구현:

- 질문 + 예상 출력이 포함된 골든 세트 생성기.
- LLM-as-judge 평가기 (점수 카드).
- 평가 결과를 관찰 가능성에 게시.
- 대시보드 쿼리 (골든 세트에 대한 기준선 점수).

실행:

```
python3 code/main.py
```

실제 LLM 없이: 합성 점수 카드와 평가 결과를 stdout으로 출력 — 커스텀 평가 하네스를 보여줌.

## 활용하기

- LLM-as-judge로 합성 골든 세트를 생성하고 중요한 사례를 수동으로 검증.
- 스코어 카드를 관찰 가능성(레슨 23-24)에 게시.
- 평가 결과를 프롬프트 템플릿 및 모델 변경에 연결 (레슨 31, 34).

## 배포하기

`outputs/skill-custom-eval.md` scaffolds a golden set (generated + validated), LLM-as-judge evaluators, score card deployment, and evaluation dashboard.

## 연습 문제

1. 결정론적 작업(코드 구문 분석)을 위한 평가기 구현하고 LLM-as-judge와 비교. 결정론적 작업에 LLM-as-judge가 좋지 않은 이유는?
2. 합성 골든용 점수 카드 확장: "안전", "정확", "간결" 각각에 대한 점수.
3. 평가 대시보드 쿼리 구현: 작업 + 모델 + 공급자별로 집계.
4. 프롬프트 템플릿 버전 관리 연결: 프롬프트 변경이 평가 점수에 미치는 영향 측정.
5. 수동 검증 단계 구축: 휴먼 평가자가 합성 생성된 골든을 승인/거부하는 UI.

## 주요 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|-------------------|-----------|
| Golden set | "정답" | 에이전트 출력과 비교할 예상 에이전트 출력 |
| LLM-as-judge | "모델이 모델 평가" | LLM을 사용하여 다른 LLM의 출력 평가 |
| Score card | "평가 출력" | 점수 출력(정확도, 안전, 간결) |
| Evaluation dashboard | "기준선 + 델타" | 시간 경과에 따른 평가 점수 추적, 변경 사항 하이라이트 |
