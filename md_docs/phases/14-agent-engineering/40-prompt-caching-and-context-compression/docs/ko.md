# 프롬프트 캐싱, 컨텍스트 압축

> 프롬프트 캐싱은 반복되는 프롬프트 접두사(시스템 프롬프트, 도구 설명)를 공급자 측에 캐시하여 지연 시간과 비용을 줄인다. 도구
> 설명 오버헤드에서 가장 큰 이점을 얻는다. 컨텍스트 압축은 긴 대화를 요약하여 컨텍스트 윈도우를 보존한다.

**Type:** Learn
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 01 (Agent Loop), Phase 14 · 05 (Model Router)
**Time:** ~45분

## 학습 목표

- 프롬프트 캐싱이 지연 시간과 비용을 줄이는 방법을 설명한다.
- 캐시 적중을 극대화하기 위해 프롬프트 접두사를 구조화하고,
- 컨텍스트 압축(요약)과 프롬프트 캐싱의 차이점을, 그리고
- 압축이 다단계 에이전트 작업의 컨텍스트 윈도우를 보존하는 방법을 설명한다.

## 문제

에이전트는 매 턴마다 시스템 프롬프트와 도구 정의를 전송한다. 이 프롬프트 접두사는 5-10k 토큰일 수 있으며, 새로운 턴마다 반복된다. 캐싱은 이 접두사를 저장하여 첫 번째 턴 이후의 지연 시간을 50-80% 줄인다. 컨텍스트 압축은 컨텍스트 윈도우를 낭비하는 오래된 대화 기록을 요약한다.

## 개념

### 프롬프트 캐싱

공급자(Anthropic, OpenAI, Google)가 접두사 캐싱을 지원. 시스템 프롬프트, 도구 정의, 고정 컨텍스트가 캐시됨. 반환값은 동등. Anthropic: `cache_control`이 있는 `ephemeral` 캐시. OpenAI: `stored` 접두사. Google: 시맨틱 캐싱.

### 두 기술 비교

| 기술 | 대상 | 효과 | 사용 예시 |
|-----------|---------|--------|------------|
| 프롬프트 캐싱 | 반복되는 접두사 | 지연 시간 50-80% 감소, 비용 50-90% 감소 | 시스템 프롬프트, 도구 설명, k-예제 |
| 컨텍스트 압축 | 긴 기록 | 컨텍스트 윈도우 30-70% 절약, 지연 시간 약 10% 감소 | 다단계 에이전트 로그, 긴 대화 |

둘은 상호 배타적이지 않음. 압축 → 요약 + 캐싱된 접두사로 계속.

### 도구 설명 오버헤드

2026년 현재, 도구 설명은 시스템 프롬프트보다 큰 경우가 많다. 도구 설명을 포함한 시스템 프롬프트는 쉽게 5-10k 토큰 이상이 된다. 캐싱은 이 오버헤드를 제거한다.

- 50개 도구, 각각 100 토큰 = 5k 토큰.
- 캐시 적중: 첫 번째 턴 이후 5k 토큰이 캐시에서 제공됨.
- 첫 번째 턴 비용(쓰기 + 캐시 읽기), 그 이후 턴(캐시 읽기 전용).

### 캐시 전략

2026년에는 공급자의 캐시 동작이 합리적이다. Anthropic은 `cache_control`이 있는 `ephemeral` 캐시를 사용한다. OpenAI는 버전이 지정된 프롬프트를 위한 `stored` 접두사를 사용한다. Google은 시맨틱 캐싱(일치하는 대신 의미 기반)을 사용한다. 경험 법칙:

- 캐시: 시스템 프롬프트 + 도구 설명 + 고정 k-예제.
- 캐시하지 않음: 대화 기록, 사용자 입력, 검색 결과.
- Anthropic `cache_control` 중단점: 캐시 사이의 경계를 명시적으로 표시.

### 컨텍스트 압축 요약

프롬프트 캐싱과 달리, 컨텍스트 압축은 편집을 한다. 오래된 대화 턴을 요약하여 컨텍스트를 보존한다. 이 압축이 턴을 완전히 제거하지 않으면 캐싱과 함께 작동한다.

- 에이전트가 50턴을 실행한다. 전체 기록은 20k 토큰이다.
- 압축은 턴 1-40을 요약하고, 턴 41-50을 그대로 유지한다.
- 새 컨텍스트: 요약(1k) + 최근 기록(5k) + 프롬프트 접두사(캐시됨).

### 이 패턴이 잘못되는 경우

- **도구 설명을 캐시하지 않음.** 많은 에이전트가 50-100개 도구를 등록하고 매 턴마다 다시 전송. 대부분의 프롬프트 오버헤드.
- **매 턴마다 캐시 무효화.** 대화 기록이 변경되면 전체 프롬프트 접두사가 캐시에서 제거. 시스템 프롬프트와 도구를 대화 기록과 분리.
- **컨텍스트 압축이 실제로 도움이 되는 경우에만 사용.** 에이전트가 10턴 미만으로 실행되면 압축으로 인해 오버헤드가 추가됨. 30턴 이상에서만 이점.
- **공급자의 캐시 제한 무시.** Anthropic은 캐시 읽기에 속도 제한이 있음 (분당 요청 수). 대규모 배포 모니터링.

## 직접 구현하기

`code/main.py`는 프롬프트 캐싱 및 컨텍스트 압축 시스템을 구현:

- 캐시 인식 프롬프트 빌더: 프롬프트를 캐시 가능한 접두사(시스템 + 도구)와 캐시 불가능한 접미사(대화)로 분리.
- 캐시 객체: 적중/실패 통계가 있는 인메모리 TTL 캐시.
- 컨텍스트 압축기: 오래된 대화 턴을 요약. 새 요약 + 최근 턴 출력.
- 캐시 비용 계산기: 캐시 적중 비용, 캐시 실패 비용, 절감액 절대값/백분율 표시.

실행:

```
python3 code/main.py
```

출력: 캐시 적중/실패, 비용 절감, 압축된 컨텍스트 크기를 시뮬레이션한 여러 턴.

## 활용하기

- **시스템 프롬프트 + 도구 설명을 항상 캐시.** 이 접두사를 대화 기록과 분리.
- **컨텍스트 압축은 30턴 이상에서만 사용.** 더 짧은 대화에서는 오버헤드가 이점을 초과.
- **공급자별 캐시 제한 모니터링.** 속도 제한에 도달하면 캐시 정책 조정.

3. 컨텍스트 압축기 임계값 추가: "25000 토큰 후 압축". 임계값 조정이 지연 시간에 어떤 영향을 미치는가?
4. 캐시된 접두사 분리: 접두사를 변경하면(도구 추가) 캐시가 어떻게 무효화되는가? 캐시 제거 전략은?
5. 다른 공급자의 캐시 동작 비교: Anthropic, OpenAI, Google을 장난감에서 시뮬레이션. 어떤 공급자의 캐시 형태가 에이전트 작업에 가장 적합한가?

## 주요 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|-------------------|-----------|
| Prompt caching | "접두사 캐싱" | 반복되는 프롬프트 접두사(시스템 + 도구)를 캐시에 저장 |
| Cache control | "캐시 중단점" | Anthropic의 캐시 가능한 콘텐츠 경계를 표시하는 방법 |
| Cache hit | "캐시에서 제공" | 접두사가 캐시에 있음 → 재전송 없음 |
| Cache miss | "전체 프롬프트 전송" | 접두사가 캐시에 없음 → 전체 프롬프트 전송 |
| Context compression | "히스토리 요약" | 오래된 턴을 요약하여 컨텍스트 윈도우 보존 |
| Tool description overhead | "도구 프롬프트 크기" | 시스템 프롬프트보다 큰 도구 설명 |
