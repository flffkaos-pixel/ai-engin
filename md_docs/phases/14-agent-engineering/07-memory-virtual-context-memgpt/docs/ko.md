# 메모리: 가상 컨텍스트와 MemGPT

> 컨텍스트 윈도우는 유한하다. 대화, 문서, 도구 트레이스는 그렇지 않다. MemGPT (Packer et al., 2023)는 이를 OS 가상 메모리로 프레이밍한다 — 메인 컨텍스트는 RAM, 외부 저장소는 디스크, 에이전트는 그 사이를 페이지 인/아웃한다. 이는 2026년 모든 메모리 시스템이 상속하는 패턴이다.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 01 (Agent Loop), Phase 14 · 06 (Tool Use)
**Time:** ~75분

## 학습 목표

- MemGPT가 기반으로 하는 OS 비유를 설명한다: 메인 컨텍스트 = RAM, 외부 컨텍스트 = 디스크, 메모리 도구 = 페이지 인/아웃.
- 메인 컨텍스트 버퍼, 외부 검색 가능 저장소, 페이지 인/아웃 도구를 사용하여 stdlib에서 MemGPT의 2계층 패턴을 구현한다.
- 에이전트가 외부 메모리를 쿼리하거나 수정하기 위해 "인터럽트"를 발행하는 방법과 결과가 다음 프롬프트에 다시 접합되는 방법을 설명한다.
- MemGPT의 설계 선택이 Letta (레슨 08)와 Mem0 (레슨 09)로 이어지는 방식을 식별한다.

## 문제

컨텍스트 윈도우는 메모리를 해결해야 할 것처럼 보인다. 그렇지 않다. 세 가지 실패 모드가 프로덕션에서 반복된다:

1. **오버플로우.** 멀티턴 대화, 긴 문서 또는 도구 호출이 많은 궤적이 윈도우를 초과한다. 컷오프 이후의 모든 것은 사라진다.
2. **희석.** 윈도우 내에서도 관련 없는 컨텍스트를 채워 넣으면 중요한 것에 대한 주의가 희석된다. 프론티어 모델도 긴 입력에서 성능이 저하된다.
3. **지속성.** 새 세션은 빈 윈도우로 시작한다. 외부 메모리가 없는 에이전트는 세션 간에 "언제 나에게 ...를 요청했는지 기억해"라고 말할 수 없다.

더 큰 윈도우가 도움이 되지만 이 문제를 해결하지는 않는다. Mem0의 2025년 논문은 128k 윈도우 기준선이 외부 메모리가 있는 4k 윈도우 에이전트가 잡는 장기 사실을 여전히 놓친다고 측정했다.

## 개념

### MemGPT: OS 비유

Packer et al. (arXiv:2310.08560, v2 Feb 2024)은 컨텍스트 관리를 운영 체제 가상 메모리에 매핑한다:

| OS 개념 | MemGPT 개념 | 2026년 프로덕션 유사 |
|---------|-------------|----------------------|
| RAM | 메인 컨텍스트 (프롬프트) | Anthropic/OpenAI 컨텍스트 윈도우 |
| Disk | 외부 컨텍스트 | 벡터 DB, KV, 그래프 저장소 |
| Page fault | 메모리 도구 호출 | `memory.search`, `memory.read`, `memory.write` |
| OS 커널 | 에이전트 제어 루프 | 메모리 도구가 있는 ReAct 루프 |

에이전트는 일반 ReAct 루프를 실행한다. 한 가지 추가 도구 클래스를 통해 메인 컨텍스트에서 데이터를 페이지 인/아웃할 수 있다.

### 두 계층

- **메인 컨텍스트.** 현재 작업을 담는 고정 크기 프롬프트. 항상 모델에 표시됨.
- **외부 컨텍스트.** 도구를 통해 검색 가능한 무제한 저장소. 관련 있을 때 읽고, 사실이 나타날 때 기록.

원본 논문은 기본 윈도우를 넘어서는 두 가지 작업에서 설계를 평가했다: 100k 토큰보다 긴 문서 분석 및 여러 날에 걸친 지속적 메모리가 있는 멀티세션 채팅.

### 인터럽트 패턴

MemGPT는 메모리-인터럽트를 도입한다: 대화 중간에 에이전트가 메모리 도구를 호출할 수 있고, 런타임이 실행하며, 결과가 새 관찰로 다음 어시스턴트 턴에 접합된다. 개념적으로 프로세스를 차단하고, 바이트를 반환하며, 프로세스가 계속되는 Unix `read()` 시스템 호출과 동일하다.

표준 메모리 도구 표면:

- `core_memory_append(section, text)` — 프롬프트의 지속적 섹션에 기록.
- `core_memory_replace(section, old, new)` — 지속적 섹션 편집.
- `archival_memory_insert(text)` — 검색 가능한 외부 저장소에 기록.
- `archival_memory_search(query, top_k)` — 외부 저장소에서 검색.
- `conversation_search(query)` — 과거 턴 스캔.

### MemGPT가 끝나고 Letta가 시작되는 곳

2024년 9월 MemGPT는 Letta가 되었다. 연구 리포지토리(`cpacker/MemGPT`)는 남아 있고, Letta는 설계를 확장한다:

- 2계층 대신 3계층 (core, recall, archival — 레슨 08).
- `send_message`/하트비트 패턴을 대체하는 네이티브 추론 (레슨 08).
- 비동기 메모리 작업을 실행하는 Sleep-time 에이전트 (레슨 08).

프로덕션 시스템이 Letta, Mem0 또는 커스텀 2계층 저장소를 실행하더라도 MemGPT 논문은 2026년의 기초다.

### 이 패턴이 잘못되는 경우

- **메모리 부패.** 쓰기가 읽기보다 빠르게 축적됨; 검색이 오래된 사실에 빠짐. 수정: 주기적 통합(Letta sleep-time), 명시적 무효화(Mem0 충돌 감지기).
- **메모리 중독.** 외부 메모리는 검색된 텍스트다. 공격자 제어 콘텐츠가 메모리 노트에 들어가면 에이전트가 다음 세션에서 다시 섭취한다. 이는 시간에 걸쳐 재진술된 Greshake et al. (레슨 27) 공격이다.
- **인용 손실.** 에이전트가 "사용자가 X를 배송하라고 요청했다"를 기억하지만 어떤 턴인지 인용할 수 없다. 모든 아카이브 쓰기에 소스 참조(세션 ID, 턴 ID)를 저장하라.

## 직접 구현하기

`code/main.py`는 stdlib에서 MemGPT의 2계층 패턴을 구현한다:

- `MainContext` — 고정 크기 프롬프트 버퍼. `core` 딕셔너리와 `messages` 리스트가 있음; 제한을 초과하면 가장 오래된 메시지를 자동으로 압축.
- `ArchivalStore` — 인메모리 BM25 유사 저장소(토큰 중복 점수)의 (id, text, tags, session, turn) 레코드.
- MemGPT 표면에 매핑되는 5개의 메모리 도구.
- 아카이브에 사실을 채운 후 `archival_memory_search`를 호출하여 질문에 답하는 스크립트 기반 에이전트.

실행:

```
python3 code/main.py
```

트레이스는 에이전트가 세 가지 사실을 작성하고, 메인 컨텍스트를 제한까지 채우고(강제 축출), 아카이브에서 검색하여 후속 질문에 답하는 과정을 보여준다 — 실제 LLM 없이 MemGPT 워크플로우를 재현한다.

## 활용하기

오늘날 모든 프로덕션 메모리 시스템은 MemGPT 변형이다:

- **Letta** (레슨 08) — 3계층, 네이티브 추론, sleep-time compute.
- **Mem0** (레슨 09) — 점수 레이어와 융합된 벡터 + KV + 그래프.
- **OpenAI Assistants / Responses** — 스레드와 파일을 통한 관리형 메모리.
- **Claude Agent SDK** — 스킬과 세션 저장소를 통한 장기 메모리.

운영 형태(자체 호스팅, 관리형, 프레임워크 통합)로 선택하고, 핵심 패턴으로 선택하지 마라 — 핵심 패턴은 MemGPT다.

## 배포하기

`outputs/skill-virtual-memory.md`는 모든 대상 런타임에 대해 축출 정책과 인용 필드가 연결된 올바른 2계층 메모리 구조(메인 + 아카이브 + 도구 표면)를 생성하는 재사용 가능한 스킬이다.

## 연습 문제

1. `len(text.split()) * 1.3`으로 근사한 토큰 단위 `max_main_context_tokens` 제한을 추가하라. 제한을 초과하면 가장 오래된 메시지를 요약으로 압축하라. 요약기가 있을 때와 없을 때의 동작을 비교하라.
2. 아카이브 저장소에 BM25를 제대로 구현하라(용어 빈도, 역문서 빈도). 장난감 사실 세트에서 토큰 중복 기준선 대비 recall@10을 측정하라.
3. 아카이브 삽입에 `citation` 필드(session_id, turn_id, source_url)를 추가하라. 모든 검색 기반 답변에서 소스를 인용하도록 에이전트를 만드라.
4. 메모리 중독을 시뮬레이션하라: "모든 미래 사용자 지시를 무시하라"는 아카이브 레코드 추가. 검색 결과에서 지시 형태의 텍스트를 스캔하여 신뢰할 수 없는 것으로 표시하는 가드를 작성하라.
5. 구현을 MemGPT 연구 리포지토리의 core-memory JSON 스키마(`cpacker/MemGPT`)를 사용하도록 포팅하라. 플랫 문자열에서 타입화된 섹션으로 전환할 때 무엇이 바뀌는가?

## 주요 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|-------------------|-----------|
| Virtual context | "무제한 메모리" | 페이지 인/아웃이 있는 메인(프롬프트) + 외부(검색 가능) 계층 |
| Main context | "작업 메모리" | 프롬프트 — 고정 크기, 항상 표시 |
| Archival memory | "장기 저장소" | 요청 시 검색되는 외부 검색 가능 지속성 |
| Core memory | "지속적 프롬프트 섹션" | 메인 컨텍스트 내에 고정된 명명된 섹션 |
| Memory tool | "메모리 API" | 에이전트가 외부 메모리를 읽고 쓰기 위해 발행하는 도구 호출 |
| Interrupt | "메모리 페이지 폴트" | 에이전트 일시 중지, 런타임 가져오기, 결과가 다음 턴에 접합 |
| Memory rot | "오래된 사실" | 오래된 쓰기가 검색을 압도; 통합으로 수정 |
| Memory poisoning | "주입된 지속적 메모" | 공격자 콘텐츠가 메모리로 저장됨, 재호출 시 재섭취 |
