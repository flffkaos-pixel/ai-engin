# 하이브리드 메모리: 벡터 + 그래프 + KV (Mem0)

> Mem0 (Chhikara et al., 2025)는 메모리를 세 개의 병렬 저장소로 처리한다 — 벡터(의미 유사도), KV(빠른 사실 조회), 그래프(엔티티-관계 추론). 점수 레이어가 검색 시 세 가지를 융합한다. 이것이 2026년 외부 메모리의 프로덕션 표준이다.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 07 (MemGPT), Phase 14 · 08 (Letta Blocks)
**Time:** ~75분

## 학습 목표

- 단일 저장소(벡터만, 그래프만, KV만)가 에이전트 메모리에 불충분한 이유를 설명한다.
- Mem0의 세 가지 병렬 저장소와 각각이 최적화하는 대상을 명명한다.
- Mem0의 융합 점수(관련성, 중요성, 최신성)와 이것이 계층 구조가 아닌 가중 합인 이유를 설명한다.
- 세 저장소 모두에 쓰는 `add()`와 결과를 융합하는 `search()`를 사용하여 stdlib에서 장난감 3-저장소 메모리를 구현한다.

## 문제

하나의 저장소는 세 가지 쿼리 클래스 중 하나에 대해 틀리다:

- **의미 유사도** — "지난주 에이전트 드리프트에 대해 무엇을 논의했나?" 벡터가 승리; KV와 그래프는 놓침.
- **사실 조회** — "사용자의 전화번호는 무엇인가?" KV가 승리; 벡터는 낭비, 그래프는 과잉.
- **관계 추론** — "어떤 고객이 같은 청구 엔터티를 공유하는가?" 그래프가 승리; 벡터와 KV는 답변 불가.

프로덕션 에이전트는 하나의 세션에서 세 가지 모두를 발행한다. 단일 저장소 메모리는 항상 그중 두 가지에 대해 틀리다. Mem0의 기여는 점수 함수로 융합하는 단일 `add`/`search` 표면 뒤에 세 가지를 모두 연결하는 것이다.

## 개념

### 세 가지 병렬 저장소

Mem0 (arXiv:2504.19413, April 2025)의 `add(text, user_id, metadata)`:

1. 텍스트에서 후보 사실 추출 (LLM 기반 단계).
2. 각 사실을 벡터 저장소(임베딩)에 기록하여 의미 검색용.
3. 각 사실을 KV 저장소에 (user_id, fact_type, entity) 키로 기록하여 O(1) 조회용.
4. 각 사실을 그래프 저장소(Mem0g)에 타입화된 엣지로 기록하여 관계 쿼리용.

`search(query, user_id)`:

1. 벡터 저장소가 임베딩 코사인으로 top-k 반환.
2. KV 저장소가 쿼리에서 파생된 (user_id, type, entity) 키로 직접 적중 반환.
3. 그래프 저장소가 쿼리 엔터티에서 도달 가능한 서브그래프 반환.
4. 점수 레이어가 세 가지를 융합.

### 융합 점수

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **관련성** — 벡터 코사인, KV 정확 일치, 그래프 경로 가중치.
- **중요성** — 쓰기 시 태깅되거나 학습됨 (일부 사실이 더 중요함: 이름, ID, 정책).
- **최신성** — 마지막 쓰기 또는 읽기 이후 시간에 따른 지수 감쇠.

가중치는 제품별로 조정된다. 채팅 에이전트는 높은 `w_recency`, 규정 준수 에이전트는 높은 `w_importance`, 검색 에이전트는 높은 `w_relevance`.

### Mem0g와 시간적 추론

Mem0g는 충돌 감지기를 추가한다. 새 사실이 기존 엣지와 모순되면 기존 엣지는 무효로 표시되지만 삭제되지 않는다. 시간적 쿼리("3월에 사용자의 도시는 어디였나?")는 유효-당시 서브그래프를 탐색한다.

이는 Letta의 무효화 패턴이 일반화하는 규정 준수 등급 동작이다.

### 벤치마크 수치

Mem0 논문 보고 (2025):

- **LoCoMo** (장문 대화 메모리): 91.6
- **LongMemEval** (장기 일화 메모리): 93.4
- **BEAM 1M** (1M 토큰 메모리 벤치마크): 64.1

비교 기준선 (전체 컨텍스트 128k LLM, 평면 벡터 저장소, 평면 KV) 모두 10점 이상 패배. 벤치마크만으로 선택을 정당화하지는 않지만(운영 형태가 중요), 수치는 융합 설계가 반올림 오류가 아님을 보여준다.

### 범위 분류

Mem0는 메모리를 범위별로 분할:

- **사용자 메모리** — `user_id` 키로 세션 간 지속.
- **세션 메모리** — 하나의 스레드 내에서 지속.
- **에이전트 메모리** — 에이전트 인스턴스별 상태.

모든 쓰기는 하나의 범위를 선택한다. 검색은 범위별 가중치로 범위를 가로질러 쿼리할 수 있다. 생각 없이 범위를 섞는 것은 "어시스턴트가 Alice에게 Bob의 프로젝트에 대해 말했다"는 사고로 이어진다.

### 이 패턴이 잘못되는 경우

- **임베딩 드리프트.** 처음 수백 개 쿼리에서 올바르게 보이는 벡터 결과가 코퍼스가 성장함에 따라 저하. 최상위 사용 레코드의 주기적 재임베딩 추가.
- **KV 스키마 확장.** `(user_id, type, entity)`는 모든 팀이 자신의 `type`을 추가할 때까지 간단해 보임. 분기별로 타입 세트 감사.
- **그래프 폭발.** 하나의 노이즈가 많은 추출기가 메시지당 50개의 엣지를 추가. `add` 호출당 그래프 쓰기 제한; 낮은 신뢰도 엣지 드롭.

## 직접 구현하기

`code/main.py`는 stdlib에서 3-저장소 패턴을 구현한다:

- `VectorStore` — 임베딩 대용으로 순진한 토큰 중복 유사도.
- `KVStore` — `(user_id, fact_type, entity)` 키의 딕셔너리.
- `GraphStore` — 타입화된 엣지 (subject, relation, object, valid).
- `Mem0` — `add()`, `search()`, 융합 점수, 범위 인식 검색이 있는 최상위 퍼사드.
- 다중 사용자, 다중 세션 대화에 대한 실행 트레이스.

실행:

```
python3 code/main.py
```

출력은 세 가지 개별 검색 경로와 융합된 top-k를 보여준다. `main()` 상단의 점수 가중치를 변경하고 순위가 어떻게 변하는지 관찰하라.

## 활용하기

- **Mem0 (Apache 2.0)** — 프로덕션 준비. Postgres + Qdrant + Neo4j로 자체 호스팅 또는 관리형 클라우드 사용.
- **Letta** — 3계층 core/recall/archival; 자체 벡터 및 그래프 백엔드 사용.
- **Zep** — 시간적 KG와 사실 추출이 있는 상용 대안.
- **커스텀 빌드** — 추출기(규정 준수) 또는 융합 가중치(최신성이 지배적인 음성 에이전트)에 대한 정확한 제어가 필요할 때.

## 배포하기

`outputs/skill-hybrid-memory.md`는 융합 점수기, 범위 분류, 시간적 무효화가 연결된 3-저장소 메모리 구조를 생성한다.

## 연습 문제

1. 장난감 벡터 유사도를 실제 임베딩 모델(sentence-transformers, Ollama, OpenAI embeddings)로 교체하라. 합성 긴 대화에서 recall@10을 측정하라. 1000번 쓰기 후 순위가 드리프트하는가?
2. 시간적 쿼리 `search(query, as_of=timestamp)`를 추가하라. 해당 시간 또는 이전에 유효한 레코드만 반환. 어느 저장소가 가장 많은 작업이 필요한가?
3. 충돌 감지기를 구현하라: 들어오는 사실이 그래프 엣지와 모순되면 이전 엣지를 무효화하고 둘 다 기록. "사용자가 베를린에 산다" -> "사용자가 리스본에 산다"로 테스트.
4. 융합 점수기에 `user_feedback` 차원을 추가하라(검색된 레코드에 대한 좋아요). 게이밍을 어떻게 방지할 것인가(에이전트가 이미 좋아한 레코드만 반환)?
5. Mem0 문서(`docs.mem0.ai`)를 읽어라. 장난감을 `mem0` 클라이언트 호출로 포팅하라. 동일한 20개 테스트 쿼리에서 검색 품질을 비교하라.

## 주요 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|-------------------|-----------|
| Hybrid memory | "벡터 + 그래프 + KV" | 병렬로 기록되고 검색 시 융합되는 세 가지 저장소 |
| Fact extraction | "메모리 수집" | 텍스트를 (엔티티, 관계, 사실) 튜플로 분해하는 LLM 단계 |
| Fusion scoring | "관련성 순위" | 관련성, 중요성, 최신성의 가중 합 |
| Scope | "메모리 네임스페이스" | user / session / agent — 누가 무엇을 볼지 결정 |
| Mem0g | "메모리 그래프" | 관계 쿼리를 위한 시간적 유효성이 있는 타입화된 엣지 |
| Temporal invalidation | "소프트 삭제" | 모순된 엣지를 무효로 표시; 절대 삭제하지 않음 |
| Embedding drift | "검색 부패" | 코퍼스 성장에 따라 벡터 품질 저하; 주기적 재임베딩 |
