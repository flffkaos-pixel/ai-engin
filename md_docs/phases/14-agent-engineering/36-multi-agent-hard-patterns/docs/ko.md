# 멀티 에이전트 하드 패턴

> 멀티 에이전트 시스템은 2026년에 유행하고 있지만 검증되지 않았다. 작업이 독립적이거나 자연스럽게 분할되는 경우에만 작동한다. 뚜렷한 하드 패턴이 있지만 — 중재자, 감독자, 계층 — 대부분의 문제는 단일 에이전트가 해결한다. 멀티 에이전트는 추가 복잡성을 정당화하는 데 필요한 문제가 있을 때 마지막 수단이어야 한다.

**Type:** Learn
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 01 (Agent Loop), Phase 14 · 12 (Workflow Patterns)
**Time:** ~60분

## 문제

멀티 에이전트는 불가피해 보인다. 하나의 에이전트가 모든 것을 처리할 수 없다 — 여러 개, 각각 특화되어야 한다. 그러나 멀티 에이전트 시스템은 중재, 조정, 오류 전파라는 근본적인 문제를 야기한다. 대부분의 프로덕션 멀티 에이전트 시스템은 단일 에이전트보다 성능이 떨어진다.

## 개념

### 언제 멀티 에이전트인가

멀티 에이전트는 다음 경우에만 문제를 해결한다:

1. **작업이 독립적이다.** 에이전트 A는 결과에 대해 에이전트 B와 대화할 필요가 없다.
2. **작업이 자연스럽게 분할된다.** 도메인이 "데이터 수집", "분석", "보고"로 분할된다.
3. **특화가 정확성을 향상시킨다.** "코드 생성" 에이전트가 "코드 검토" 에이전트보다 더 나은 코드를 생성한다.

다른 모든 경우 — 병목 현상이 발생하는 중재자, 엉키는 컨텍스트, 오류 전파.

### 세 가지 하드 패턴

**1. 중재자 (중앙 오케스트레이터).** 하나의 중재자가 작업을 라우팅. 이해하기 쉽지만 중재자가 병목이 됨. 확장되지 않음.

**2. 감독자 (에이전트가 작업을 위임).** 에이전트가 다른 에이전트를 생성. 병렬화에는 좋지만 깊이가 깊어질수록 오류 비용이 증가.

**3. 계층 (에이전트를 그룹화).** 그룹화가 작업 유형과 일치하는 경우 중재자보다 확장됨. 그룹 경계가 잘못되면 실패.

### 일반적인 실패 모드

| 실패 | 증상 | 원인 |
|-------|---------|-------|
| 중재자 병목 | 모든 작업이 단일 에이전트를 통과 | 에이전트가 라우팅보다 느림 |
| 컨텍스트 오염 | 에이전트가 공유 상태를 덮어씀 | 에이전트 경계가 불분명함 |
| 오류 전파 | 하위 에이전트 오류가 상위 에이전트로 전파됨 | 오류 처리가 부족함 |
| 통신 오버헤드 | 에이전트가 작업보다 통신에 더 많은 시간 소비 | 작업 분해가 너무 세분화됨 |
| 조정 좌절 | 에이전트가 서로를 기다리며 교착 상태 | 동기화 부족 |

### 포지셔닝

멀티 에이전트 패턴은 Azure AI Agent Service(레슨 37) 및 Microsoft의 마케팅과 같은 상위 계층에서 판매되고 있다. 실제 프로덕션 사용량은 2026년에 여전히 낮다. OpenAI의 'agentic' 기능(CUA, Operator, Deep Research)도 판매 중이다. 열광과 프로덕션 현실 사이의 균형을 유지하라.

### 이 패턴이 잘못되는 경우

- **멀티 에이전트를 기본값으로 사용.** 단일 에이전트가 작업을 처리할 수 있는지 먼저 확인하지 않고 아키텍처 구축.
- **중재자 없는 멀티 에이전트.** 모든 에이전트가 모든 것에 대해 통신 — 통신 오버헤드 폭발.
- **오류 전파 무시.** 하위 에이전트 실패가 상위 에이전트를 중단시킴 — 오류가 전체 시스템을 중단시키기 전에 차단.
- **과잉 특화.** 너무 많은 에이전트, 각각 너무 좁게 범위가 지정됨. 3-5개의 에이전트로 충분한 경우가 많음.

## 직접 구현하기

`code/main.py`는 간단한 멀티 에이전트 시스템을 구현:

- 중재자: 입력을 리뷰하고 에이전트에 라우팅.
- 세 개의 에이전트: "리서처", "라이터", "리뷰어".
- 각 에이전트는 격리된 컨텍스트를 가지며 결과를 반환.
- 중재자가 병목이 되는 타이밍을 보여주는 데모: 각 에이전트가 중재자를 통해 통신.

실행:

```
python3 code/main.py
```

출력: 각 에이전트가 완료된 작업을 보여주는 중재된 흐름.

## 활용하기

- **단일 에이전트를 먼저** — 작업이 자연스럽게 분할되지 않으면 멀티 에이전트를 건너뛰어라.
- **중재자 패턴** for simple routing needs, accept the bottleneck.
- **감독자 패턴** for parallel independent work.
- **계층 패턴** for work that naturally groups by domain.

## 연습 문제

1. 장난감 시스템을 세 개가 아닌 열 개의 에이전트로 확장. 중재자가 언제 병목이 되는가?
2. 감독자 패턴 추가: 에이전트가 결과를 보고 감독자가 다음 단계를 결정.
3. 오류 전파 차단: 하위 에이전트가 실패하면 중재자가 차단하고 재시도.
4. 단일 에이전트와 멀티 에이전트의 작업 완료 시간을 측정. 세 번째 에이전트가 이점을 어디서 잃는가?
5. 구체적인 사용 사례 선택: 리서처 → 라이터 → 리뷰어. 패턴이 실제 워크플로우와 일치하는가?

## 주요 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|-------------------|-----------|
| Mediator | "중앙 오케스트레이터" | 작업을 에이전트로 라우팅하는 단일 중재자 |
| Supervisor | "에이전트 위임" | 에이전트가 다른 에이전트를 생성 |
| Hierarchy | "에이전트 그룹화" | 그룹화된 에이전트가 작업 유형과 일치 |
| Bottleneck | "느린 중재자" | 중재자가 처리할 수 있는 것보다 많은 작업 |
| Error propagation | "계단식 오류" | 하위 에이전트 오류가 상위로 전파됨 |
